Implementation Plan: Apple Health XML Workout Import

Approval required Created 2026-07-01. Implementation must wait for explicit approval.

Task Summary

Extend the Apple Health historical import path so export.xml / Apple Health export ZIP imports <Workout> elements into the existing workouts table. The existing Health Auto Export JSON endpoint already imports workout summaries; this plan covers the native Apple Health XML backfill gap.

Current Behavior

HAE JSON workouts work

/health/workouts parses Health Auto Export workout JSON, stores the raw payload, converts summary fields, and calls storage.DB.UpsertWorkout.

XML import skips workouts

internal/applehealth.ParseXML only processes <Record> elements into storage.MetricPoint. It ignores <Workout> elements.

Import callers are points-only

cmd/import and internal/ui/import_handler.go both pass a single callback for metric point batches.

Storage is ready

The workouts table and read APIs already exist, keyed by external_id with upsert semantics.

Real Export Findings

A local unpacked Apple Health export at <LOCAL_APPLE_HEALTH_EXPORT_DIR>/ was inspected on 2026-07-01. Only structural counts and attribute shapes were used; implementation should not bake in personal paths or source names.

  • export.xml is about 2.3 GB and contains 862 <Workout> elements.
  • Workout activity distribution: Walking 818, Cycling 15, Running 7, Swimming 7, Downhill Skiing 4, Functional Strength Training 4, Hiking 4, Cross Training 1, Equestrian Sports 1, Underwater Diving 1.
  • There are 201 GPX files under workout-routes/, referenced by nested <WorkoutRoute> / <FileReference> elements.
  • Top-level workout attributes are limited to activity type, duration/unit, source, creation/start/end dates, and sometimes device/source version.
  • Useful measures are nested in <WorkoutStatistics>: active energy 860 rows, walking/running distance 829, basal energy 463, heart-rate stats 186, swimming/cycling/snow-sports distance for smaller subsets.
  • Workout heart-rate stats use average and maximum attributes, not sum.
  • Workout metadata includes HKMetadataKeySyncIdentifier on 339 workouts and HKExternalUUID on 143 workouts; 518 workouts have neither, so deterministic fallback IDs are required.

Desired Behavior

  • Apple Health XML import streams both metric points and workout summaries without loading the full export into memory.
  • <Workout> rows are converted into storage.Workout and upserted into workouts.
  • Existing metric import behavior stays backward-compatible for callers that only need points.
  • CLI import and Admin UI import report useful workout counts in logs/status where practical.
  • Historical imported workouts can unlock future data checks for #163/#165, but readiness experiments remain gated by actual sample size.

Proposed Design

Add a new parser API that keeps the existing point callback but also accepts an optional workout callback. Keep ParseXML, ParseZip, and ParseXMLFile as compatibility wrappers around the new path. 

type EmitOptions struct {
    Points   func([]storage.MetricPoint)
    Workouts func([]storage.Workout)
}

func ParseXMLWithOptions(r io.Reader, opts EmitOptions) error
func ParseZipWithOptions(path string, opts EmitOptions, onProgress func(read, total int64)) error
func ParseXMLFileWithOptions(path string, opts EmitOptions, onProgress func(read, total int64)) error

This avoids making internal/applehealth depend on internal/handler. XML-specific workout conversion should live in internal/applehealth and target storage.Workout directly.

Workout Field Mapping

  • external_id: prefer HKMetadataKeySyncIdentifier, then HKExternalUUID; fall back to a deterministic hash from type/start/end/source/duration/statistics when Apple exports lack IDs.
  • name: map workoutActivityType suffix into readable names such as Outdoor Run, Outdoor Cycling, Walking. Unknown values keep a readable suffix rather than failing import.
  • start_time, end_time: parse Apple Health XML timestamps with the existing HealthKit layout.
  • duration_sec: use duration plus durationUnit when present; otherwise compute from start/end.
  • energy_kcal: parse nested WorkoutStatistics type="HKQuantityTypeIdentifierActiveEnergyBurned" using sum and unit.
  • distance_km: parse nested distance statistics: walking/running, cycling, swimming, and downhill snow sports. Normalize with existing distance helpers.
  • avg_hr_bpm, max_hr_bpm: parse nested HKQuantityTypeIdentifierHeartRate statistics using average and maximum.
  • is_indoor: parse HKIndoorWorkout metadata when present.
  • avg_speed_kmh, max_speed_kmh, elevation_up_m, temperature_c, humidity_pct: parse workout metadata keys such as HKAverageSpeed, HKMaximumSpeed, HKElevationAscended, HKWeatherTemperature, and HKWeatherHumidity where unit-bearing values are stable.
  • hr_z*_sec: leave NULL for XML imports unless future evidence shows Apple export contains enough per-sample timing inside workout scope. The current export only has aggregate heart-rate statistics under workouts.

Data, API, and UX Impact

  • No schema migration is expected; workouts already exists and is auto-created by startup table setup.
  • No public endpoint changes are required.
  • Admin import status may gain optional workout counters; existing clients should tolerate additional JSON fields.
  • Upsert by external_id keeps repeated XML imports idempotent.
  • Metric caches still need backfill after import; workout rows do not feed existing aggregate cache tables directly.

  • Run Admin UI import on a small XML/ZIP fixture and confirm status completes without breaking existing point import progress.

  • Re-import the same fixture and confirm counts do not duplicate due to upsert.

Risks and Edge Cases

  • Apple Health XML workout attributes may vary by iOS version. Unknown fields should be skipped or left NULL rather than failing the whole import.
  • Fallback deterministic IDs can collide if they are too coarse. The fallback should include type, start, end, source, duration, distance, and energy when available.
  • The same real-world workout may appear from multiple sources or app versions. Upsert identity should preserve useful distinct workouts while avoiding duplicate rows for the same Apple sync identifier.
  • Plain Apple XML contains aggregate heart-rate stats for some workouts, but not per-sample timing inside the workout row, so HR-zone data should stay NULL for XML-imported workouts.
  • Readable workout-name mapping must not invent semantics. Unknown HealthKit activity types should remain visibly unknown-but-stable.
  • Large XML import must remain streaming and avoid collecting all workouts in memory.
  • GPX route import is intentionally out of scope; adding route storage would be a separate data model and privacy decision.

Rollback Plan

Revert the parser/import changes. Existing imported workout rows can remain because they are additive and keyed by external_id. If a bad import needs cleanup, delete rows by health_record_id or by the deterministic fallback ID prefix chosen during implementation.

Open Questions

  • Should XML import include workouts by default, or should CLI/Admin expose a flag to disable workout import for very conservative historical imports?
  • Should the implementation keep only summary rows from <Workout>, or also persist a route reference path for future diagnostics while still not importing GPX coordinates?
  • Should imported XML workouts be linked to a synthetic health_records row, or is health_record_id = NULL acceptable for CLI historical import batches?
  • Do we want to immediately re-check #163/#165 after importing real historical workouts, or leave that as a separate triage step?

Implementation Result

Implemented on 2026-07-03 on branch apple-health-xml-workout-import. The parser now supports streaming metric points and workout summaries from Apple Health XML without loading the full export into memory.

  • Added applehealth.EmitOptions plus ParseXMLWithOptions, ParseXMLFileWithOptions, and ParseZipWithOptions.
  • Kept the previous points-only parser functions as compatibility wrappers.
  • Added XML workout conversion into storage.Workout, including sync/external ID preference, deterministic fallback IDs, activity-name mapping, nested WorkoutStatistics, and selected metadata fields.
  • Updated CLI import and Admin UI import to upsert parsed workouts while preserving existing metric import and backfill behavior.
  • Added workout import counters to Admin import status JSON: workouts_parsed, workouts_upserted, workouts_failed.
  • Fixed distance normalization for Apple XML meter/foot distance units, which are present in workout statistics.
  • Kept zero-valued XML quantity records instead of dropping them, preserving meaningful zero values such as walking asymmetry.
  • Kept Admin import metric cleanup scoped to metric-point date ranges only; workout-only dates no longer expand RemoveAutoExportForRange.
  • Updated README to document XML workout summary import and route-import limitations.

Known Limitations After Implementation

  • GPX route files and route references are not imported.
  • XML-imported workouts do not compute HR-zone seconds because Apple XML workout summaries expose aggregate heart-rate statistics, not per-sample timing inside the workout row.
  • CLI historical import stores XML workouts with health_record_id = NULL; Admin UI import behaves the same for workout rows while metric points continue through the existing raw-import path.
  • Run/Cycle readiness experiments remain sample-size gated even after XML import; the inspected export contains 7 running and 15 cycling workouts.
