Implementation Plan: Admin UI Cleanup

Approval required before implementation

Task Summary

Rework the Health Dashboard admin page so it reads as a practical operator console instead of a long list of unrelated checks. The change should also fix the concrete review findings already identified: legacy-mode AI settings breakage, buttons inside <summary> toggling sections, full API key exposure, inconsistent left alignment, and the page title still saying “Settings”.

Current Behavior

  • /admin renders the title from admin_title, currently “Settings” / “Настройки”.
  • Multi-user mode shows one flat tab row: global admin/settings tabs mixed with user profile tabs.
  • The tenant panel has many peer-level checks: cache, gaps, quality, check-in, stress validation, readiness contract, readiness monitoring, operations, onboarding, and energy config.
  • Most sections were converted to <details>, but nested margins and summary arrows create uneven left edges.
  • Some action buttons sit inside <summary>, so clicking them can also open or close the section.
  • AI settings are multi-user-only in the template, while loadAdminSettings() still runs in all modes.
  • /api/admin/users returns full API keys and the UI renders them directly.

Desired Behavior

Operator Overview

The tenant tab starts with a compact status strip: cache/sync, gaps, data quality, check-in, readiness pipeline. Each item has a simple state and direct action.

Clear Scope

Global controls are visually separated from profile tabs. Tenant actions make the active schema obvious.

Readiness Group

Readiness diagnostics and operations become a profile sub-tab, not multiple top-level page sections.

EnergyBank Group

EnergyBank status and stress-drain settings become a profile sub-tab, separate from generic diagnostics.

Consistent Grid

All section titles, descriptions, forms, tables, and action cards share one left edge. No nested visual drift.

Assumptions and Unknowns

  • Keep the existing Go template architecture and embedded JS; do not introduce a frontend framework.
  • Keep htmx for existing fragments where it already works.
  • Do not change database schema or tenant isolation rules.
  • Assume the dev server remains available through Docker Compose at http://localhost:18080.
  • API keys must remain accessible after creation because an operator may need to view one again to configure an MCP server.
  • Global AI settings must be available in single-user mode as well as multi-user mode.

Files Likely to Change

  • internal/ui/templates/pages/admin.html - restructure tabs, tenant overview, section grouping, readiness block, button placement, and JS guards.
  • internal/ui/style.go - define a stricter admin layout grid, overview cards, tab grouping, section spacing, and left-edge alignment.
  • internal/ui/i18n_en.go, internal/ui/i18n_ru.go, internal/ui/i18n_sr.go - rename admin title and add labels for the new overview/grouping.
  • internal/ui/handler.go - mask user API keys in adminUsers and optionally expose only last characters.
  • internal/ui/admin_page_test.go, internal/ui/admin_template_scope_test.go - update template and user API tests for the new structure and key masking.
  • Possibly add or update a small focused UI test file if existing tests do not cover summary button placement or legacy AI settings.

Proposed Implementation Steps

  1. Rename the admin page title from “Settings” to “Admin” / localized equivalents, while leaving the user settings page unchanged.
  2. Split the tab row visually into global tabs and profile tabs. Keep the existing tab mechanics but style them as two grouped zones.
  3. Add a tenant overview strip at the top of profile tabs. Use existing fragment/API data where practical; avoid adding new expensive backend aggregation unless necessary.
  4. Collapse top-level tenant diagnostics to generic data health and maintenance groups.
  5. Add profile sub-tabs for Diagnostics, Readiness, and EnergyBank.
  6. Move readiness contract, monitoring, chip recompute, and onboarding under the Readiness profile sub-tab.
  7. Move EnergyBank stress validation and stress-drain configuration under the EnergyBank profile sub-tab.
  8. Move all buttons out of clickable <summary> toggles, or add an explicit helper that stops summary propagation for section-action buttons.
  9. Replace ad-hoc inline margins with shared admin layout classes so section content starts on one consistent left edge.
  10. Make loadAdminSettings() safe when AI settings controls are absent, and decide whether global AI settings should be visible in legacy mode.
  11. Mask API keys in the default user table, but add an explicit admin-only reveal/copy path so full keys remain available when needed.
  12. Update tests and run UI checks in desktop and mobile widths.

UX Impact

  • The first admin screen should answer “is anything broken?” before exposing detailed tools.
  • Routine operations should require fewer scrolls and fewer similarly weighted choices.
  • Experimental readiness work remains accessible but stops dominating the main admin surface.
  • Profile-specific actions remain scoped to the active tenant schema.

Security and Permission Impact

  • No auth or role model changes are planned.
  • Admin-only user management remains admin-only.
  • Full API keys should not be returned by the default list users endpoint.
  • Add an explicit admin-only reveal endpoint or action for a selected user key, because operators need to retrieve keys for MCP server setup.
  • Admin session auth is sufficient for API key reveal/copy; no extra password confirmation is required.
  • Regeneration is optional and can be deferred; reveal/copy is required for this pass.

Test Plan

  • Run go test ./internal/ui.
  • Run go test ./internal/registry ./internal/tenants if user-list or registry response shape changes.
  • Run go test ./... if handler contracts or shared types change beyond UI-only behavior.
  • Use the Docker Compose dev server and inspect http://localhost:18080/admin.
  • Check browser console for JS errors after loading admin, switching global/profile tabs, and opening readiness sections.

Manual QA Checklist

  • Admin page title says “Admin” / localized equivalent, not “Settings”.
  • Global tabs and profile tabs are visually distinct.
  • All admin section content starts on a consistent left edge.
  • Clicking Refresh/Run buttons does not unexpectedly collapse a section.
  • The profile tab for admin and mariia sends schema-scoped requests correctly.
  • Readiness tools are findable under the active profile's Readiness sub-tab, not scattered across the page.
  • EnergyBank tools are findable under the active profile's EnergyBank sub-tab.
  • User table does not display full API keys by default.
  • An admin can explicitly reveal or copy a user's full API key when configuring an MCP server.
  • Desktop and mobile layouts do not overlap, overflow, or hide primary actions.

Risks and Edge Cases

  • Moving htmx targets can silently break fragment reloads if hx-get URLs are not updated with the active schema.
  • Masking API keys without a reveal path would break MCP setup workflows; this pass must include explicit key reveal/copy.
  • A new overview strip can become another noisy surface if it duplicates every diagnostic rather than summarizing states.
  • Legacy single-user mode is easy to miss because current dev data is multi-user.

Rollback Plan

The changes are limited to Go templates, CSS, i18n strings, UI handlers, and tests. Rollback is a normal git revert of the admin UI cleanup commit. No database migrations or data backfills are planned.

Implementation Notes

  • Implemented on 2026-05-28 after approval in the current branch.
  • The admin page now has separate global and profile scope groups. Global contains admin user management and general AI settings; profiles contain tenant-scoped operational panels.
  • Each profile now has three sub-tabs: Diagnostics, Readiness, and EnergyBank. Readiness and EnergyBank controls were moved out of the general diagnostics flow.
  • Profile diagnostics now starts with a small operator overview linking to cache status, data gaps, quality audit, and check-in coverage.
  • Action buttons were moved out of section summaries where practical, and admin section content now uses shared left-aligned layout rules.
  • User API keys are masked in the default users table. A new admin-only reveal endpoint returns the full key for a selected user when an operator needs to configure MCP.
  • Global AI settings are rendered in the single-user path as well as the multi-user path; the JS loaders are guarded so absent controls do not crash older layouts.
  • The users table now has explicit table styles, mobile containment, and clipped API key display so revealing a long key does not stretch the admin page.

Known Limitations

  • The three-level tab structure is clearer than the previous mixed admin surface, but it still feels visually heavy. A later polish pass should consider a left rail or compact segmented scope control.
  • The mobile header still has pre-existing horizontal overflow outside the admin content. This pass did not change the global header/navigation.
  • Serbian labels for newly added admin grouping strings currently fall back through the existing i18n behavior rather than adding a full Serbian translation pass.
