AI-инсайт v2: один вывод без потери секций

План исправляет найденные ошибки данных и провайдерских вызовов, сокращает четыре конкурирующих AI-текста до одного синтеза и перестраивает утренний Telegram-отчёт по варианту A: решение → три причины → конкретное действие.

Дата: 2026-08-05 База: origin/main @ b53bfc0 Статус: ожидает одобрения Production-код не изменён

Резюме задачи

Текущий отчёт выводит отдельно rule-based секции Sleep / Yesterday / Recovery, три AI-комментария и ещё один AI-план. Из-за этого одна и та же мысль повторяется, а независимые генерации могут противоречить серверному EnergyBank и друг другу. В примере за 2026-08-04 одновременно появились «HRV выше нормы», «можно жёстко» и AI-утверждения о снижении HRV до недельного и месячного минимума.

Целевой принцип: сервер остаётся единственным источником вердикта и фактов. AI не принимает решение, а один раз кратко объясняет уже вычисленный вывод.

Текущее поведение и подтверждённые проблемы

Проблема Причина в коде Наблюдаемый эффект
Сдвинутые временные ряды rawMetricsFromDailyScores независимо удаляет NULL/0 из каждого массива, а prompt трактует одинаковый индекс как один день. Модель может сопоставить HRV одного дня со сном или RHR другого и придумать ложный тренд.
EnergyBank не попадает в фактический request Вердикт входит в hash, но GenerateRecommendation получает recoveryJSON без EnergyBank. AI способен отменить разрешённую нагрузку или, наоборот, советовать нагрузку при серверном rest.
Четыре независимых AI-текста Три leaf-вызова плюс RECOMMENDATION; каждый лист получает почти весь сырой набор метрик. Повторы, противоречия, лишние токены и задержка.
Слишком медицинский prompt Роль «clinical health analyst», жёсткие клинические пороги и причинные формулировки для consumer wearable. Диагностический тон и чрезмерная уверенность в данных Apple Watch.
Небезопасный legacy HTML renderAITake и финальная рекомендация вставляют модельный текст без HTML escaping. Символы <, >, & ломают Telegram-разметку.
Rich-разметка шумит при чтении и копировании Утренний отчёт использует <table>, три <blockquote> и <details>Freshness. В копии появляются буквальные Table / Quote / Freshness, а отчёт выглядит тяжелее.
Неполная обработка provider response Gemini читает только первую part и не проверяет finishReason, promptFeedback, usage; оба адаптера не имеют bounded retry. Обрезанный/заблокированный ответ может выглядеть как обычный сбой; transient ошибки не восстанавливаются.
Слабая наблюдаемость и завышенный лимит Нет provider request ID, latency, attempts и usage metadata; общий default — 5000 output tokens. Нельзя нормально оценить стоимость/латентность; короткий отчёт допускает чрезмерный ответ.
Ненадёжный OpenAI model picker Модели отбрасываются по эвристике имени, хотя /models не возвращает карту output-capabilities. Новая подходящая модель может исчезнуть из подсказок, а неподходящая — пройти фильтр.

Желаемое поведение

Структурированные секции Sleep, Yesterday, Recovery, alerts, readiness, EnergyBank и freshness остаются на сервере.
→
Детерминированный отбор Сервер выбирает максимум три причины, не более одной на секцию, и формирует canonical action.
→
Один AI-синтез Модель пишет только короткое объяснение. При ошибке отчёт полностью работает без AI.

Целевой Telegram-порядок

  1. Заголовок и одна короткая freshness/settling-плашка, если нужна.
  2. Сегодня: canonical action verdict и одна строка объяснения.
  3. Три компактных значения: Energy, Readiness, Sleep.
  4. Почему: максимум три отобранных сервером факта.
  5. План: детерминированное действие сервера; AI не вправе его менять.
  6. Одна строка свежести внизу без details.

Куда деваются секции

Они не удаляются. Полные BriefingSection продолжают питать dashboard/API. Для Telegram из каждой секции строится список типизированных кандидатов. Ranking выбирает наиболее важные факты; остальные доступны в полном health briefing, но не отправляются отдельными AI-эссе.

Архитектурный контракт

1. Датированные значения вместо сжатых массивов

Legacy-поля RawMetrics.HRV, Sleep и остальные сохраняются для существующего scoring-кода. Для AI добавляется новый date-aligned источник: 

type DailyHealthMetrics struct {
    Date      string   `json:"date"`
    HRV       *float64 `json:"hrv,omitempty"`
    RHR       *float64 `json:"rhr,omitempty"`
    Sleep     *float64 `json:"sleep,omitempty"`
    Deep      *float64 `json:"deep,omitempty"`
    REM       *float64 `json:"rem,omitempty"`
    Awake     *float64 `json:"awake,omitempty"`
    Steps     *float64 `json:"steps,omitempty"`
    Calories  *float64 `json:"calories,omitempty"`
    Exercise  *float64 `json:"exercise,omitempty"`
    SpO2      *float64 `json:"spo2,omitempty"`
    VO2       *float64 `json:"vo2,omitempty"`
    Resp      *float64 `json:"resp,omitempty"`
    WristTemp *float64 `json:"wrist_temp,omitempty"`
}

type RawMetrics struct {
    // existing fields remain unchanged
    Daily []DailyHealthMetrics `json:"daily,omitempty"`
}

Каждый элемент соответствует ровно одной календарной дате; отсутствующее значение остаётся null, поэтому модель не может принять вчерашний HRV за сегодняшний.

2. Серверный evidence packet

type MorningInsightEvidence struct {
    Date          string
    Verdict       string
    VerdictLabel  string
    VerdictReason string
    Action        string
    Reasons       []MorningInsightReason // 0..3, ranked
    Metrics       []DailyHealthMetrics    // aligned, newest first
    EnergyBank    *EnergyBank
    Readiness     MorningReadinessContext
    Freshness     MorningFreshnessContext
}

type MorningInsightReason struct {
    Key      string
    Section  string // sleep|yesterday|recovery|alert|headline
    Severity string // critical|warning|info|good
    Text     string // localized, rule-based
}

Ranking-инварианты:

  • critical/warning flags и safety ограничения выше positive сигналов;
  • не более одной причины из одной секции;
  • не более трёх причин всего;
  • причина не включается, если соответствующий источник stale/unknown;
  • AIAdviceMode=withheld запрещает тренировочный action;
  • canonical action определяется только серверным EnergyBank/readiness policy.

3. Один кэшируемый AI-блок

Вводится block key SYNTHESIS. Его hash строится из точного JSON MorningInsightEvidence плюс provider/model/reasoning/token budget/prompt revision. Старые SLEEP/YESTERDAY/RECOVERY/RECOMMENDATION rows не удаляются.

  • Если SYNTHESIS существует — Telegram, dashboard, MCP и API используют его и игнорируют старые leaf-блоки.
  • Если его ещё нет — текущий v1 cache остаётся временным fallback до первой успешной v2 генерации.
  • Rollback на старый бинарник автоматически снова увидит старые блоки; миграция БД не нужна.

4. Контракт AI-ответа

AI возвращает один короткий объект, а не самостоятельный medical verdict: 

{
  "explanation": "Почему выбран серверный план; 1–2 предложения, до 60 слов."
}

Общий GenerationRequest получает опциональную JSON Schema. OpenAI adapter переводит её в Responses API text.format.type=json_schema; Gemini generateContent — в responseMimeType=application/json и responseJsonSchema. После JSON parse выполняется semantic validation: непустой текст, word limit, отсутствие markup и запрещённых диагностических/прескриптивных конструкций. При провале AI-текст не сохраняется, а отчёт использует только server copy.

5. Provider-neutral telemetry и retry

type GenerationResult struct {
    Text           string
    RequestPayload []byte
    RequestID      string
    InputTokens    int64
    OutputTokens   int64
    TotalTokens    int64
    FinishReason   string
    Attempts       int
    Latency        time.Duration
}
  • Не более двух повторов после первоначальной попытки.
  • Retry только для 408, 429 и 5xx; 400/401/403 не повторяются.
  • Учитывается Retry-After; иначе exponential backoff с jitter.
  • Ожидание прерывается через context.Context.
  • В логах: provider, model, block, request ID, attempts, latency, token counts, finish reason; без API key и health payload.

Предположения и границы

  • Выбран визуальный вариант A из файла вариантов.
  • Morning report меняется; evening report сохраняет текущую структуру, кроме общего escaping/telemetry.
  • Серверные rule-based формулы readiness, EnergyBank и health sections не пересчитываются.
  • Схема PostgreSQL не меняется: block уже TEXT и принимает SYNTHESIS.
  • Существующие API-поля сохраняются. Новые клиенты получают canonical section summary; legacy recommendation указывает на тот же synthesis body.
  • Детальные секции остаются на dashboard/API и не генерируются моделью заново.
  • OpenRouter в эту работу не входит; новый общий контракт должен позволить добавить его отдельным адаптером.

Rollback

  1. Откатить application image на digest предыдущего deploy.
  2. Не выполнять SQL rollback: новая строка SYNTHESIS безопасна для старого кода и будет проигнорирована.
  3. Старые SLEEP/YESTERDAY/RECOVERY/RECOMMENDATION rows остаются в таблице и снова используются старым бинарником.
  4. Если требуется временно отключить AI, очистить provider API key/выключить AI через Admin; rule-based morning report продолжит работать.

Открытые вопросы

Блокирующих вопросов нет. Зафиксированы следующие решения по умолчанию:

  • целевой дизайн — вариант A;
  • AI пишет только объяснение, не план тренировки;
  • Telegram показывает top-3 причины, полные секции остаются на dashboard/API;
  • v1 cache сохраняется как rollback fallback;
  • OpenRouter остаётся отдельной будущей задачей.

Проверенные внешние контракты

  • OpenAI Responses API поддерживает structured output через text.format с JSON Schema; официальная документация рекомендует Structured Outputs вместо JSON mode, когда они доступны.
  • Gemini generateContent поддерживает response MIME type + response schema и отдельно предупреждает, что schema-valid output всё равно нужно семантически валидировать.
  • Google рекомендует exponential backoff с jitter только для transient 408/429/5xx и ограниченное число попыток.
