Cache-first dashboard performance

Implemented locally; not committed, pushed, or deployed

Цель и наблюдаемая проблема

Сделать интерактивный dashboard предсказуемо быстрым при обычной работе и сразу после backend restart, не жертвуя изоляцией tenants и не блокируя UI ради чтения raw-данных.

Production evidence от 2026-09-10: /api/health-briefing выполнялся за 1–992 мс; медленные запросы были /api/dashboard (6.507–8.492 с). Они совпали с тремя одновременными startup cache refresh. В это время один tenant пересчитывал историю с ранней датой 1970 года.

Текущее поведение

  • internal/storage/queries.go:GetDashboard по очереди запрашивает 12 сегодняшних карточек из metric_points и 12 вчерашних из hourly_metrics, плюс отдельные date/units запросы. Raw path попадает в пользовательский запрос.
  • cmd/server/main.go:startTenant запускает для каждого tenant отдельную goroutine через пять секунд после boot. Каждая запускает broad cache refresh: aggregates, scores и затем derived-state update.
  • После ingest targeted UpsertRecentCache и readiness recompute уже выполняются до debounced safety net. Значит normal current-day UI может опираться на cache, а не ждать raw fallback.
  • React loader запрашивал stable GET /api/dashboard параллельно с основными ресурсами, но response не использовался в view model. Его удаление из loader убирает лишнюю нагрузку со стартового user path.

Одобренное product-решение

Интерактивные dashboard reads становятся cache-first. Когда current cache ещё обновляется, UI показывает последний complete snapshot и явную метку «Обновляем данные», а не запускает raw metric scans на request path. Raw metric_points остаётся источником данных и используется ingestion/background rebuild, но не synchronous dashboard response.

Предположения и открытые вопросы

  • Семантика source priority для sum metrics должна совпасть с текущей preferredSourceForMetric; до изменения SQL её нужно зафиксировать fixture-тестом.
  • «Complete» означает успешный cache snapshot для даты, выбранной dashboard. Не означает, что телефон уже успел прислать самые свежие данные.
  • Если cache отсутствует на чистой установке, endpoint возвращает explicit unavailable state без raw scan. UI показывает existing empty/loading state и retry после cache completion.
  • Нужно определить budget: предлагается server-side /api/dashboard p95 < 500 мс на прогретом production-sized fixture; startup queue не должна ухудшать readiness или tenant schema gate.

Вероятно затрагиваемые файлы

  • internal/storage/queries.go — cache-only dashboard query.
  • internal/storage/queries_test.go или новый focused test — source priority, empty cache, current/previous date и отсутствие raw fallback.
  • cmd/server/main.go — process-level sequential startup backfill coordinator вместо concurrent per-tenant goroutines.
  • cmd/server/main_test.go или focused coordinator test — ordering, one-at-a-time execution и non-blocking startup.
  • apps/web/src/features/dashboard/loader.ts — remove the unused optional dashboard request from the interactive start path.

Implementation steps

  1. Write regression tests that expose the current raw-query dependency and preserve card/source semantics on a representative multi-source fixture.
  2. Introduce one atomically persisted cache-only dashboard snapshot while preserving source-selection semantics and the meaning of existing response fields.
  3. Remove the unused optional dashboard fetch; keep the existing server-owned primary briefing freshness UI.
  4. Extract startup broad refresh scheduling into a process coordinator that queues active tenants sequentially after HTTP readiness. Do not change targeted post-ingest rebuilds.
  5. Persist hourly AVG sample counts, retain verified source units in the snapshot, execute focused tests, contract checks and web checks. Reproduce restart against a disposable multi-tenant database before production.
  6. Deploy through the immutable-pair and tenant-schema gate, then verify server timings, user dashboard and a fresh authenticated browser route.

Это намеренно не массовая параллелизация: один этап меняет один тип риска, а следующий получает проверяемый артефакт вместо предположений. Model allocation не меняет approval gate и не даёт права на production mutation.

Validation and QA

  • go test ./internal/storage ./internal/ui ./cmd/server -count=1 plus the narrow new tests.
  • make contract-generate && make contract-check and make web-check.
  • Use a disposable PostgreSQL multi-tenant fixture to prove one broad startup refresh at a time and that HTTP readiness is available before queue work begins.
  • Measure /api/dashboard and /api/health-briefing before/during/after startup refresh; confirm dashboard stays within the agreed budget and no request performs raw fallback.
  • Manual browser QA: fresh dashboard load, a post-ingest updating badge, fallback with a retained prior snapshot, empty-install unavailable state, RU/EN/SR, then a sleep/detail route.

Риски и rollback

  • Неправильная batch SQL source selection может изменить displayed sums. Fixture tests compare every card with the current semantics before cutover.
  • Cache-only can surface a briefly stale snapshot after an ingest failure. The explicit freshness state must make this visible and background rebuild must retain retry/error reporting.
  • A queue must not serialize tenant provisioning, request serving or target-date ingest rebuilds; it applies only to broad startup refresh.
  • Rollback: deploy the previous immutable image pair. No data migration is proposed; additive contract fields are ignored by older clients.

Implementation record

  • Sol review found six correctness blockers in the first local draft: partial snapshots, unweighted AVG values, unsafe unit labels, a changed last_updated contract, a 128-tenant startup deadlock, and a DB regression test absent from routine CI.
  • Remediation stores one durable dashboard snapshot after a complete successful cache generation, retains the prior row on failure, and exposes additive complete/updating/unavailable state. last_updated remains the latest receipt timestamp; unit labels are retained only when raw inputs agree.
  • Hourly AVG writers now persist sample_count and snapshot SQL uses weighted averages. This is an additive schema-contract v8 change and therefore requires the existing tenant-schema deployment gate.
  • Startup refresh uses an unbounded pending list plus one worker after HTTP readiness; the routine DB lane now explicitly runs the dashboard snapshot regression.
  • PR review remediation: dashboard publication now creates a fresh context after a long backfill; a missing snapshot defers the durable evening delivery before it can consume its at-most-once reservation, retries only until the tenant-local day boundary, and then stops; and last_updated is read live from the receipt timestamp instead of being frozen in the snapshot payload.
  • Validation after the review remediation: notify, storage, UI, and server Go tests pass; the focused DB snapshot regression passes with HEALTH_DB_TESTS=1, including a receipt accepted after snapshot publication; API contract check and the complete web type/lint/test/build pipeline pass. No commit, push, deployment, or production mutation has occurred.
