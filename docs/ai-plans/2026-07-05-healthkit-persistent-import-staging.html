Implementation Plan: Persistent Staging for Apple Health XML Imports

Created 2026-07-05 for a separate PR after the staged XML import merge.

Approval required before implementation

Task Summary

Finish the remaining P2 follow-up for Apple Health XML imports: replace the current temporary-table staging transaction with persistent staging tables keyed by import_run_id. The goal is to let very large HealthKit exports parse and stage data for hours without holding one long PostgreSQL transaction open.

Inspected Context

  • internal/storage/import_run.go currently owns import metadata, temporary staging, promotion, commit, and abort behavior.
  • internal/storage/import_schema.go currently defines import_runs and import_run_coverage.
  • internal/storage/indexes.go creates import tables during startup via EnsureIndexes.
  • internal/ui/import_handler.go and cmd/import/main.go both use BeginAppleHealthXMLImport, AddPoints, AddWorkouts, Commit, and Abort.

Current Behavior

What is already durable

BeginAppleHealthXMLImport creates import_runs and a synthetic health_records row before parsing. Failed imports can therefore be marked in durable metadata.

What is still transactional

The same method then opens s.pool.Begin(ctx) and creates temporary ah_import_points / ah_import_workouts tables with ON COMMIT DROP. Parser callbacks CopyFrom into those temp tables.

Why this is risky

The transaction spans the full XML parse plus final promotion. For a multi-hour import, that can retain database resources, fail late after substantial work, and make operational recovery worse than necessary.

Desired Behavior

  • Use persistent staging tables, likely import_stage_points and import_stage_workouts, with every row keyed by import_run_id.
  • Keep parser callbacks streaming-friendly: AddPoints and AddWorkouts should still batch via CopyFrom, but each call should complete independently without one long-held transaction.
  • Open a short transaction only in Commit to promote coverage, delete stale covered rows, upsert current points and workouts, mark the run committed, and clean up staging rows.
  • Abort should persist failure counters/error text, mark the run failed, and delete that run's staging rows so abandoned data does not grow by default.
  • Preserve the behavior from the previous PR: snapshot_at freshness protection, live-data precedence for newer rows, deterministic duplicate tie-breaking via staged_seq, workout import, and coverage audit rows.

Assumptions and Unknowns

  • Default behavior should prefer cleanup over retaining failed staging rows for debugging. Because current failed imports only persist status and error, this PR must explicitly persist parsed/staged counters on the failure path before deleting stage rows.
  • Persistent staging increases WAL writes versus temp tables. That is acceptable for this PR because avoiding a multi-hour transaction is the larger operational win.
  • Persistent staging makes concurrent imports stage-isolated, not globally concurrency-safe. Target tables are shared, workout promotion is currently commit-order dependent, and CLI imports can run independently of the UI.
  • Cleanup must not delete a live import. Stale cleanup should touch running imports only when they are clearly abandoned by age and/or protected by an import lease/advisory lock.

Proposed Implementation Steps

  1. Add persistent table DDL for import_stage_points and import_stage_workouts. Include import_run_id, staged_seq BIGSERIAL, and the current staging columns.
  2. Add explicit indexes for the actual query shapes: points by (import_run_id, metric_name, date, source, staged_seq DESC), points coverage by (import_run_id, metric_name, source, local_date), workouts by (import_run_id, external_id, staged_seq DESC), workouts synthetic stale-delete keys by (import_run_id, name, start_time, end_time), plus simple import_run_id cleanup paths if the composite indexes do not cover deletes well enough.
  3. Wire table creation into both startup DDL and EnsureAllTables alongside import_runs and import_run_coverage.
  4. Change ImportSession so it no longer stores a long-lived pgx.Tx. BeginAppleHealthXMLImport should create durable metadata and return immediately after any stale-stage cleanup needed for the run.
  5. Change AddPoints and AddWorkouts to CopyFrom into persistent stage tables with import_run_id included in each row.
  6. Change promotion queries to read only rows for s.runID. Every nested stage reference, including NOT EXISTS stale-point checks and workout exact-row checks, must also filter by import_run_id.
  7. Keep DISTINCT ON ordering by staged_seq DESC so later staged duplicates win deterministically inside one run.
  8. Make Commit open a transaction, promote coverage/points/workouts, update import_runs, delete staging rows for the run, and then commit.
  9. Define commit-failure behavior explicitly: if promotion fails before commit, roll back target-table changes, mark the run failed, persist failure counters, and then delete stage rows only after the failure state is durable. Treat ambiguous tx.Commit errors conservatively: mark the run failed only when the transaction state is known rolled back; otherwise leave staging rows for manual inspection.
  10. Make Abort persist failure counters, delete staging rows for the run, and mark the import failed. Keep the caller API stable unless tests show returning cleanup errors is necessary.
  11. Add a conservative cleanup helper for stale stage rows: delete rows for already failed imports, and for running imports only when started_at is older than a high threshold such as 24 hours. Run it at startup and before a new import begins, unless implementation shows an advisory-lock/lease approach is cleaner.
  12. Run focused storage, parser, CLI, and UI tests. Update docs and this plan after implementation.

Data, API, Deployment, and UX Impact

  • Database: adds persistent staging tables and indexes. No destructive migration is planned.
  • API: no external API contract change is expected for the web import endpoint or CLI flags.
  • UX: import progress should behave the same, but long imports should be operationally safer. Leaving the import page still should not determine whether server-side staging continues.
  • Deployment: startup DDL must be safe on existing production data. New staging tables start empty, so initial index creation should be cheap.
  • Performance: parser staging may write more WAL than temp tables. Final commit should be shorter because parsing no longer happens inside the transaction, but promotion can still be a large transaction and must be indexed and measured.

  • Verify import_stage_points and import_stage_workouts have no rows for the committed run after commit.
  • Trigger a controlled parse/stage failure in a test run and verify the run is marked failed and stage rows are cleaned.
  • Use the Admin import page on a small fixture and confirm progress, completion counters, and cache invalidation still work.
  • After deploy, check startup logs for DDL errors and smoke-test authenticated dashboard redirects as usual.

Risks and Edge Cases

  • Crash during parse: persistent stage rows can remain if the process dies before Abort. Mitigate with cleanup for stale failed imports and only clearly abandoned running imports.
  • Commit failure after staging: stage rows should remain or be cleaned according to a documented policy. The transaction must not mark committed unless promotion and cleanup succeed, and ambiguous commit errors must not destroy the only forensic data.
  • Large stage tables: indexes must stay scoped to promotion and cleanup access patterns, not over-index every column.
  • Duplicate ordering: changing from temp BIGSERIAL to persistent BIGSERIAL must preserve deterministic "last staged row wins" behavior inside each run.
  • Concurrent imports: all promotion, delete, and cleanup queries must filter by import_run_id so one import cannot consume another import's staged rows. Shared target-table behavior is still commit-order dependent unless this PR adds serialization.

Rollback Plan

If the PR causes import trouble after deployment, revert the code to the previous temp-table staging implementation. The new persistent staging tables are additive and can remain unused. If needed, remove leftover stage rows with targeted deletes by import_run_id after confirming no import is running.

Open Questions

  • Should this PR add explicit import serialization with an advisory lock to avoid commit-order surprises between CLI and UI imports, or is documented stage isolation enough for this follow-up?
  • What stale-running threshold is appropriate for cleanup after crashes? Proposed default: 24 hours.
  • Should ambiguous commit errors preserve staging rows for manual inspection even if normal abort/promotion failures clean them?

Implementation Update

Implemented on branch codex/persistent-import-staging. The importer now writes parser batches to persistent import_stage_points and import_stage_workouts rows keyed by import_run_id. The long parse transaction is removed; Commit opens a transaction only for coverage promotion, stale-row cleanup, point/workout upserts, import counter persistence, and stage-row cleanup.

  • Added stage-table DDL to both EnsureAllTables and startup EnsureIndexes.
  • Added promotion indexes for point dedup, point coverage, workout dedup, and synthetic workout cleanup query shapes.
  • Added conservative cleanup for committed/failed runs and running runs older than 24 hours; recent running imports are preserved because CLI imports can run outside the UI process.
  • Abort now persists failure counters before deleting that run's staging rows.
  • Known limitation: concurrent imports are stage-isolated, but shared target-table workout behavior remains commit-order dependent; this PR documents and tests stage isolation rather than introducing advisory-lock serialization.
