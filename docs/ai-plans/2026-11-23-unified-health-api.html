Единый API Health

Локальная реализация согласована и проверена на серверном и мобильном клиентах. База — релиз PR #293 и текущие исходники Health Sync. Цель — для каждой операции определить один контракт, одну реализацию правил и проверяемое поведение для всех потребителей.

Исходное состояние

В contracts/openapi.json описаны 19 операций на 17 путях. Клиенты уже вызывают /api/metrics, /api/metrics/latest и /api/sections, которых в спецификации нет. Старый веб и React получают дневные шаги через отдельный JSON-фрагмент. iOS запрашивает точки и диапазон параллельно, но ждёт оба ответа до отрисовки. Полный перечень расхождений требует сверки регистрации маршрутов с реальными вызовами.

Охват

  • Все операции пользовательского и административного HTTP API, включая чтение и запись. Включить Today, разделы, метрики, сон, Readiness, Energy, исследования, историю и отчёты, настройки, импорт, управление профилями и обслуживание.
  • Целевые пользовательские клиенты — React и iOS. Учесть также фоновые задания и внешние интеграции. Для приёма данных, вебхуков, MCP и служебных проверок зафиксировать отдельные протокольные контракты, способы аутентификации и проверки совместимости. Общую доменную операцию вызывать через одну реализацию. Сохранить доставку, идемпотентность, повтор и потоковый ввод там, где они предусмотрены.
  • Для оставшихся Go-страниц отметить используемые маршруты как зависимости совместимости. При изменении такого маршрута проверить существующий экран. По мере переноса экранов на React новые компоненты используют канонический API. Сохранить снимки уже отправленных отчётов, права администратора и изоляцию профилей.

Порядок работ

  1. Составить воспроизводимый реестр из регистрации Go-маршрутов, OpenAPI, внешних транспортов и мест вызова. Для каждой операции записать метод, путь, назначение, потребителей, права, формат, источник данных, версию и статус миграции. Отдельно проверить динамические пути, вспомогательные JSON-маршруты, отсутствие подписанного потребителя и контракт без обработчика.
  2. По реестру назначить каноническую операцию и описать входы, значения по умолчанию, историю, типы, ошибки, NULL, пагинацию и права. Расширять существующий OpenAPI совместимо. Старые URL и форматы выпущенных клиентов направлять в общую реализацию через адаптеры. Сохранить передачу контекста профиля от аутентифицированного сервера.
  3. Подключить React и iOS по семействам операций, которые использует каждый клиент. Для графиков различать сумму, min/max, почасовые и дневные значения, выбор источника, «Всё» и заданные даты. Управлять выбором готовой публикации dbt и резервным расчётом на сервере для обоих клиентов. В iOS и React показывать точки до завершения необязательных запросов. Не позволять позднему ответу предыдущего диапазона менять экран.
  4. Начать с internal/api, internal/ui (серверные обработчики API), internal/storage, internal/handler, internal/mcpserver, cmd/server, apps/web/src/api и health-sync/ServerClient.swift. Уточнить полный список по реестру. Изменения выполнять в изолированных ветках, сохраняя текущие незакоммиченные файлы.

Приёмка и откат

Автоматическая сверка должна обнаруживать новую незарегистрированную операцию и обход общей реализации в React или iOS. В реестре отличать временные зависимости Go-страниц от целевых вызовов. Проверить текущих и ранее выпущенных клиентов, права и отказ в доступе, пустой профиль, пропуски, позднюю синхронизацию, устаревшую публикацию и сохранённую историю. Для записей проверить побочные эффекты и повтор на изолированных фикстурах с отключённой внешней доставкой. Сверять типы, значения и наблюдаемые эффекты, а не только HTTP 200.

Прогнать make contract-check, тесты Go с PostgreSQL, make web-check и целевые тесты iOS. Замерить время API и время до отображения данных на клиентах. На закрытых копиях пяти профилей сверять результаты чтения, сохраняя только агрегированные итоги в локальном отчёте. Публикация нового графа dbt в production — отдельное изменение инфраструктуры.

Риск — потерять семантику старого клиента или повторно выполнить запись при переключении. Переводить по операциям, удерживать совместимые адаптеры и возможность вернуть читателя на предыдущий источник. Удаление старых маршрутов согласовывать по фактическому использованию. Перед релизом представить покрытие реестра, оставшиеся исключения, замеры и порядок отката.

Локальная реализация и проверка, 24 ноября

Серверная ветка основана на 2771974, мобильная на 4ce39fe. Один OpenAPI описывает 58 операций на 49 путях, включая административные. Инвентарь связывает пути с регистрацией, правами и клиентами. В нём также 13 фрагментов совместимости, 18 записей внешних протоколов и 18 инструментов MCP. Проверка со вторым репозиторием сверяет исходники обоих клиентов. Статическая проверка находит буквальные пути. Смысл новой операции по-прежнему требует ревью.

React и iOS запрашивают значения графика через /api/metrics/data с версией контракта 2. Сервер выбирает опубликованный источник и резервный расчёт. Дневные шаги за месяц и за весь период используют одну функцию. Старый Go-фрагмент вызывает её же. Разрез по устройствам сохраняет измерения каждого источника. Полная выдача дневных шагов сохраняет наблюдаемые экстремумы и берёт итог из той же транзакции. Клиенты могут показать график, пока поступают дополнительные данные.

Результаты

  • На снимках пяти профилей сравнили массивы дат и значений обработчика с ранее проверенными daily_scores. Совпали 7 875 значений за всю историю и 136 значений в пяти окнах по 30 дней. Пустые дни оставались пустыми. На локальном PostgreSQL 16 обработчик месячного запроса занял 1,8–3,2 мс, всей истории 3,2–8,8 мс в первом прогоне. Это отдельные измерения без сетевого пути от телефона.
  • В симуляторе iPhone 17 Pro с iOS 26.5 три открытия месячного графика заняли 1,299, 1,241 и 1,215 секунды до появления числа при искусственной задержке границ истории на восемь секунд. Границы отобразились после ответа.
  • В независимой сверке готовых дневных и почасовых публикаций dbt со старым кэшем шаги совпали. У одного профиля в публикации на 862 даты больше. Различались 1 446 дневных значений калорий, 18 HRV и 11 частоты дыхания. На уровне часов выявлены также различия активности, дистанции и пропуски старых значений. Этот аудит сравнивает два сохранённых результата и сам по себе не определяет верную версию. Смена HTTP API не переводит остальные графики на новый источник.
  • Проверки включали make contract-check с обоими исходными деревьями, штатные Go/DB-проверки с PostgreSQL, make web-check, семь браузерных тестов, 166 модульных тестов и проверки экранов iOS. Все 144 теста React прошли. Финальная проверка включала go vet по изменённым пакетам, отмену запроса, отказ резервного чтения и наблюдение с часовым смещением в последнюю секунду суток. Тесты изменений и повторных операций используют синтетические данные. Измерения сервера и симулятора не включают сетевую задержку в production.

Два прерванных запуска по ранее настроенному подключению создали две синтетические схемы на внешнем тестовом стенде. Обе удалены, отсутствие проверено. Штатные проверки прошли в Docker с тестовыми ролями. Проверки восстановления, требующие Unix-сокет PostgreSQL, выполнены внутри контейнера.

Выпуск и возврат

Сначала выпустить обратно совместимый сервер и React, затем клиент iOS. При возврате сначала восстановить предыдущие клиенты. Сохранить совместимые URL, исходную версию контракта и настройки доступа при откате. Отдельное решение требуется для публикации PR, серверного релиза и выпуска iOS. Перенос оставшихся Go-страниц на React зарегистрирован в Todoist.
