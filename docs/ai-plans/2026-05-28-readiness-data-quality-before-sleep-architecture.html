90-Day Follow-Up: Tolerance Hypothesis

The May-only check was not enough; the tenant already has about 90 days of history. A second read-only SQL simulation was run across the latest 90-day secondary-tenant window. It compared the current strict 4.0h Recovery cutoff with a tiny numerical tolerance at 3.95h, staged-sum substitution, and the evidence-only 2-of-3 target.

Scenario Rows Eligible MAE vs existing EWMA45 Decision
strict_3of3_base 87 35 0.0255 current baseline
strict_3of3_tolerance_3_95h 87 38 0.0250 small positive signal
strict_3of3_staged_sub 87 35 0.0255 no value
candidate_2of3_base 87 77 0.0276 coverage rescue, worse MAE
candidate_2of3_tolerance_3_95h 87 77 0.0273 still worse than strict
candidate_2of3_staged_sub 87 80 0.0275 still worse than strict

The 3.95h tolerance rescues exactly three strict rolling rows in the 90-day window, all caused by one borderline source-rounded night just below 4h. This is not broad model work; it is numerical stability around a hard cutoff. The result is small but clean enough to justify a minimal tolerance PR if approved.

The same 90-day simulation on the primary health tenant is a no-op: every scenario has 87/87 eligible rows and 0.0245 MAE. There are zero sleep_total < 4h days, zero borderline [3.95h,4.0h) days, and zero rescued strict rows. This lowers the blast-radius risk for the tolerance fix.

Desired Behavior

  • The operator can inspect tenant-specific admin monitoring for the primary tenant, a secondary tenant, and explicit schema=all without profile leakage.
  • Secondary-tenant sparse Recovery labels are treated as a data-quality/wear-discipline problem before any model or feature promotion.
  • Sleep architecture remains evidence-only unless it beats the predeclared floor. The current 2026-05-28 probe says it does not.
  • The next decision is framed as one of: keep strict labels, gather more data, add better capture diagnostics, or design a separate fallback target. It is not framed as "ship architecture features".

Recommended Approach

Approach A: Minimal threshold tolerance PR (recommended after 90-day check)

Keep §6.5 sleep architecture blocked, keep 2-of-3 evidence-only, and open a tiny PR that treats sleep totals in the narrow band [3.95h, 4.0h) as eligible for Recovery efficiency. This is justified as threshold tolerance, not as a physiology/model change. The PR must include tests proving a synthetic source-rounded 3.99h night becomes eligible while true short sleeps such as 3.60h and 3.94h remain ineligible.

Approach B: Evidence gate only

Stop after recording the DB evidence and make no code change. This is still valid, because the measured improvement is small and comes from one borderline night. It leaves a known brittle threshold in place.

Approach C: Implement a product fallback now

Promote rolling_3d_candidate_2of3 or low-confidence handling into product paths. This improves coverage but risks hiding real short sleep and currently has weak MAE evidence. Not recommended.

Approach D: Continue architecture feature engineering

Add or tune more architecture features. This is fishing-prone after a clear fail result. Only revisit after capture quality is cleaner or after a new physiological hypothesis is predeclared with a different stop rule.
