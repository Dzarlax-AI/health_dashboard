Implementation Plan: Persistent Review Tenant

Approved and implemented

Task Summary

Create a persistent, non-personal tenant for UI review, screenshots, demos, and safe dashboard regression checks. The tenant should behave like a normal multi-user account, but contain only synthetic health data.

This is separate from the throwaway integration schema added in the startup DDL PR. The throwaway schema proves DDL safety; the persistent review tenant gives us stable browser-visible data for future product work.

Current System Facts

  • Users live in health_registry.users; each user maps to an isolated tenant schema.
  • registry.CreateUser generates an API key and derives schema names as health_<username> unless explicitly supplied.
  • tenants.Manager.CreateUserSchema creates the schema and calls EnsureAllTables, EnsureIndexes, EnsureAIBriefingsTable, EnsureAIBriefingBlocksTable, EnsureEnergySnapshotsTable, and EnsureReadinessRedesignTables.
  • Admin UI already has POST /api/admin/users, but scripted provisioning is better for repeatable screenshots and seed-data refreshes.
  • Readiness redesign writers can be run over date ranges after daily seed data exists.

Desired Behavior

  • A stable review user, proposed username review, schema health_review.
  • No real personal data, no copied raw payloads, no Telegram notifications, no Gemini generation requirement.
  • Deterministic seed data for at least 90 days ending near the current date, so dashboard cards, charts, readiness history, EnergyBank, freshness/confidence states, and admin previews have useful content.
  • Rolling seed window: every seed refresh should anchor on tenant-local today so the review tenant always has data for today, the previous month, and the full baseline window.
  • Seeder should be idempotent: safe to rerun to refresh the review tenant.
  • Seeder should be opt-in and explicit, not part of normal server startup.

Proposed Scope

Provisioning

Add a small CLI command that ensures the review user and schema exist through the same registry/tenant APIs used by production account creation.

Seed Data

Insert deterministic synthetic daily_scores rows plus enough metric_points / hourly_metrics for dashboard and chart surfaces that depend on raw-ish metrics.

Derived Layers

Run relevant cache/readiness writers so target_snapshots, feature_snapshots, and naive_baselines exist for review dates.

Safety

Keep the command behind an explicit name and require DATABASE_URL. Never infer or mutate real tenants.

Likely File Changes

  • cmd/seed_review_tenant/main.go - new opt-in CLI for provisioning and deterministic seed refresh.
  • internal/storage - possibly a tiny helper only if direct SQL in the CLI becomes too repetitive; prefer keeping seed-only logic in the command.
  • README.md or a small docs section - document how to run the seed command and how to log in/use the tenant for screenshots.
  • docs/ai-plans/2026-05-28-persistent-review-tenant.html - update with implementation result and verification.

Seed Data Shape

  • 90 to 120 days of synthetic data ending at tenant-local today, regenerated as a moving window rather than fixed calendar dates.
  • Default refresh should keep at least today + the previous 30 days fully populated, with older synthetic history retained or regenerated to preserve mature baselines.
  • Sleep: normal nights, short nights, fragmented nights, and a few missing/stale windows for confidence UI.
  • Recovery: HRV/RHR variation with readable good/poor recovery periods.
  • Activity: steps, calories, exercise minutes, and some low/high days.
  • Vitals: SpO2, respiratory rate, VO2 where useful for cards and anomaly surfaces.
  • EnergyBank: enough inputs or snapshots to render trend and capacity states.
  • Readiness redesign: run Phase 0 writers after seeding so review surfaces show target/features/baselines.

Implementation Steps

  1. Inspect exact dashboard/API read paths that must look populated for screenshot review.
  2. Create cmd/seed_review_tenant with flags such as --username review, --schema health_review, --days 120, --anchor today, --reset-window, and --dry-run.
  3. Provision the registry user if absent, using registry.CreateUser; create schema through the existing schema creation path.
  4. Disable notification settings for the review schema explicitly by leaving Telegram settings blank and documenting that this tenant must not receive reports.
  5. Seed deterministic daily and metric rows in a controlled rolling date range. Use clear synthetic source labels such as ReviewSeed.
  6. Run cache/readiness derivation for the seeded range.
  7. Print the generated API key and a one-time local password only to the operator console; do not commit credentials.
  8. Verify via DB queries and browser/API checks.

Test Plan

  • go test ./cmd/seed_review_tenant ./internal/storage ./internal/registry ./internal/tenants -count=1 if command-level tests are practical.
  • go test ./... before PR.
  • Live dry-run against ~/.health-db to confirm the command reports intended changes without writing.
  • Live apply against health_review, then query row counts in health_registry.users, daily_scores, metric_points, target_snapshots, feature_snapshots, and naive_baselines.
  • Run the seeder with a shifted anchor date in a temporary schema and verify the populated window moves forward while preserving today's rows and the previous month.
  • Browser smoke: log in as review user and capture dashboard/admin screenshots at desktop and mobile widths.

Risks and Edge Cases

  • Do not seed from real health or health_mariia data. Synthetic-only data is a hard requirement.
  • Do not make the review user admin unless there is a specific screenshot need for admin-only pages. Safer default is non-admin.
  • Do not enable Telegram or AI generation by default; screenshots should not trigger real notifications or model calls.
  • Seeded synthetic data can drift from real product behavior if it bypasses too many normal write paths. Prefer normal storage writers where feasible.
  • Rolling refresh must avoid unbounded growth: old synthetic rows should either be replaced inside the configured window or clearly retained as archived synthetic history.
  • Reset mode must only allow the configured review schema, never arbitrary schema names without validation.

Rollback Plan

Delete the review user from health_registry.users and drop only the health_review schema. The command should print the exact rollback SQL after provisioning. No production tenant data is touched.

Open Questions

  • Should the review tenant be non-admin only, or do we also need an admin-review account for admin screenshots?
  • Should screenshots use local/dev only, or is a production-hosted review login desirable?
  • Should seed data include intentionally stale/missing data windows for the upcoming confidence UI work?
  • Should the rolling refresh run manually before screenshot sessions, or should we add a scheduled automation after the first version is proven?

Approval Gate

Approved in-session on 2026-05-28. Implementation results and verification are recorded below.

Implementation Result

  • Added cmd/seed_review_tenant, an explicit opt-in CLI for provisioning and refreshing review / health_review.
  • The command refuses non-review username/schema combinations, supports --dry-run, --days, --anchor today, --tz, and --reset-window.
  • Seed data is deterministic and synthetic-only: 120 tenant-local days by default, sourced as ReviewSeed Apple Watch and ReviewSeed iPhone.
  • Refresh clears prior ReviewSeed points, generated raw seed records, daily rows, readiness redesign rows, and backfilled EnergyBank snapshots in the rolling window before reseeding.
  • After insertion, the command rebuilds caches, recomputes readiness, runs readiness redesign Phase 0 writers, and backfills EnergyBank EOD snapshots.
  • Added README maintenance documentation for dry-run and apply usage.

Known Limitations

  • Browser screenshot smoke was not run in this implementation pass; the tenant is prepared in the database for the next UI review session.
  • The review password is only used when creating the user. If the existing review user already has a different password, the seeder does not rotate it.
  • Readiness redesign backfill expands the seed range with lookback dates, so derived rows start earlier than daily_scores. This is expected and keeps target/baseline calculations mature.
