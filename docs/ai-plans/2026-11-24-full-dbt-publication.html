Полный перенос расчётов Health на dbt

Рабочий воркер выбирает +daily_metrics. Архивная проверка локального полного графа охватила 453 активных идентификатора. Некоторые модели возвращают результат, ранее записанный Go. Такой результат сам по себе не доказывает перенос формулы.

Критерий завершения

Для каждого идентификатора каталог указывает тип значения, источник, версию и владельца расчёта. Каждая вычисляемая метрика получается исполняемой моделью dbt. Наблюдения сохраняют исходную детализацию. Отправленные отчёты воспроизводят сохранённое объяснение. Один API читает согласованную публикацию профиля.

Локальная реализация

  1. На базе текущей ветки общего API сопоставить каталог, исполняемые SQL-модели, Go-писателей и потребителей, включая Today, историю, исследования, MCP и отчёты. Сделать проверку покрытия обязательной для каталога.
  2. Для оставшихся формул, включая Readiness и Energy, фиксировать входы и время принятия решения. Перенести вычисления в модели, проверить границы суток и зависимость Energy от предыдущего состояния. Отмечать исторические решения с утраченными входами как невоспроизводимые.
  3. Расширить существующий tenant_aggregate_worker.py. Для каждой семьи определить окно зависимостей и правила пересчёта после поздней синхронизации или отзыва. Публиковать согласованный результат после успешного расчёта, сохранять предыдущую публикацию при сбое и новые поколения очереди при конкурирующей записи.
  4. Подключить читателей через общий серверный слой. Сохранить календарь завершённых дней, единицы, источники, сведения о пропусках и исторические версии. При откате переключить профиль на прежний читатель.

Приёмка

Синтетические проверки охватывают непустое значение каждой активной метрики, пустой профиль, повтор, сбой, конкуренцию, изоляцию и откат. На временных копиях пяти профилей сравнить ключи, пропуски, значения и происхождение, проверить результаты против исходных данных при разногласии. Сопоставить полный и инкрементальный пересчёт, измерить задержку обычной синхронизации и открытия экранов. Не включать область с необъяснённым расхождением. Сохранить только сводные результаты.

Согласование

Предлагается одно согласование локальной реализации всего объёма. Окна пересчёта и допустимое численное отклонение определить по формулам и закрепить тестами. Переключение производственных профилей и выпуск согласовать по итогам репетиции.

Локальная реализация

План согласован. Подготовлены контракт v19 и отдельная публикация результатов по версии формулы и хешу входов. Интеграционные проверки Readiness и Energy на PostgreSQL прошли. Контрольным запросом только на чтение проверены пять профилей. Во всех пяти запись входов решений отключена, таблица журнала пуста. Историческая сверка этих решений по исходным входам пока недоступна. Переключение профилей и выпуск требуют отдельного решения после приёмки.

Проверка источников и архивов

Для 456 идентификаторов добавлен воспроизводимый реестр производителей. На временных копиях пяти профилей проверено 232 152 почасовых значения и девять дневных столбцов на 8 789 профиль-днях. Для 7 879 дневных значений шагов результат совпал с независимым расчётом по физическим часам. Подробности и пределы проверки приведены в experiments/dbt_metrics/semantic/fleet_catalog_parity.md в рабочей ветке. Временные копии удалены.

Синтетический граф прошёл 40 тестов dbt. Для каждого из 123 исходных наблюдений проверены измеренный ноль, единица и источник. Снимки из архива и неповторимые решения отмечаются отдельно от расчётов по исходным данным.

Приёмка нативного каталога

Установка под ролью профиля даёт 453 идентификатора значений и три определения без значения. На локальном PostgreSQL проверены все 456, правила доступа, повтор установки и откат при сбое. Для 51 признака сравнили независимый расчёт dbt с результатом четырёх писателей. Сохранённая историческая запись доступна отдельно. Разные способы получения числа перечислены в semantic/catalog_verification.md.

В чистом синтетическом графе на двух изолированных профилях проверены 79 моделей, 40 тестов dbt, 20 200 типизированных значений на профиль и пользовательские пути. Обычный Go-прогон и проверка контракта клиентского API прошли. Отзыв измерения проверен отдельно: историческое тело отправленного отчёта сохранено.

Фоновый воркер материализует почасовые и дневные агрегаты и поддерживаемые решения. Часть каталога вычисляется представлениями при чтении. Полное покрытие реестра и переключение каждого потребителя учитываются отдельно.

Существующий GET /api/metrics/data принимает view=catalog и возвращает типизированную страницу с ограничением по размеру и курсором, привязанным к профилю и фильтрам. Проверены аутентифицированный HTTP-запрос, прежний формат графика и генерация клиента. Make contract-check, make web-check и полный Go-прогон прошли. Штатная установка воркером создаёт общий и три типизированных представления одной транзакцией.

Финальная сверка пяти архивов

На каждом профиле проверены все 456 идентификаторов. У 251 идентификатора нашлось значение хотя бы на одном профиле. Все 251 прошли независимую сверку. Среди 14 308 507 проверенных строк отсутствовали расхождения, дубли и потерянные ключи. У 13 идентификаторов нашлись только NULL, у 189 не было строк, ещё три предусматривают только статус. На копиях заново рассчитаны 20 решений Readiness, Energy и Today, все совпали. Это воспроизведение по доступным на момент проверки данным. Исходные журналы решений всех пяти профилей были пусты.
