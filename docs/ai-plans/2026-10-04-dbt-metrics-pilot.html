Пилот dbt для исторических агрегатов Health

4 октября 2026 · Ревизия 2 · Complete · Локальный пилот проверен

1. Цель и границы

Проверить, упрощает ли dbt описание, тестирование и частичный пересчёт SQL-агрегатов при сохранении текущей семантики Go. Получить исполняемый локальный эксперимент и отчёт сравнения, а не переключение продукта.

Включены: чтение синтетических metric_points в изолированном PostgreSQL, часовые агрегаты и дневные колонки hrv_avg, rhr_avg, sleep_total, sleep_deep, sleep_rem, sleep_core, sleep_awake, sleep_unspecified, steps, calories, exercise_min, spo2_avg, vo2_avg, resp_avg. Отдельные модели и макросы dbt, полная сборка, пересчёт явно заданных дат, проверки повторных обновлений, сравнение с существующим Go и измерение длительности.

Исключены: readiness и остальные формулы, Energy, wake detection, HR baseline, sustained HR load, Today, ingestion, AI, Telegram, production, fleet migration, изменение tenant schema contract. Production-данные не копируются и не читаются. Коммиты, push, PR и deployment требуют отдельной явной команды пользователя.

2. Что подтверждено в репозитории

Рабочая директория — health_processing; текущая ветка codex/dbt-metrics-pilot, HEAD d5cc509493a3b1c7b1c271b34bb5b3c9154169cd. Релиз #262 завершён до пилота. Предыдущая рабочая директория сохранена в stash; перенесён только этот план.

В internal/storage/aggregates.go upsertHourlyAvgForDate использует AVG положительных quality=ok точек; SUM-путь сначала берёт MAX внутри минуты. Дневные AVG — среднее часовых средних по источнику, затем среднее между источниками, а не среднее всех исходных точек.

sleepDedupClause предпочитает валидную полуночную сводку и исключает фрагменты, если она есть. Это противоположно краткому описанию Sleep Dedup в AGENTS.md; источником поведения пилота служит исполняемый SQL. Пилот не исправляет эту разницу в документации.

upsertDailyForDate выбирает один источник сна по sleep_total: при MIN>1 часа и MAX>MIN×1.4 выбирает минимальный; иначе Watch → RingConn → максимальный. Равенства разрешаются source ASC. Gate допускает один источник, пять традиционных стадий или total+unspecified. При неполном обновлении сохраняется старый блок; при переходе на coarse-only старые стадии очищаются. Остальные отсутствующие дневные значения сохраняются через COALESCE.

Docker 29.8.1 доступен; PostgreSQL 17.11-alpine и Python 3.12.14 подтверждены. dbt Core 1.12.5 / dbt-postgres 1.11.0 закреплены после проверки PyPI и официальной документации.

3. Контракт эксперимента

  • Отдельный локальный временный PostgreSQL для пилота; исходные синтетические таблицы и Go-эталон принадлежат только этому эксперименту. dbt пишет только в выделенную экспериментальную схему через отдельную роль; исходные таблицы доступны этой роли только на чтение.
  • Запуск по умолчанию создаёт собственное окружение. Не использовать DATABASE_URL, реальные credentials или автоматически обнаруженные production-подключения. Привязка порта только к loopback; тестовые credentials не переиспользуются вне пилота.
  • Go-эталон вызывает существующие непубличные hourly/daily функции из отдельного тестового файла пакета storage. Не копировать реализацию в независимый «эталон» и не вызывать UpsertRecentCache с его дополнительными зависимостями.
  • Часовые модели проверяются по ключу metric_name/hour/source; дневные — по date и указанным колонкам. computed_at исключён. NULL сравнивается отдельно; числа — с документированной абсолютной/относительной погрешностью 1e-9.
  • Существующее выделение дня и часа через SUBSTRING(date,…) сохраняется. Новая нормализация timezone и изменения суммирования не входят в эксперимент.
  • Исторические изменения задаются явным набором affected_dates. Пересчитывать весь выбранный день, включая удаление устаревших часовых строк; не ограничиваться новыми timestamps. Расхождения со stale-row поведением текущего Go регистрировать отдельно, без скрытого исправления продукта.
  • Полная реконструкция и incremental update проверяются отдельно: сохранение предыдущих значений делает часть текущего поведения зависимой от истории обновлений. Не обещать равенство этих режимов там, где его не обеспечивает Go.

5. Выполнение и роли

  1. Ведущий агент фиксирует fixture contract, версию dbt-postgres и доступный локальный runtime; проверяет свежую официальную документацию. Если локальный PostgreSQL запустить невозможно, подготовить код и явно оставить DB-приёмку неподтверждённой.
  2. Ведущий агент создаёт изолированный harness и fixtures; подтверждает Go-результат, роли и ограничения доступа. Это открывает реализацию SQL-моделей.
  3. Один последовательный implementation-subagent: gpt-6-luna, reasoning medium, только experiments/dbt_metrics/. Реализует модели и runner по утверждённому контракту. Возвращает actual diff, команды, результаты и ограничения. Go harness и HTML остаются собственностью ведущего агента. Модель подходит для ограниченного SQL/dbt задания; границы и эталон заранее фиксированы.
  4. Ведущий агент проверяет SQL, фактический diff и интеграцию, разбирает расхождения, запускает совместную приёмку. Не принимать совпадение только потому, что агент сообщил об успешном тесте.
  5. Обновить этот план и записать фактическое решение: оставить исследовательским инструментом, предложить следующий перенос или отказаться. Никакое переключение продукта не происходит автоматически.

Подагенты до утверждения плана не запускаются. Делегирование предусмотрено skill html-implementation-plan; при недоступности executor ведущий выполняет работу сам и отмечает это в результате.

6. Приёмка и измерения

Все проверки ниже выполнены на синтетическом окружении. Реальная production-производительность этим экспериментом не проверялась.

  • dbt compile/build и data tests на изолированных данных; полный прогон сравнения Go/dbt. Уникальность ключей, совпадение чисел/NULL и источника сна. Границы 1h и 1.4×, равные суммы, один источник, coarse-only и неполный picked source.
  • Midnight summary против fragments; несколько точек в минуте; несколько устройств; неравное число samples в часах; qty≤0 и quality≠ok; пустая дата.
  • Повтор без новых данных; поздняя запись в старую дату; изменение существующей точки; quality invalidation; смена staged→coarse; неполное обновление после полного. За пределами affected_dates результат не меняется.
  • Попытка dbt-ролью изменить источник должна завершиться отказом доступа. Runner отклоняет чужую DB и не отправляет уведомления.
  • На детерминированных синтетических наборах измерить полный расчёт и обновление одной старой даты: end-to-end wall time, включая startup dbt, отдельно SQL execution по доступным EXPLAIN ANALYZE/BUFFERS. Указать число строк, версии, объём/окно, cold/warm запуск; повторить минимум три раза. Сравнивать только одинаковую функциональную область Go, а не весь UpsertRecentCache.
  • Нулевые необъяснённые расхождения на fixtures — критерий корректности. Выявленные ограничения Go и различия full/incremental фиксируются отдельно. Синтетический benchmark не доказывает production speedup, contention или окупаемость.

Рабочий entrypoint: Python 3.12 + experiments/dbt_metrics/scripts/run_pilot.py; команда и условия описаны в README. Опт-ин Go DB harness действительно запускался, а не был пропущен.

7. Риски и восстановление

Главные риски: перенос неочевидной update-семантики, дрейф SUM-списка и sleep thresholds, пустые дни и stale rows, неверная оценка времени из-за startup и разницы вычисляемых стадий. Fixtures и отчёт явно разделяют эти случаи; SUM-список сверяется с Go.

Доступ dbt к schema contract активного tenant не предполагается. Ограниченная dbt-роль и собственный временный DB устраняют необходимость production ACL/DDL изменений. Очистка удаляет только созданный runner контейнер/ресурсы по точному ID и маркеру; общие volumes и чужие схемы не удаляются.

Откат — прекратить использование нового экспериментального модуля; изменения production не требуются. Незавершённые пользовательские изменения остаются нетронутыми.

9. Фактический результат

Baseline: 115 точек → 101 часовая строка и 15 дневных записей. Полная сборка: 2 модели + 9 data tests, без ошибок. Совпали ключи, числа и NULL; ручные ожидания проверены отдельно. SUM-список сверяется с реальным Go.

Проверены повтор, поздняя запись, исправление точки, staged→coarse и incomplete-after-complete, а также неизменность остальных дат. Зафиксировано ровно одно ожидаемое stale-hour расхождение Go при quality invalidation: старые 35 шагов против 100 по оставшемуся iPhone источнику. Чистый пересчёт снова даёт равенство. Неполный сон после сохранённого полного даёт 7 часов в incremental и NULL при full reconstruction в обеих реализациях.

Пять неправильных входов отклонены до изменений output, включая partial full refresh. dbt-роль не может писать source. Финальный контейнер и его собственный anonymous volume удалены; ведущий отдельно подтвердил отсутствие обоих по записанным ID.

Масштаб: 17 642 точки, 380 дат, 17 627 часовых строк. Три full и три old-day запуска. Медианы full: Go harness 1.809 с / writers 1.207 с, dbt 2.584 с. Один день: Go harness 0.605 с / writers 10.6 мс, dbt 1.385 с. dbt timers включают новый процесс и исключают data tests; Go harness timer включает экспорт результатов. SQL EXPLAIN отделён от DDL/hooks. Кэши warm/uncontrolled.

Решение: сохранить как offline audit / historical-recalculation prototype. Live-обновления остаются на Go; миграция продукта не выполнялась. Отчёт: experiments/dbt_metrics/report.md, повторный запуск: experiments/dbt_metrics/README.md. Изменения локальные, без commit/push/PR.
