Желаемый результат

  • DB-only runtime работает из immutable GHCR digest; изменения нового dashboard не включены.
  • Frontend и backend пока остаются в текущем приложении. Разделение на отдельные images и общий API для web/mobile вынесено в следующий архитектурный этап.
  • Каждый из 3 tenant-ов подключается собственной DB-ролью; registry и administration используют отдельные least-privilege identities.
  • Никаких runtime-ссылок на mutable :latest во время cutover.
  • Traefik, Authentik и PostgreSQL-контейнеры не перезапускаются.
  • После релиза проходят health/readiness checks, fleet audit, login/API/ingest smoke tests и проверка стабильности контейнера.

Последовательность релиза

  1. Завершить UI PR и получить immutable artifact. Перевести PR #209 из draft, дождаться review/CI, merge в main, дождаться main image workflow. Разрешить опубликованный image в digest и дальше использовать только ghcr.io/dzarlax-ai/health_dashboard@sha256:….
  2. Зафиксировать rollback baseline. Повторно записать current digest, состояние контейнера и логи. Сделать отдельный on-demand pre-cutover PostgreSQL backup и проверить архив. Ежедневный backup уже валиден, но cutover получает собственную контрольную точку.
  3. Подготовить production compose без переключения runtime. Изменить локальный personal_ai_stack compose, проверить docker compose config, показать diff с remote, затем загрузить только non-secret config. Remote .env не перезаписывается копированием.
  4. Безопасно подготовить DB identities и secrets. Сгенерировать независимые пароли fixed roles и 32-byte tenant master secret, создать root-only secret files. Bootstrap DSN хранить отдельно и использовать только для one-shot CLI; он не остаётся в runtime env. На этом этапе TENANT_DB_ISOLATION_ENABLED=false.
  5. Bootstrap и pre-finalize verification. Из exact target image запустить bootstrap-db-identities с checksum-protected manifest. Затем выполнить read-only verify-db-identities --allow-legacy-bridge. Любая неоднозначная роль, ACL drift или ошибка немедленно останавливает релиз.
  6. Inventory, dry-run и canary. Прочитать реальные schema names из registry во время выполнения. Не придумывать имя tenant-а. Выбрать один зарегистрированный non-primary schema как canary, выполнить inventory/dry-run, затем apply и verify только для canary.
  7. Мигрировать остальной fleet, primary последним. После успешного canary применить ownership/credential migration ко всем оставшимся tenant-ам, оставив canonical primary schema health последней. Подтвердить ровно 3 isolation-ready tenant-а.
  8. Контролируемое окно cutover. Остановить только health application. Выполнить finalize-db-identities, удалить legacy bridge, затем authoritative verify-db-identities без allow-legacy flag. Это точка невозврата для простого application rollback.
  9. Schema gate и запуск нового digest. Установить TENANT_DB_ISOLATION_ENABLED=true и запустить deploy-tenant-schema-gate.sh с exact digest, project/service/network/primary schema и root-owned audit env. Gate выполняет audit до downtime, stopped-service migration, повторный audit, запуск target и stability/log checks.
  10. Postflight и доказательство результата. Проверить compose status, restart count, /healthz, /readyz, публичный UI, authenticated dashboard/API, API-key ingest и MCP typed tools. Повторить authoritative fleet audit, проверить tenant count и отсутствие новых ERROR/FATAL/panic. Issue #198 закрывать только после сохранения этих доказательств.

Ключевые команды выполнения

Команды ниже — форма runbook. Реальные digest, canary schema и secret paths подставляются только после read-only discovery.

# Bootstrap fixed DB identities from exact target image
/app/tenant_isolation \
  --mode bootstrap-db-identities \
  --manifest /secure/health-db-identities.json \
  --confirm

# Pre-finalize restricted-identity verification
/app/tenant_isolation --mode verify-db-identities --allow-legacy-bridge

# Canary, then full fleet with primary last
/app/tenant_isolation --mode inventory --all --primary-schema health
/app/tenant_isolation --mode dry-run --all --primary-schema health \
  --image "$TARGET_DIGEST" --manifest /secure/health-isolation.json
/app/tenant_isolation --mode apply --schema "$DISCOVERED_CANARY" \
  --credential-version 1 --image "$TARGET_DIGEST" \
  --manifest /secure/health-canary.json --confirm
/app/tenant_isolation --mode verify --schema "$DISCOVERED_CANARY"
/app/tenant_isolation --mode apply --all --primary-schema health \
  --credential-version 1 --image "$TARGET_DIGEST" \
  --manifest /secure/health-isolation.json --confirm

# With legacy app stopped: irreversible cutover
/app/tenant_isolation --mode finalize-db-identities \
  --manifest /secure/health-db-identities.json --confirm
/app/tenant_isolation --mode verify-db-identities

# Exact production release gate
scripts/deploy-tenant-schema-gate.sh \
  --image "$TARGET_DIGEST" \
  --compose-dir /root/health \
  --compose-file docker-compose.yml \
  --project health \
  --service health-receiver \
  --primary-schema health \
  --audit-env /root/health/secure/audit.env \
  --network infra \
  --readiness-timeout 120

Команды с секретами не запускаются через shell history в открытом виде. Конкретное имя Docker network будет подтверждено через docker inspect/docker network ls; infra выше — параметр, который должен совпасть с фактическим production network до запуска gate.

Риски и стоп-условия

Finalize необратим простым restart-ом После удаления legacy bridge нельзя просто вернуть старый image. Нужен manifest-driven DB rollback.
Credential mismatch Ошибка master secret/version или role password заставляет runtime fail closed. Проверяем каждую restricted identity до cutover.
Shared PostgreSQL budget Tenant pools ограничены; не увеличивать MaxConns и не перезапускать PostgreSQL/Authentik.
Повторные уведомления Перед rollback или повторным запуском проверить delivery state; schedulers не должны повторно отправить ambiguous report.

Немедленный STOP: невалидный backup, CI/image mismatch, неизвестный tenant schema, manifest checksum error, ACL/schema drift, canary verify failure, tenant count не равен registry count, authoritative audit finding или растущий restart count. Такие ошибки не «чинятся на ходу» в production.

Rollback

До finalize

Оставить TENANT_DB_ISOLATION_ENABLED=false, вернуть проверенный compose и текущий immutable digest, при необходимости откатить подготовленные tenant manifests штатной CLI-командой. Legacy app продолжает использовать общий credential; fixed roles могут оставаться подготовленными и неактивными.

После finalize

  1. Оставить приложение остановленным и отключить notification schedulers на время восстановления.
  2. Сначала выполнить rollback-db-identities из сохранённого DB identity manifest.
  3. Затем выполнить tenant fleet rollback из canary/fleet manifests.
  4. Проверить восстановленный legacy bridge и registry access.
  5. Только после этого запустить записанный current digest sha256:46e333… с isolation disabled.
  6. Повторить login/API/ingest/log smoke tests и сохранить evidence.

Schema gate намеренно не делает автоматический DB rollback и не запускает старый image при ошибке. Это защищает от запуска несовместимого приложения поверх частично изменённой модели ownership.
