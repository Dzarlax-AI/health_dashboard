Версии кэша и приоритет синхронизации

5 октября 2026 · Revision 1 · Approved · Локальная приёмка завершена · Release approved

Цель и границы

Обычный рестарт с актуальным кэшем не запускает исторический пересчёт. Новая синхронизация получает приоритет перед следующей единицей фоновой работы. Устаревший или незавершённый кэш восстанавливается, включая историю после изменения формул.

Сохраняем формулы, live/legacy AVG, неизвестные sleep-метрики, приоритеты источников, дедупликацию, зависимости Readiness и лимиты пула. dbt остаётся локальным средством сравнения. Без изменения API, Telegram, AI, production .env и без глобального удаления кэша при запуске.

Проверенные факты

  • Ветка codex/calculation-followup от main 8a8d6a350182d81f583168e2feefe93a73adb586, рабочее дерево до плана чистое.
  • enqueueStartupCacheRefresh всегда вызывает BackfillAggregates и BackfillScores. BackfillAggregates удерживает cacheMu на всём проходе; UpsertRecentCache использует тот же замок.
  • buildBaselineHROvernightAll обходит всю историю даже при force=false. BackfillScores(false) вычисляет историю от самого раннего hourly дня. Поэтому incremental не означает работу только над последними днями.
  • После релиза стартовый refresh основного tenant занял 4m12.695s; первая синхронизация ждала кэш 2m19.527s. Следующие проходы кэша заняли 1.04–1.08s. Это наблюдение одного релиза, не контролируемый benchmark.
  • AggregateContractChecksum пока идентифицирует SQL и политику в отчётах; он не подтверждает версию сохранённого кэша и не охватывает все вспомогательные формулы.

Контракт версии и восстановления

  • Новый tenant-local журнал обслуживания в существующей settings: типизированный JSON с target identity, статусом, диапазоном истории, завершёнными единицами и durable dirty dates. Новая таблица и изменение tenant schema contract не требуются. Записи обслуживает только storage-код; проверить, что обычное сохранение пользовательских настроек не удаляет служебные ключи.
  • Identity объединяет AggregateContractChecksum, ScoreVersion и новую явную версию вспомогательных расчётов baseline/sustained HR. Бамп вспомогательной версии обязателен при изменении её семантики. Это отметка завершённого обслуживания, а не заявление, что каждая историческая строка имеет собственную версию.
  • Версия отмечается завершённой только после успешного диапазона, зависимых стадий, публикации согласованного snapshot и отсутствия необработанных dirty dates. Любая ошибка остаётся незавершённой; чтение metadata с ошибкой не считается отсутствием/актуальностью версии.
  • Первый запуск без журнала консервативно создаёт проверенную базу всей имеющейся истории по текущему коду. Нельзя объявить старый кэш актуальным лишь потому, что он непустой. Пустая установка ждёт данные без бесконечного retry.
  • При той же завершённой версии и чистом журнале исторический проход пропускается. При несовпадении выполняется возобновляемый пересчёт; после аварии продолжается незавершённая работа.
  • Durable dirty dates регистрируются до завершения обработки принятой записи; снимаются только после успешного кэша и обязательных зависимостей. Учесть повторную запись той же даты: снять только обработанное поколение, более новое остаётся dirty. Импорт и административные изменения также должны оставлять корректный сигнал восстановления.

Приоритет и семантика

Фоновый startup runner обрабатывает ограниченные единицы по датам, освобождая доступ между ними. Tenant-local диспетчер сначала выдаёт ожидающую foreground работу. Синхронизация может дождаться уже выполняемой единицы, но не всего исторического прохода. Один фоновый worker на установку; MaxConns и глобальная параллельность не увеличиваются.

Для фоновых единиц применяются исторические SQL-правила с ограниченным диапазоном; для синхронизации — существующие live-правила. Все стадии одной даты завершены до её публикации. Дата, затронутая foreground во время фонового прохода, не должна затем быть перезаписана legacy-стадией: фиксируем поколение/владение и оставляем live-пересчёт последним. Исторический Readiness использует тот же lookback и source epochs; дробление не должно менять результат.

Длинный уже начатый запрос невозможно мгновенно уступить. Проверяем длительности единиц, ограничиваем их контекстом и уменьшаем диапазон при необходимости. Не обещаем нулевое ожидание. На ошибках — cooldown и сохранение прогресса; на shutdown — отмена фона. Полные завершённые dashboard snapshots остаются доступными, частичный результат не маркируется свежим.

Проверки и критерии

Фактические проверки: все 12 синтетических aggregate снимков совпали с чистым baseline; bounded legacy-date совпал с legacy-force. Полный go test ./..., race затронутых пакетов, contract-check, pure Go build и diff-check прошли. Изолированный PostgreSQL подтвердил journal isolation/generation fencing, import marker, quality correction, rollback/deadline, cursor resume, отсутствие range scan для актуальной версии и запрет публикации нового snapshot при correction interleaving. Target/feature/baseline/Energy результаты ремонта совпали с writer-major проходом, включая пропущенную будущую ночь и сохранение живых intraday/EOD наблюдений. Проверки ниже описывают критерии и будущую release QA; production latency пока не измерялась для нового кода.

  • Снять новый синтетический baseline текущего main через run_go_contract.py --record в отдельном каталоге, затем --compare; не перезаписывать предыдущие эталоны. Дополнить meaningful fixtures с неравномерными источниками и границами сна для диапазонных historical helpers.
  • DB integration: одинаковая версия без dirty dates — ноль historical jobs; смена каждой составляющей identity — нужный диапазон; отказ SQL/чтения/записи/публикации — completion не записан; crash/resume, пустая установка, interleaving двух ingestion поколений, изоляция двух tenants.
  • Concurrency: управляемые барьеры подтверждают, что foreground ждёт максимум текущую единицу и исполняется до следующей; background не затирает live результат. Проверить cancellation, pool budget и отсутствие deadlock.
  • Snapshot QA: старый завершённый snapshot читается во время восстановления; incomplete состояние не выдаётся за новую успешную генерацию; readiness lookback parity.
  • go test ./internal/storage ./internal/handler ./cmd/server; go test -race для затронутых пакетов; полный go test ./...; make contract-check; CGO_ENABLED=0 go build -o /tmp/health-startup-cache-server ./cmd/server; git diff --check. DB проверки — изолированный локальный PostgreSQL, без production данных.
  • Отдельный release QA после разрешения: exact image pair и tenant gate, первый запуск/повторный рестарт, реальная синхронизация во время background работы, публичный API и все Today стадии. Не считать green CI доказательством production latency.

Риски и восстановление

Главные риски: ошибочно пропущенные stale caches, потерянное dirty поколение, смешение live/legacy правил, неполный lookback, длительный запрос и starvation фонового восстановления. Первый baseline может занять значительное время, но должен уступать foreground между единицами. Не переносить текущий checksum автоматически в завершённую metadata.

Откат к предыдущему образу возвращает прежний startup refresh. Исходные health_records и metric_points не удаляются. Незавершённый журнал сохраняется; новая версия при следующем запуске перепроверяет identity и диапазон. Production rollback, принудительный пересчёт и изменение .env не входят в локальное approval.
