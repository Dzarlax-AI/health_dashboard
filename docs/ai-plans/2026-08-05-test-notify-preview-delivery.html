Telegram test-notify: повторяемый preview

План одобрен 2026-08-05 · Реализация выполнена

Задача и подтверждённая причина

«Тест утро» и «Тест вечер» вызывали production-функции отправки. Они использовали дневные ключи report:<kind>:<date> в notification_deliveries. После настоящего отчёта повторное резервирование возвращало reserved=false, Telegram transport не вызывался, а endpoint всё равно отвечал message sent.

Согласованное поведение

  • Каждое нажатие test-notify отправляет сообщение; cooldown отсутствует.
  • Отчёт заново собирается из актуальных детерминированных метрик.
  • AI provider не вызывается: используются сохранённые блоки, включая SYNTHESIS и legacy fallback.
  • Preview не создаёт и не меняет production delivery-key.
  • Scheduler и proactive delivery сохраняют durable at-most-once семантику.

Рассмотренные варианты

  1. Удалять production delivery-key — отклонено как нарушение at-most-once гарантии.
  2. Создавать minute-bucket test-key — отклонено после решения не ограничивать частоту.
  3. Явный preview delivery без durable reservation — выбран и реализован.

Фактические изменения

  • internal/notify/report.go: добавлены политики durable/preview и функции SendMorningPreview, SendEveningPreview.
  • Production и preview используют одинаковый путь подготовки payload и одинаковый Rich Message fallback.
  • cmd/server/main.go: admin test callback переключён только на preview API; provider regeneration отсутствует.
  • internal/notify/report_test.go: preview дважды проходит поверх уже занятого production-key, reservation store не вызывается; production остаётся at-most-once; transport error распространяется.

Воздействие

  • БД и миграции: изменений нет.
  • HTTP API: URL и JSON-форма ответа не меняются.
  • Auth/tenant routing: без изменений.
  • Стоимость AI: дополнительных вызовов нет.
  • UX: несколько кликов намеренно создают несколько сообщений.

Manual QA после деплоя

  • После настоящего morning report дважды нажать «Тест утро» и получить два сообщения.
  • Дважды нажать «Тест вечер» и получить два сообщения.
  • Проверить отсутствие новых AI generation событий.
  • Проверить, что test clicks не добавили production delivery rows.

Риски и ограничения

  • Повторные клики могут создать Telegram spam; это явно выбранная семантика без cooldown.
  • Transport timeout остаётся неоднозначным: Telegram мог принять сообщение даже при ошибке ответа; автоматический retry не добавлен.
  • Полное готовое сообщение не кешируется, поэтому deterministic metrics остаются актуальными на момент preview.

Rollback

Вернуть test callback к SendMorning/SendEvening и удалить preview policy/API. Миграций и очистки данных не требуется.
