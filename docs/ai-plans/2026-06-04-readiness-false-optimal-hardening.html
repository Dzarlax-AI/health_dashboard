Implementation Plan: Readiness False Optimal Hardening

Plan for issue #175: prevent Health Dashboard from presenting a fully confident optimal readiness or recovery state when same-day evidence is incomplete, unstable, or contradicts illness/recovery signals.

Approval required before implementation area:readiness evidence-boundary plan-only branch

Task Summary

The dashboard recently showed a perfect or near-perfect readiness score on a private acute illness/recovery-impaired day. After an additional sync, the score moved into a more plausible range, which means the final daily data was not the only problem: the system also needs a safer freshness, confidence, and component-capping contract while data is still accruing.

The goal is not to copy Bevel, Oura, Whoop, or any third-party number. The goal is to preserve Health Dashboard's own evidence contract: high readiness should require complete, concordant evidence, and contradictory illness/recovery signals must be visible to the score or its confidence.

Transparency Principle

Health Dashboard's primary goal is to be transparent and honest. If the system does not have enough same-day evidence, it should say that plainly and wait for data rather than fabricate certainty, silently reuse stale inputs, or normalize away missing components.

  • Missing acute data is a first-class state, not a neutral value.
  • Confidence must be visible whenever the displayed score is provisional or capped.
  • The UI should prefer honest copy such as "waiting for today's recovery data" over a falsely precise readiness claim.
  • AI insights must follow the same rule: no confident AI recommendation may be generated from incomplete same-day evidence.
  • The morning Telegram check-in is collected before the AI insight for a reason: it must help the AI explain how the user's subjective state aligns or conflicts with the objective signals.
  • Debug/API metadata should explain which inputs are present, missing, stale, or excluded.

Plan Review Verdict

Decision: approved with amendments. The direction is correct, but the original draft left several policy choices open. This revision closes those choices so implementation can be reviewable and bounded.

  • Keep this as a serving-safety PR first; do not redesign the whole readiness model in one pass.
  • Prefer additive API metadata over breaking existing clients.
  • Cap user-facing confidence/band conservatively while preserving the raw numeric score for audit/debug.
  • Do not rewrite all historical readiness aggregation in this PR; create a separate history/backfill follow-up after the serving contract is validated.
  • Make date-aligned evidence explicit in v1; do not rely on slice discipline to prevent stale fallback.

Inspected Current Behavior

Readiness Formula

  • internal/health/readiness.go computes a z-score readiness over HRV, RHR, and sleep duration.
  • When a component is missing, the weighted z-score is normalized over the remaining available components.
  • Sleep readiness mostly sees duration plus modest consistency/absolute-duration penalties.
  • RecoveryPct is currently assigned to the same number as readiness in ComputeBriefing.

Storage and Freshness

  • internal/storage/briefing.go reads cached daily_scores, then overrides the latest day from raw points via freshDayFromRaw.
  • appendIfPositive compresses metric slices, so missing component days disappear from the scoring input rather than remaining explicit.
  • computeReadinessHistory recomputes historical scores from metric_points for HRV, RHR, and sleep_total.
  • baseline_hr_overnight exists in daily_scores, but it is not part of the readiness score.

Private validation note: the problematic day is intentionally described as a pattern rather than raw values. The public plan should not publish personal health measurements.

Desired Behavior

  • A day with incomplete same-day autonomic data cannot render as fully confident optimal.
  • Same-day readiness must not silently fall back to previous-day acute inputs when today's key signals are missing.
  • If key same-day evidence is missing, the dashboard should explicitly say it is waiting for data instead of inventing a confident score.
  • High HRV from a sparse or unstable sample set cannot dominate readiness without a confidence caveat or cap.
  • Elevated overnight heart rate can reduce or cap recovery/readiness when rhr_avg is missing or stale.
  • Sleep architecture and sleep quality can reduce readiness when sleep duration alone looks acceptable.
  • Moderate or high illness_suspicion can cap readiness confidence or band without becoming a diagnosis.
  • API and UI surfaces can explain which components were used, missing, low-confidence, or capped.
  • AI briefing blocks must not present final recovery/readiness recommendations when the underlying evidence is provisional or incomplete.
  • When a pre-insight Telegram check-in exists, AI should use it as subjective context and explain plausible evidence boundaries: what metrics support it, what metrics do not, and what is still missing.

Key Design Decisions

Decision Proposed v1 Policy Reason
Readiness vs recovery Keep RecoveryPct as a compatibility alias for one PR, but stop presenting it as independent recovery in UI copy and expose recovery_source=readiness_legacy_alias. A hard API break is unnecessary for this fix, but current semantics are misleading and must be visible.
Data accruing If key same-day inputs are incomplete, keep raw score but set readiness_confidence=provisional and cap the displayed band at fair. Perfect readiness during partial sync is worse than a conservative temporary estimate; keeping raw score preserves auditability.
No stale acute fallback For today's briefing, do not fill missing acute inputs from prior days. Add a date-aligned ReadinessEvidenceInput in v1 so previous days may inform baselines/trends, but missing same-day HRV/RHR/overnight HR/respiratory/sleep-quality evidence stays explicit. During abrupt illness or recovery changes, yesterday's normal data is actively misleading if presented as today's state.
Honest missing-data state When required same-day evidence is absent, render a waiting/provisional state with explicit missing inputs rather than a normal-looking score card. The product promise is auditability and honesty, not filling every card at all costs.
AI insight gating Backend assigns AI mode before prompting: withheld, provisional_explanation_only, needs_regeneration_after_sync, or confident_advice_allowed. Prompt instructions then operate inside that mode. AI prose can sound more authoritative than the UI; the model must not decide by itself whether confident advice is allowed.
Check-in as AI context Include same-day Telegram check-in status/answer in AI prompt inputs and cache hashes. Use it to explain subjective-objective alignment or mismatch, not as a standalone diagnosis. The scheduler collects check-in before insight generation specifically so the narrative can reflect how the user says they feel.
HRV robustness Full-confidence HRV requires at least 3 valid HRV samples inside the selected main sleep/rest window. If the sleep window is unavailable, require at least 4 valid same-day samples and mark confidence provisional. One unusually high HRV sample should not turn a recovery-impaired day into optimal.
RHR fallback Use baseline_hr_overnight as a secondary autonomic penalty and as fallback when rhr_avg is absent or stale. Overnight HR can be available and meaningful before the platform emits same-day RHR.
Illness cap moderate illness suspicion caps displayed readiness band at fair; high caps it at low. Numeric raw score remains available in debug metadata. The illness layer already expresses converging evidence and should prevent contradictory hero states.
Sleep quality Sleep quality affects the numeric score through penalties, and can also cap confidence when stage/awake evidence is severe. Duration-only sleep can look normal during poor recovery; Bevel-style quality disagreement exposed this gap.
Historical scores First PR hardens current briefing and latest-day serving. Historical robust-HRV/backfill changes are a separate follow-up unless tests show the same code path must change for correctness. This keeps the review surface small and avoids moving the entire readiness history before the serving contract is validated.
Rollback controls Add simple code-level constants such as EnableReadinessEvidenceCaps and EnableAIReadinessGating, defaulted on, so caps/gating can be disabled separately if production behavior is too pessimistic. A small safety switch is cheaper than reverting the whole feature if only one presentation layer misbehaves.

Closed Policy Answers

  • RecoveryPct: keep it for compatibility in this PR, but mark it as a legacy readiness-derived alias and avoid UI wording that implies an independent recovery model.
  • Recovery UI wording: replace or soften independent "Recovery" presentation in UI. Use "Readiness", "Recovery proxy", or an explicit compatibility note until a true recovery model exists.
  • HRV threshold: full-confidence HRV requires at least 3 valid samples inside the selected main sleep/rest window. Without sleep-window alignment, require at least 4 same-day samples and mark HRV provisional.
  • HRV constants: implement thresholds as named constants, not inline literals: MinSleepWindowHRVSamplesForFullConfidence = 3 and MinUnalignedHRVSamplesForProvisionalUse = 4.
  • Same-day missingness: missing acute same-day inputs are never filled from previous days for the current briefing. Prior days are baseline/trend context only.
  • ReadinessEvidenceInput: date-aligned evidence input is in v1 scope, not a follow-up. Each component carries value, evaluated date, source date, presence/freshness, sample count, confidence, and missing reason.
  • Missing data copy: if key evidence is missing, UI copy should say the system is waiting for today's recovery data. Do not imply the missing data is normal.
  • AI insights: when readiness/recovery evidence is provisional, AI blocks must either be withheld, regenerated with explicit provisional context, or limited to a missing-data explanation. No confident training/recovery recommendation from incomplete evidence.
  • Pre-insight check-in: same-day Telegram check-in is an AI input. The insight should explain whether objective signals support, partially support, or fail to explain the user's answer.
  • Moderate illness: cap displayed band at fair and set cap reason; do not hide the raw numeric score from API/debug output.
  • High illness: cap displayed band at low and mark the score as safety-capped, still without diagnostic wording.
  • Sleep quality: apply numeric penalties first, then confidence/band caps only for severe stage/awake evidence or missing stage evidence that prevents confident interpretation.
  • History: latest briefing first. Historical readiness robust aggregation and full recompute become a follow-up issue/PR after private validation.

Serving Pipeline Contract

Implementation should keep the scoring pipeline explicit. Raw physiology scoring and serving safety are related but separate steps:

  1. Evidence collection: build date-aligned ReadinessEvidenceInput with explicit missing/stale/sample-count metadata.
  2. Raw readiness score: compute the auditable raw numeric score from available components.
  3. Evidence quality: evaluate component confidence, freshness, missing inputs, and subjective/objective context.
  4. Safety caps: apply illness, missingness, sparse-HRV, sleep-quality, and overnight-HR caps to display band/confidence.
  5. Display readiness: emit raw score, display score/band, confidence, cap reason, and component explanations.
  6. UI/AI presentation: render honest missing-data/provisional copy and restrict AI advice mode accordingly.

Implementation Steps

  1. Add a pure-health readiness result type, for example ReadinessComputation, with score, band, confidence, components, caps, missing inputs, and reason codes.
  2. Add date-aligned ReadinessEvidenceInput and component evidence types. Each component should carry Value, Present, EvaluatedDate, SourceDate, Freshness, SampleCount, Confidence, and MissingReason where applicable.
  3. Preserve existing ComputeReadinessScore as a compatibility wrapper, but make new briefing paths consume the richer computation.
  4. Update storage input construction so latest-day missingness stays explicit instead of being lost by compressed slices. Current-day acute components must be date-keyed; do not let appendIfPositive shift yesterday's value into today's slot.
  5. Add HRV sample-count metadata and implement a robust daily HRV policy. Start conservatively: use sleep/rest-window samples when available; otherwise sparse or unaligned HRV reduces confidence and caps displayed band before changing all historical aggregation semantics.
  6. Add overnight HR fallback or penalty path using baseline_hr_overnight when same-day RHR is missing.
  7. Add sleep-quality penalties or caps from deep sleep percentage, awake percentage, efficiency, and existing SRI when available. Numeric penalties should apply before band caps so the score remains interpretable.
  8. Apply illness/autonomic caps after illness suspicion is computed, so the hero readiness state cannot contradict the warning surface.
  9. Update UI copy and API output to distinguish score from confidence. If key evidence is missing, show an explicit waiting/provisional state. Avoid medical or diagnosis wording.
  10. Gate AI generation and cached AI block reuse on readiness evidence completeness. Include confidence/missing-input metadata and same-day check-in status/answer in the AI input hash so a provisional block cannot be reused after complete data arrives, a complete-data block cannot be shown for a provisional state, and a pre-check-in block cannot survive after the user answers.
  11. Enforce AI advice mode in backend before prompt generation. The prompt receives an allowed mode; it does not choose whether confident advice is safe.
  12. Update AI prompt instructions: when subjective check-in and objective data disagree, explain the disagreement honestly. Examples: "You report feeling sick; respiratory and overnight HR support that, but HRV is not yet aligned" or "You report feeling bad; today's key recovery inputs are still missing, so the system should wait before drawing a confident conclusion."
  13. Decide at implementation time whether ScoreVersion must change. Serving-only confidence/cap metadata does not require a historical cache bump; persisted score formula changes do.
  14. Add code-level safety constants for readiness caps and AI gating, both enabled by default.
  15. Run private retrospective sweeps on Profile A and Profile B before PR submission, reporting only anonymized counts and pattern summaries.

Data, API, UX, and Deployment Impact

  • Database: no schema migration is expected for v1 if metadata is computed at read time. Cached daily_scores.readiness needs recomputation only if the persisted score formula changes.
  • API: additive fields are preferred, such as readiness_raw_score, readiness_display_score, readiness_confidence, readiness_components, readiness_cap_reason, and recovery_source. Existing fields should remain for clients.
  • UI: the hero card should show capped/low-confidence states without alarming copy. Example: "Waiting for today's recovery data" or "Readiness is provisional while today's recovery signals are still settling."
  • Recovery wording: UI must not present RecoveryPct as an independent physiological recovery model while it remains a readiness alias.
  • AI briefing: AI block prompts and inputs_hash must include readiness confidence, missing-data state, and same-day check-in. If evidence is incomplete, AI output should be deferred or explicitly provisional.
  • Telegram/reporting: morning report AI text must not override rule-based provisional banners or imply complete recovery evidence.
  • MCP: no separate MCP logic. MCP should receive the canonical briefing object passively, including readiness confidence and AI provisional state.
  • Deployment: normal GHCR image deploy. After deploy, run cache recompute/backfill or rely on startup recompute depending on final implementation.

Risks and Edge Cases

  • Over-capping: conservative caps can make the dashboard feel pessimistic on normal days with sparse data.
  • Sync timing: a provisional morning score may differ from the final post-sync score. The UI should make this visible rather than hide it.
  • Stale acute substitution: previous-day values can make an abruptly sick day look healthy. The implementation must keep baseline/trend fallback separate from same-day evidence.
  • Over-empty UI: honest missing-data states can feel less polished than a filled score. This is acceptable; polish must not come at the cost of false certainty.
  • AI cache staleness: if readiness confidence is not included in AI inputs, stale confident AI text can survive after the numeric score is corrected. The cache key must include confidence/missing-data state.
  • Subjective overreach: check-in can help explain the day, but AI must not treat "sick" as proof of illness or "great" as proof that objective risk is absent.
  • Historical drift: changing persisted HRV aggregation or sleep quality semantics can move old readiness history. Keep this out of the first PR unless necessary; if included, bump ScoreVersion and document the change.
  • Client compatibility: mobile/MCP clients may expect existing readiness fields. Prefer additive fields first.
  • Medical overclaiming: illness caps must stay evidence-bound and non-diagnostic.

Rollback Plan

  • Revert the readiness hardening PR if score behavior regresses badly.
  • Restore the previous serving behavior by redeploying the prior image. If a persisted score-version change is included, cached scores can be recomputed from source data.
  • If UI confidence copy is confusing, hide the new explanatory fields while keeping backend caps disabled behind a code-level feature flag or constant.
  • If caps are too pessimistic but AI gating is correct, disable EnableReadinessEvidenceCaps only. If AI text is wrong but numeric caps are useful, disable EnableAIReadinessGating only.
