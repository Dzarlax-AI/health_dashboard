Implementation Plan: Admin Profile Scope and Candidate Monitoring

Approval required before implementation

Task Summary

Fix the multi-user admin page so profile tabs are truly tenant-scoped, then expose the evidence-only Recovery rolling_3d_candidate_2of3 target in admin readiness monitoring. This PR must not change dashboard verdicts, Telegram copy, chips, scoring, or production behavior outside admin/evidence surfaces.

Current Behavior

The backend already has the right default for readiness admin fragments: omitted schema means the request tenant, explicit schema=<tenant> means one tenant, and explicit schema=all means read-only aggregation.

The leak is in internal/ui/templates/pages/admin.html: the tenant panel initializes readiness contract and monitoring with schema=all, and setTenantHTMX also falls back to schema=all when activeAdminSchema is empty. Hidden HTMX load triggers can therefore render all tenants inside the reused tenant panel.

Desired Behavior

  • General remains the place for global configuration and can keep all-tenant read-only surfaces when explicitly added there.
  • Each user/profile tab must load tenant panel fragments with that profile's schema only.
  • The tenant panel must never use schema=all as a fallback for readiness contract or monitoring.
  • Recovery candidate coverage should appear as an evidence-only monitoring row: recovery_stability / rolling_3d_candidate_2of3.

Files Likely to Change

  • internal/ui/templates/pages/admin.html - remove schema=all fallback from the tenant panel and keep profile refreshes schema-specific.
  • internal/storage/readiness_redesign_monitoring.go - add candidate target coverage to monitoring.
  • internal/storage/readiness_redesign_monitoring_test.go - pin candidate target coverage and its 3-day maturity lag.
  • internal/ui/admin_*_test.go - add or adjust tests so scoped monitoring remains one tenant by default and template URLs do not regress.
  • This HTML plan - update with actual changes and verification results after implementation.

Implementation Steps

  1. Change static tenant-panel HTMX URLs for readiness contract and monitoring from schema=all to tenant-default URLs.
  2. Change setTenantHTMX so tenant refreshes append schema=<active profile> only when a profile tab is active, and otherwise use server tenant default.
  3. Keep all mutating admin actions per-tenant; do not introduce any all-tenant write path.
  4. Add rolling_3d_candidate_2of3 to readiness monitoring coverage with the same 3-day maturity lag as strict rolling_3d.
  5. Add focused regression tests for the template/monitoring behavior.

Impact

  • Data/API: no schema migration and no new endpoint.
  • Auth/permissions: no new permissions; existing admin schema override rules stay in force.
  • UX: profile tabs become isolated. General configuration stays separate from per-profile operational diagnostics.
  • Product behavior: no user-visible readiness behavior changes outside admin.

Test Plan

  • go test ./internal/storage -run ReadinessMonitoring -count=1
  • go test ./internal/ui -run "AdminReadiness|TenantScope|AdminTemplate" -count=1
  • go test ./...
  • After deploy, verify read-only monitoring with schema=health, schema=health_mariia, and schema=all returns the expected tenant sets.

Risks and Edge Cases

  • Hidden HTMX elements may still fire load triggers; the safe default must therefore be tenant-scoped, not all-tenant.
  • Adding candidate monitoring rows can change admin overall status if the candidate target is sparse. This is acceptable only if the row is evidence-only and uses the same mature-window contract.
  • General all-tenant views should stay read-only. No write action should accept schema=all.

Rollback Plan

Revert the admin template URL changes and remove the candidate monitoring target entry. No database rollback is required because this PR only reads existing target snapshots and changes template/monitoring logic.

Open Questions

  • Should General later include an explicit all-tenant readiness overview section, separate from the tenant panel? This PR can leave that out to keep the scope tight.

Approval Gate

Implementation must not start until this plan is approved. The intended approval scope is limited to admin tenant scoping plus evidence-only candidate monitoring visibility.

Implemented Changes

  • Tenant-panel readiness contract and monitoring HTMX URLs now default to the request tenant instead of schema=all.
  • setTenantHTMX now appends schema=<active profile> only for an active profile tab and does not use all-tenant fallback.
  • Readiness monitoring now includes recovery_stability / rolling_3d_candidate_2of3 as an evidence-only coverage target with a 3-day mature-window lag.
  • Added a template regression test that fails if tenant-panel readiness fragments default back to all schemas.
  • Extended storage monitoring tests so the candidate target is pinned to the same maturity behavior as strict rolling_3d.
