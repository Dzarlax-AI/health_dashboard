Implementation Plan: DB Test Harness Redesign

Approved; harness implemented with follow-up lane closure

Task Summary

Replace the current ad-hoc DB-backed integration test pattern with a predictable test system: fast default tests, explicit DB integration commands, bounded database connection usage, reusable schema fixtures, and clear runtime expectations.

Current Behavior

  • Default CI runs CGO_ENABLED=0 go test ./... and DB-backed tests skip when no Postgres env is configured.
  • CONTRIBUTING.md documents that DB-backed tests use READINESS_TEST_DSN or libpq env vars and create throwaway schemas.
  • internal/storage has many tests calling testDB(t); several files create many independent throwaway schemas in one package run.
  • Before the issue #182 changes, testDB(t) used production-sized tenant pools through NewWithSchema (MaxConns=8, MinConns=2) for every throwaway schema.
  • Issue #182 introduced a smaller test pool and a readiness-only helper, but the broader pattern still creates a large number of schemas and pools.
  • Some UI tests use a separate testTenantDB(t) helper and can drift from storage setup unless kept in sync manually.
  • The current Makefile has no useful test-unit, test-db, or test-ci targets; make test is an HTTP smoke POST against a running server.

Observed Pain

  • Targeted DB tests can take seconds each over remote Postgres even when the actual assertion is small.
  • Broad DB package runs are not a normal dev-loop: internal/ui passed in about 76 seconds in one run, while internal/storage timed out at 120 seconds while opening another DB pool.
  • Sandbox-blocked network can make DB tests look green because helpers skip after connect: operation not permitted.
  • Long-running DB tests are hard to interrupt cleanly and can leave test-prefixed schemas behind.

Desired Behavior

  • Default local and CI test loop remains fast and does not require a live DB: go test ./... or make test-unit.
  • DB integration tests have a named command such as make test-db, explicit environment requirements, and a realistic runtime target.
  • DB integration commands fail fast when DB execution is explicitly requested but the database is unreachable. They must not silently skip in that mode.
  • Unit commands must not accidentally run DB tests just because libpq env vars such as PGHOST are present in the user's shell.
  • DB tests use test-sized pools with no idle connection floor and bounded total connections.
  • DB tests reuse a small number of schemas per package or test group and reset tables between tests instead of creating a fresh schema for every test case.
  • Tests declare the schema family they need: full health schema, readiness redesign only, energy snapshots only, or UI tenant schema.
  • Skipped DB tests are distinguishable from executed DB tests in docs and command output.
  • Slow integration tests are grouped or tagged so developers can run focused lanes without paying for the whole suite.

Activation Contract

  • Use env-gated DB tests for the first implementation pass, not build tags. Build tags can be revisited later if env-gating remains confusing.
  • Add a dedicated required flag such as HEALTH_DB_TESTS=1 for DB execution. DB helpers should skip unless this flag is set, even if PGHOST or READINESS_TEST_DSN exists in the shell.
  • make test-unit: clears or ignores HEALTH_DB_TESTS and runs the default pure suite.
  • make test-db-storage, make test-db-ui, and make test-db: set HEALTH_DB_TESTS=1 and require READINESS_TEST_DSN or libpq env. In this mode, connection failure must be t.Fatal, not t.Skip.
  • Keep go test ./... behavior compatible with CI: pure tests run, DB tests skip unless HEALTH_DB_TESTS=1 is explicitly set.
  • Do not repurpose the existing make test target in the first pass. Add explicit targets and optionally add make smoke-health-post as an alias for the existing HTTP smoke command.

Proposed Architecture

  • Create a real shared test helper package, likely internal/testdb, instead of hiding helpers in internal/storage/*_test.go. Both internal/storage and internal/ui tests can import it.
  • internal/testdb should own connection parsing, the HEALTH_DB_TESTS activation contract, test-sized pgx pool configuration, schema create/drop, and identifier quoting.
  • Storage-specific setup can stay in internal/storage test helpers when it needs unexported storage symbols, but low-level schema/pool lifecycle should be shared.
  • Use one schema per package run or per test file group where isolation permits, with TRUNCATE ... RESTART IDENTITY CASCADE or targeted DELETE resets between tests.
  • Keep destructive DDL drift tests isolated in their own disposable schema because they intentionally mutate table shape.
  • Keep writer/backfill tests that depend on broad table sets on a full-schema fixture, but move pure readiness table tests to readiness-only fixtures.
  • Expose separate commands: make test-unit, make test-db-storage, make test-db-ui, make test-db, and possibly make test-all.
  • Document runtime goals: unit suite under normal CI budget; targeted DB lanes ideally under 30 seconds each on the configured local network; full DB lane allowed to be slower but not part of routine edits.

Fixture Reset Contract

  • Do not migrate all DB tests to shared schemas at once. First classify tests as shared-safe or isolated-required.
  • Shared fixtures must reset data before each test with an explicit table list. For full health schemas, reset should include health_records, metric_points, caches, daily_scores, settings, workouts, energy_snapshots, readiness tables, check-ins, AI tables, and any future startup-created tables used by tests.
  • Use FK-safe ordering or TRUNCATE ... RESTART IDENTITY CASCADE only on test-owned schemas. Never run broad truncate against a production tenant schema.
  • After resetting readiness tables, reseed the bootstrap source_epochs row exactly as EnsureReadinessRedesignTables does.
  • After resetting settings, tests that depend on config must seed explicit values instead of relying on leftovers from another test.
  • Tests that mutate schema shape, source epoch boundaries in hard-to-restore ways, global config semantics, or table definitions remain isolated in disposable schemas.
  • Run shared-schema tests sequentially unless the fixture can allocate independent schemas per parallel group. Do not introduce t.Parallel() for tests sharing one schema.

  • internal/storage/*_integration_test.go, internal/storage/*_test.go - migrate repeated testDB(t) calls to appropriate shared fixtures or narrower helpers.
  • internal/ui/admin_readiness_redesign_config_test.go - current home of UI tenant DB helper; align with storage harness or wrap shared setup without exporting production APIs.
  • internal/testdb - new test helper package for shared DB activation, pool, schema lifecycle, and cleanup primitives.
  • Makefile - add explicit test targets and rename the current HTTP smoke target if needed.
  • CONTRIBUTING.md - document test lanes, DB env, skip behavior, runtime expectations, and cleanup commands for test-prefixed schemas.
  • .github/workflows/ci.yml - update stale comments and optionally switch CI to make test-unit once that target exists.
  • docs/TEST_COVERAGE.md - update the testing roadmap with the DB harness policy.
  • docs/ai-plans/2026-06-29-issue-182-db-backed-integration-tests.html - link this follow-up as the broader harness redesign.

Implementation Steps

  1. Inventory DB-backed tests by schema needs and reset requirements: full health, readiness-only, energy-plus-settings, UI tenant, destructive DDL, and pure tests that should not use DB at all. Record this inventory in a short doc or table before migrating tests.
  2. Add internal/testdb with the activation contract: skip when HEALTH_DB_TESTS is unset; fail when it is set and connection/schema creation fails; use test-sized pools; expose schema lifecycle helpers.
  3. Add Makefile targets for unit and DB lanes. Keep existing HTTP smoke behavior under the current make test target for compatibility in the first pass, or add smoke-health-post without changing make test.
  4. Update CI workflow comments, route unit CI through make test-unit, and add automatic Postgres service-container CI for stable DB lanes once their runtime is bounded.
  5. Move the existing storage helper code out of recovery_stability_writer_integration_test.go so the harness is not hidden in one feature test file.
  6. Convert readiness-only tests first, because their dependency surface is smallest. Keep destructive drift tests isolated.
  7. Convert energy tests only after inventory confirms exact dependencies such as settings, energy_snapshots, and any config tables read by EnergyBank paths.
  8. Convert full writer/backfill tests in batches, using shared fixtures only for tests proven shared-safe. Leave high-risk tests on isolated schemas.
  9. Unify UI helper setup by importing internal/testdb for schema/pool lifecycle, while keeping UI-specific handler context helpers in internal/ui.
  10. Update docs and plan files with exact commands, expected env, skip/fail behavior, cleanup commands, and runtime expectations.
  11. Run focused lanes after each migration batch rather than one huge suite after every edit.

Manual QA Checklist

  • Confirm DB tests create only schemas with explicit test prefixes.
  • Confirm cleanup removes test schemas after success and after failures where Go cleanup runs.
  • Confirm no production tenant schema is used when READINESS_TEST_DSN points at the shared database.
  • Confirm connection counts stay bounded while running DB lanes.
  • Confirm docs explain that sandbox/network-denied skips are not real DB verification.

Risks And Edge Cases

  • Shared schemas can leak state between tests if reset helpers are incomplete. Migrate incrementally and keep destructive tests isolated.
  • Over-optimizing setup can hide missing startup DDL. Keep at least one full-schema provisioning test that validates startup helpers together.
  • Some tests may depend on sequence values or computed timestamps; table resets must account for those assumptions.
  • Makefile target changes could confuse existing workflow if make test is repurposed. Prefer adding explicit targets first and only renaming the smoke target after a clear doc update.
  • Remote Postgres latency means “fast” has a ceiling; pure tests should carry most feedback, DB tests should be targeted and explicit.

Rollback Plan

Revert harness/helper migrations and Makefile/docs changes. Because the plan targets test infrastructure only, production behavior should not need rollback. If a run leaves test schemas behind, drop only schemas with the documented test prefixes.

Open Questions

  • Should DB tests eventually run in GitHub Actions using a Postgres service container, or stay local/manual only?
  • What runtime SLA should be enforced for make test-db-storage and make test-db-ui on this machine/network?
  • After the env-gated harness is stable, should DB integration tests move to build tags for even stronger separation?
  • After new targets exist, should make test eventually become the default unit test target, or remain the HTTP smoke command permanently?

  • Added storage.NewFromPool so tests can wrap test-sized pools without using production tenant pool sizing.
  • Rewired storage and UI DB helpers to use internal/testdb.
  • Converted storage DB helpers to shared package-level schemas guarded by mutexes, with reset before each test and schema drop in TestMain.

  • Kept destructive readiness DDL tests on an isolated readiness schema.
  • Added Make targets: test-unit, test-db-storage, test-db-ui, test-db, and smoke-health-post. Existing make test remains the HTTP smoke command via smoke-health-post.
  • Follow-up lane closure added test-db-ui-fast, test-db-energy-smoke, test-db-energy, and test-db-readiness. test-db now runs only the fast DB contract lanes in sequence: UI-fast, Energy-smoke, and Readiness.

  • test-db-ui and test-db-energy remain full domain sweeps for changes that touch those areas.

Known Limitations And Follow-Up

  • This implementation establishes the activation contract, shared low-level harness, shared storage/UI schemas, and one specialized energy fixture.
  • The broad make test-db-storage lane is still too slow for automatic CI because acute/chronic/passive/recovery writer groups perform substantial DB work; the measured full storage run timed out at 120s.
  • The routine make test-db lane now avoids the full storage package, full UI package, and full Energy verdict-band group. test-db-readiness intentionally excludes readiness monitoring tests because they still use the full storage DB helper and failed during the first targeted-lane trial.
  • The full UI DB lane is reliable but not sub-20s on the current remote Postgres path; use make test-db-ui-fast for tight UI handler loops and make test-db-ui for broader UI DB verification.
  • The full Energy DB lane is now bounded enough for domain verification after batching seed rows, but remains separate from the routine make test-db aggregate.
  • The next implementation batch should convert more repeat-schema groups to specialized fixtures only where dependency inventory shows it is safe.
