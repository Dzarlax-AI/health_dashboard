Implementation Plan: Illness Suspicion Evidence and MCP Surface

Approval required before implementation

Task Summary

Add an evidence-bound illness suspicion layer that detects acute, same-day respiratory/autonomic anomalies without diagnosing illness. The layer should be visible in the main health briefing, available to MCP clients, and testable from anonymized real-data patterns.

Current Behavior

  • internal/mcpserver/tools.go returns GetHealthBriefing() directly for get_health_briefing; MCP does not calculate illness evidence itself.
  • internal/health/alerts.go calculates respiratory and wrist-temperature alerts over a 7-day recent average versus baseline. This is useful for sustained drift but can miss a single acute day.
  • SpO2 is present in RawMetrics, daily cache, dashboard cards, and cardio section, but it is not part of anomaly alerts.
  • RawMetrics is slice-based and compressed by available values. Same-day illness evidence must not infer date alignment from parallel slice indexes alone.
  • EnergyBank.Flags documents an illness_signature flag, but the live case had no flags because the existing signature is narrower than this respiratory/SpO2 pattern.
  • The generic MCP find_anomalies tool can detect metric-level anomalies only when the agent already knows which metric/date range to query.

Desired Behavior

  • Expose a structured illness_suspicion object on BriefingResponse.
  • Use converging evidence, not diagnosis: respiratory rate, SpO2 average/drop/low cluster, RHR, HRV, wrist temperature, sleep disruption, activity-adjusted sustained HR load, existing stress flags, and optional subjective check-in answer.
  • Detect acute same-day anomalies separately from existing 7-day alerts.
  • Surface confidence and reasons with exact contributing deltas, e.g. low, moderate, high, signals[], reason.
  • Keep wording evidence-bound: "signals consistent with illness or respiratory stress", never "you are sick".
  • Make MCP consumption first-class, either through the enriched get_health_briefing response or a focused get_illness_suspicion tool.

Scientific Rationale

The implementation should treat wearable metrics as converging evidence, not diagnosis. The design choices below are grounded in published wearable-health and sleep/immune research, but the output must remain conservative because consumer devices, missing data, activity context, and individual baselines can all confound interpretation.

Design decisionEvidence basisImplementation consequence
Use respiratory rate, heart rate, HRV, sleep/activity context as a multi-signal illness surface. Natarajan et al. report that respiration rate, heart rate, and HRV are wearable-measurable metrics that can provide early illness signs; in their COVID-19 dataset, respiration rate and heart rate were typically elevated by illness while HRV was decreased (npj Digital Medicine, 2020). Use converging evidence across respiratory/autonomic channels rather than a single metric trigger.
Keep symptom/check-in data as optional support rather than a required input. Quer et al. found that symptom plus wearable sensor data improved discrimination of COVID-positive versus COVID-negative symptomatic participants compared with symptoms alone (Nature Medicine, 2020). Subjective sick can raise confidence when objective evidence exists, but absence of symptoms should not suppress objective signals.
Use HRV/RHR as autonomic support signals, not standalone diagnosis. Hirten et al. found longitudinal Apple Watch HRV changes associated with SARS-CoV-2 infection and symptoms, including changes before PCR diagnosis; the authors note study limitations and the need for further work (JMIR, 2021). HRV/RHR should contribute to confidence only as support signals unless existing illness_signature is present.
Keep same-day acute evidence separate from the existing 7-day alert smoothing. Gadaleta et al. show that passive wearable models can detect COVID-19 in symptomatic and asymptomatic or pre-symptomatic settings, including models that adapt to missing self-reported symptoms (npj Digital Medicine, 2021). Acute same-day evidence should be surfaced explicitly instead of being hidden by 7-day averaging.
Use sleep disruption only as a support signal. Cohen et al. studied sleep habits and experimentally induced common cold susceptibility (Arch Intern Med, 2009), and sleep/immune reviews describe bidirectional sleep-immune interactions (Pflugers Archiv, 2012). Sleep can support the interpretation but should not be a primary illness trigger in v0.
Use SpO2 cautiously and never infer clinical hypoxia from wearable data. FDA consumer guidance says pulse oximeter readings must be interpreted with signs and symptoms, only a health care provider can diagnose hypoxia, and accuracy can be affected by circulation, skin pigmentation, skin thickness, skin temperature, tobacco use, and nail polish. It also distinguishes medical-purpose pulse oximeters from general wellness products that are not evaluated for clinical decision-making (FDA Pulse Oximeter Basics). SpO2 should require cluster/drop/source context, non-diagnostic wording, and never high confidence from one low reading.

Product Benchmark

Oura and WHOOP are useful current product references for this feature, but they should be treated as UX and product-contract benchmarks, not as scientific validation by themselves. The implementation should borrow the conservative framing and personal-baseline pattern while keeping Health Dashboard's own auditable evidence model.

ProductRelevant behaviorDesign implication for Health Dashboard
Oura Symptom Radar Oura describes Symptom Radar as looking for body strain using average body temperature, respiratory rate, resting heart rate, HRV, and inactive time. It uses a three-level estimate: no signs, minor signs, and major signs. Oura also states that the ring is not a medical device and is not intended to diagnose, treat, cure, monitor, or prevent medical conditions or illnesses (Oura Member Care). Match the non-diagnostic "signs of strain" framing, expose contributing biometrics, and keep confidence levels coarse rather than over-precise.
WHOOP Health Monitor WHOOP Health Monitor surfaces HRV, respiratory rate, blood oxygen, skin temperature, and related vitals against a member's personalized normal range. WHOOP also supports shareable 30-day and 180-day health reports (WHOOP Support). Keep the output personal-baseline driven, show which metrics are outside normal range, and preserve aggregate/debug evidence suitable for MCP and admin review.
  • Do not copy proprietary scoring or claim equivalence with Oura/WHOOP.
  • Use them to validate user expectations: personal baselines, coarse confidence, explicit contributing metrics, and recovery/rest-oriented wording.
  • Health Dashboard should go further on auditability: every signal should expose method, baseline, status, and source summary when available.

Date-Aligned Input Contract

Same-day illness evidence must be computed from an explicit per-date input object. Do not infer acute evidence by comparing RawMetrics.SpO2[0], RawMetrics.Resp[0], and RawMetrics.RHR[0]; those slices are most-recent-first per metric and can lose date alignment when one channel is missing. 

type IllnessEvidenceInput struct {
    Date string
    RespiratoryRate *MetricEvidenceInput
    SpO2Average     *MetricEvidenceInput
    SpO2LowCluster  *SpO2ClusterEvidence
    RHR             *MetricEvidenceInput
    HRV             *MetricEvidenceInput
    SleepDisruption *MetricEvidenceInput
    SustainedHRLoad *MetricEvidenceInput
    WristTempDeviation *MetricEvidenceInput
    StressFlags []string
    SubjectiveCheckin *SubjectiveCheckinSummary
}
  • Storage owns date alignment for the evaluated briefing date.
  • Health-domain code owns scoring the already-aligned evidence object.
  • MCP must read the canonical object from the briefing/storage path and must not recompute illness logic independently.
  • For sleep-derived metrics, the evaluated date means the sleep session ending on that local date.
  • For daytime metrics, the evaluated date means the local calendar day.
  • Wrist temperature is an optional explanatory signal. It can support or explain illness_signature, but it is not required for respiratory/SpO2-based moderate suspicion.

Relationship to Existing Stress Flags

illness_suspicion must not become a second, contradictory illness model. It should be the broad evidence layer; existing stress_flags remain the narrow, high-confidence EnergyBank/verdict inputs.

  • illness_signature remains a high-confidence subtype: temp up + respiratory rate up + HRV down.
  • If illness_signature is present, illness_suspicion.confidence should be at least high and include that flag as a contributing signal.
  • Respiratory + SpO2 evidence can produce low or moderate suspicion without setting illness_signature.
  • EnergyBank verdict overrides remain driven by stress_flags only in the first PR; weak or moderate suspicion should not force rest.
  • The MCP tool should return both the broad suspicion object and any raw stress_flags so agents can explain why they differ.

Baseline and Evidence Policy

  • Prefer existing storage.PersonalBaseline(...) median/MAD-derived SD and channel floors for channels that already have baseline support.
  • Exclude the evaluated date from baseline windows to avoid diluting acute anomalies.
  • Represent unavailable or warmup channels explicitly as status="missing" or status="warmup"; do not silently treat them as normal.
  • Do not mix mean/stddev z-scores with median/MAD z-scores in the same output without labeling the method.
  • Each signal should carry metric, direction, value, baseline, z_score when available, method, status, and short evidence text.
  • Confidence should require convergence: a single mild metric should not exceed low; moderate requires at least two compatible objective signals or one strong objective signal plus subjective sick.

  • none: no objective signals.
  • low: one mild objective signal.
  • moderate: two compatible objective signals, or one strong objective signal plus subjective sick.

  • high must never come from a single SpO2 minimum, one isolated wearable reading, or multiple sub-signals from only one noisy channel.

SpO2 Source Policy

  • A single low wearable reading must not produce high confidence by itself.
  • Use low-reading count/cluster, daily average drop, and source context together.
  • Return source summaries when available: source name, count, minimum, average, and whether lows came from sleep window or daytime.
  • Repeated lows means at least the v0 threshold count of valid readings below the threshold on the evaluated date, from allowed sources, excluding impossible/invalid readings. The output must expose count, min, avg, and source summary.
  • Prefer not to hard-code one device as always authoritative; expose source evidence so downstream agents and UI can explain mixed-source cases.
  • High-confidence SpO2 contribution should require either repeated lows, agreement with respiratory-rate elevation, or a strong drop from personal baseline.
  • Allowed wording: "signals consistent with respiratory stress or illness, but this is not a diagnosis."
  • Disallowed wording: "you may have low oxygen", "you are likely sick", or any claim that a wearable reading diagnoses hypoxia or illness.
  • Document device limitations in MCP/tool descriptions: readings can be affected by circulation, skin pigmentation, skin thickness, skin temperature, tobacco use, nail polish, sensor fit, and consumer wellness devices may not be evaluated for clinical decision-making. This wording follows FDA pulse oximeter consumer guidance.

Evidence Sufficiency and Merge Gate

V0 is approved as an experimental, evidence-bound MCP/briefing field only. The literature and product benchmarks are sufficient for signal direction and UX framing, not for exact thresholds. Before merging the implementation PR, validate thresholds against this project's own data pipeline.

  • Run a retrospective 90-180 day false-positive sweep on anonymized Profile A and Profile B.
  • Report none, low, moderate, and high counts per profile.
  • Inspect the top 10 moderate/high days with signal breakdowns, without publishing raw health values.
  • Run known-day validation: acute-pattern day reaches moderate or high; nearby normal day stays none or low; Profile B normal day stays none or low; high-activity non-illness day does not reach moderate/high unless respiratory/SpO2 are also abnormal.
  • Run threshold sensitivity and ablation: respiratory thresholds, SpO2 average-drop thresholds, SpO2 cluster counts, SpO2-disabled, respiratory-disabled, and sustained-HR-load-disabled variants.
  • Run SpO2 coverage/source audit: valid readings per day, days with 0/1/2/3+ readings, source names, sleep-window versus daytime, min/avg distribution, and frequency of lows below 94% and 92% on normal days.
  • Confirm wording safety: no output strings should claim diagnosis, hypoxia, "you are sick", "you have low oxygen", or "likely sick".
  • Confirm default MCP output exposes aggregate evidence only, not raw timestamped readings.

Risks and Edge Cases

  • SpO2 wearable readings can be noisy; use cluster/count and source context rather than a single minimum alone.
  • Exercise, alcohol, altitude, poor sensor fit, or sleep apnea patterns can mimic illness signals; sustained HR load must include activity context in evidence text (normal, high, or unknown).
  • Consumer wearable SpO2 readings have device and physiology limitations; tool output must present them as evidence, not clinical conclusions.
  • Subjective symptoms are private and should not be stored or exposed beyond existing check-in semantics unless explicitly designed.
  • New response fields must be additive so mobile, MCP, and browser clients keep working.
  • Do not make EnergyBank automatically force rest from weak illness suspicion without a high-confidence threshold.
  • Duplicating calculations between storage, health, and MCP would create drift; MCP should call the canonical storage/health path only.

Rollback Plan

Keep all changes additive. If the new signal is noisy, remove or hide the UI/MCP tool surface while leaving the pure calculation tests in place for future tuning. No database migration is expected unless the approved scope adds persistent symptom labels or evidence snapshots.
