Implementation Plan: Readiness Sleep Architecture Features

Approval required before implementation

Task Summary

Implement the next Readiness redesign backlog item: §6.5: sleep-architecture features -> Recovery / Chronic. The hypothesis is that the current EWMA45 floor captures sleep level through efficiency, but not sleep architecture: wake after sleep onset (WASO), wake-bout fragmentation, and sleep continuity may explain future recovery_stability/rolling_3d and chronic_load/chronic_label outcomes.

Recommended Approach

Ship this as an evidence PR, not as a chip/model behavior change. Add segment-derived sleep architecture fields to feature_snapshots for Recovery and Chronic, and add a read-only feasibility probe with predeclared metrics. Do not change target_snapshots, naive_baselines, chip thresholds, Telegram copy, or dashboard verdicts in this PR.

Primary decision point: Recovery rolling_3d. Chronic chronic_label remains secondary/exploratory because it has fewer events and noisier tenant-level precision. Rationale: prior Phase 1 attempts closed on naive baselines. A new feature class needs evidence before replacing the production floor. This also keeps rollback simple: feature payloads can be overwritten by feature-version rollback without changing user-facing behavior.

Current Behavior

  • internal/storage/recovery_stability_writer.go reads sleep from daily_scores only.
  • Recovery targets are future labels: daily_point = night t+1, rolling_3d = mean(t+1..t+3).
  • Recovery features currently include previous efficiency, 7-day mean, EWMA45, EWMA180, sleep debt, and eligible counts.
  • internal/storage/chronic_load_writer.go consumes Recovery rolling_3d outputs for chronic_label.
  • Existing segment helpers already parse and merge sleep segments in wake_time_for_date.go and sri.go, but they are shaped for wake time / SRI, not per-date architecture features.
  • Live DB check on 2026-05-26: last 90 days have segment data on both tenants, but source/stage double-counting makes raw sums unsafe without the existing winning-source logic.

Desired Behavior

  • For each feature date t, compute architecture only from sleep segments available by end of day t.
  • Persist Recovery feature payload version 2 with new trailing-window fields such as waso_hours_7d, explicit_wake_bouts_7d, gap_inferred_wake_bouts_7d, fragmentation_index_7d, and coverage/confidence counters.
  • Persist Chronic feature payload version 2 with 7-day and 14-day sleep architecture summaries before t; Chronic labels still use the existing future Recovery window.
  • Add a read-only feasibility command/report that compares architecture-augmented probes against the existing floors.
  • Keep production baselines and chip behavior unchanged unless the probe passes the predeclared stop rule and the operator approves a follow-up PR.

Predeclared Metrics and Stop Rule

Recovery rolling_3d

Compare an architecture-augmented linear probe against EWMA45 on recovery_stability/rolling_3d. Primary metric: MAE on the same leakage-safe split convention used in the readiness plan. Secondary: directional hit rate for below-baseline deterioration. Pass rule: pooled MAE improves by at least 3% versus EWMA45, and no tenant regresses by more than 1% MAE.

Chronic label

Compare an architecture-augmented classifier against event_base_rate on chronic_load/chronic_label. Primary metric: precision at the existing operating point (R=0.5). Secondary: AUC and top-k precision. Promotion rule: precision@R=0.5 improves by at least +5pp with no worse top-k precision. Otherwise Chronic remains exploratory even if Recovery passes.

Stop Rule

Any inconclusive, mixed, or below-threshold result stops after the read-only feature/probe PR. Do not tune thresholds, swap models, or ship user-facing behavior changes from weak evidence.

Implementation Steps

  1. Create a fresh feature branch from origin/main for implementation after this plan is approved.
  2. Add a focused sleep architecture calculator that uses one winning source per night and segment rows only.
  3. Compute daily architecture fields: asleep duration, WASO hours, explicit wake-bout count, gap-inferred wake-bout count, longest wake bout, fragmentation index, source, confidence, and coverage reason.
  4. Add rolling summary helpers for [t-6,t], [t-13,t], and optional [t-44,t] windows with explicit eligible counts.
  5. Extend Recovery feature snapshots to version 2; keep target and baseline formula versions unchanged.
  6. Extend Chronic feature snapshots to version 2 using only data at or before t.
  7. Add the read-only feasibility probe in the same PR and run it on both health and health_mariia.
  8. Update the plan with measured results and a recommendation: stop, collect more data, or open a separate behavior-changing PR.

Feature Payload Contract

  • Explicit wake and inferred gaps are separate: explicit_wake_bouts_* comes only from sleep_awake; gap_inferred_wake_bouts_* comes only from gaps between asleep segments.
  • Each architecture window carries first-class quality fields: architecture_eligible_days_*, architecture_source_days_*, architecture_missing_reason_counts_*, and architecture_confidence_*.
  • Low-confidence or coarse-only nights should not emit zero-valued architecture metrics that a probe could misread as healthy sleep.
  • Feature payloads must identify whether architecture metrics are explicit, inferred, mixed, or unavailable.

Leakage Contract

  • Feature row for date t may use only sleep segments whose end timestamp is at or before end of tenant-local day t.
  • Recovery labels may look at t+1..t+3; Chronic labels may look at t+1..t+14; feature builders must never read those forward windows.
  • Tests must prove that adding sleep segments on t+1 does not change Recovery features for t.
  • Tests must prove that adding Recovery/segment data inside t+1..t+14 does not change Chronic features for t.
  • Probe input building must ignore or reject any feature whose availability date is after the row date.

Data and API Impact

  • No schema migration expected; feature_snapshots.features is JSONB and designed for feature-version bumps.
  • No user-facing API contract changes expected in this PR.
  • No Telegram, dashboard chip, or readiness score copy changes expected.
  • Backfill will overwrite Recovery and Chronic feature_snapshots with higher feature_version; target and baseline rows should remain semantically identical.
  • Probe command is read-only against production data unless explicitly run alongside a backfill.

Risks and Edge Cases

  • Double-counting sleep stages across sources or overlapping stage rows would fabricate WASO/fragmentation. The calculator must pick one source before deriving features.
  • sleep_awake may be absent for true zero-awake Apple Watch nights; absence must not be treated as evidence of zero WASO unless staged rows cover the main sleep.
  • Coarse-only sources can provide sleep_unspecified but not architecture. They should produce explicit coverage reasons, not zero-valued architecture features.
  • Same-window leakage is the main failure mode: Chronic features for t must not inspect t+1..t+14, even though the label does.
  • Small tenant sample sizes may make the feasibility result inconclusive. In that case, stop and leave the feature payload available for future accumulation.

Manual QA Checklist

  • Open admin monitoring after backfill and verify Recovery/Chronic coverage did not regress.
  • Inspect several feature payloads for both tenants: fields are present, counts are plausible, and coverage reasons are explicit.
  • Check deploy logs for startup backfill errors and slow query spikes.
  • Confirm UI chip behavior is unchanged after deploy.

Rollback Plan

Revert the code commit and redeploy. If feature rows were backfilled, rerun the previous main build's readiness backfill to overwrite feature_snapshots back to version 1. Because this plan does not change target or baseline semantics, no destructive data migration should be required.
