Implementation Plan: Issue #182 DB-Backed Integration Tests

Approval required before implementation

Task Summary

Stabilize the opt-in Postgres-backed Go tests for internal/storage and internal/ui so they create complete throwaway schemas, fail fast on setup problems, and do not run unrelated long backfill work inside validation-focused tests.

Current Behavior

  • internal/storage has a shared testDB helper in recovery_stability_writer_integration_test.go. It creates a throwaway schema, calls EnsureAllTables, EnsureIndexes, EnsureReadinessRedesignTables, then verifies readiness schema health.
  • internal/ui has a similar testTenantDB helper in admin_readiness_redesign_config_test.go. It creates a throwaway schema and readiness redesign tables, but does not currently create subjective_checkins.
  • TestAdminCheckinCoverage_JSONShape seeds check-in rows through SaveCheckinPrompted and fails on a fresh UI test schema with ERROR: relation "subjective_checkins" does not exist.
  • TestFragmentAdminReadinessMonitoring_Renders seeds a single current-day target row and expects the phrase inputs stable through. With the current monitoring window shape, the fragment can correctly render critical: no stable input in monitoring lookback instead, making the assertion brittle.
  • TestOnboardingWizard_RejectsSchemaAll tests schema validation for every onboarding fragment, but the missing-schema subtest for step-4-run POST calls the real one-year readiness backfill chain. On real Postgres this timed out after 90s inside BackfillAcuteRiskSnapshots.
  • TestVerifyReadinessRedesignSchema_DetectsReasonColumnDrift now passes on real Postgres in the observed run, but each subtest takes about 7-9 seconds because it creates and mutates a fresh schema.

Observed Verification Notes

  • Running DB tests without network permission can be misleading: the DB helpers skip after connect: operation not permitted, producing a green result that did not exercise the database.
  • With real Postgres access, go test ./internal/storage -run "TestVerifyReadinessRedesignSchema_DetectsReasonColumnDrift" -count=1 -timeout=90s -v passed in about 23.6s.
  • With real Postgres access, go test ./internal/ui -run "TestAdminCheckinCoverage_JSONShape|TestOnboardingWizard_RejectsSchemaAll|TestFragmentAdminReadinessMonitoring_Renders" -count=1 -timeout=90s -v reproduced the missing table failure, the brittle fragment assertion, and the onboarding timeout.
  • go test ./... inside the sandbox also fails in internal/notify because httptest.NewServer cannot bind a local port under current sandbox permissions. That is separate from issue #182.

Desired Behavior

  • DB-backed tests create every table their exercised code paths require, including newer startup-created tables such as subjective_checkins.
  • Tests whose purpose is request validation do not run slow product backfills as incidental side effects.
  • Monitoring fragment tests assert stable user-facing contract markers without depending on a data shape that contradicts the seeded fixture.
  • DB tests remain opt-in through READINESS_TEST_DSN or libpq env vars and continue to skip on machines without configured Postgres.
  • Failures should be specific and fast enough to identify the broken contract within a 90-120s package timeout.

Assumptions And Unknowns

  • Assumption: the intent is to stabilize the existing opt-in test suite, not to make CI require a live database.
  • Assumption: production startup still owns auto-created auxiliary tables; the test helpers should mirror startup setup for the tables they need.
  • Assumption: the onboarding validation test should prove schema=all rejection and missing-schema fallback without executing a full historical backfill.
  • Unknown: whether to introduce a shared exported test setup helper in internal/storage or keep package-local helpers to avoid test-only API surface.
  • Unknown: whether the slow storage drift test should be optimized now or only left with clearer timeout coverage, since it currently passes.

  • internal/ui/onboarding_handlers_test.go - split schema validation from expensive run paths, or provide a handler/test seam that validates scope without running the real one-year backfill.
  • internal/ui/admin_readiness_redesign_monitoring_test.go - make the seeded fixture and assertions agree. Either seed enough stable rows to expect inputs stable through, or assert the current no-stable-input message as the correct output for a sparse fixture.

Implementation Steps

  1. Update the UI DB test setup helper to mirror required startup-created tables. Start with db.EnsureSubjectiveCheckinsTable(), then rerun the targeted UI tests to reveal any next missing table.
  2. Refactor TestOnboardingWizard_RejectsSchemaAll so validation coverage does not execute heavy backfills. Prefer separate cases: read-only handlers can still call real handlers; mutating run handlers should test schema=all rejection directly and test missing-schema fallback through a lightweight seam or a narrower helper.
  3. Adjust the monitoring fragment test. If the contract requires displaying stable input text, seed a full enough monitoring window to make that text true. If the sparse fixture is intentional, update the assertion to require critical: no stable input in monitoring lookback instead.
  4. Rerun the targeted UI test command against real Postgres with a 90s timeout. Confirm failures are gone and no new setup gaps appear.
  5. Rerun go test ./internal/storage ./internal/ui -count=1 -timeout=120s against real Postgres.
  6. Run the default suite without DB env to confirm opt-in behavior remains fast and green, using sandbox-compatible GOCACHE. If local port binding remains blocked for internal/notify, record it separately rather than treating it as a #182 regression.
  7. Update this HTML plan with implementation results, checks run, limitations, and follow-up recommendations.

Manual QA Checklist

  • Confirm DB-backed tests create and drop only schemas named with the test prefixes such as ui_test_* and rs_test_*.
  • Confirm no production tenant schema is modified during test setup or teardown.
  • Confirm schema=all onboarding requests still return HTTP 400 for read-only and mutating fragments.
  • Confirm missing schema still falls back to the request tenant for lightweight paths without requiring a full backfill run in the validation test.

Risks And Edge Cases

  • Adding every startup helper to test setup could mask missing-table regressions if production startup forgets to call the same helper. Keep setup explicit and tied to tested behavior.
  • Mocking or stubbing onboarding writers too broadly could stop testing the real handler wiring. Keep at least one focused integration test for actual run behavior if one does not already exist elsewhere.
  • Monitoring output depends on time windows and tenant-local dates. Tests should use helpers such as daysAgoUTC and seed data that matches the expected monitoring window.
  • DB tests can look green when sandbox network blocks Postgres and helpers skip. Verification must distinguish skipped tests from executed tests.
  • Long-running tests can leave throwaway schemas behind if interrupted before cleanup. Check and clean only test-prefixed schemas if needed.

Rollback Plan

Revert the test helper and test assertion changes. Because no production code or schema migration is planned, rollback should be limited to test files and this plan update. If interrupted test runs leave throwaway schemas, drop only schemas with the exact test prefixes created by these helpers.

Open Questions

  • Should EnsureAllTables eventually include auxiliary tables like subjective_checkins, or should startup-only helpers remain separate and explicitly called by tests?
  • Should the readiness schema drift test be optimized now, or is a 23s targeted runtime acceptable for an opt-in DB test?

Known Limitations And Follow-Up

  • The reproduced issue-specific UI failures are fixed by targeted verification.
  • The storage suite still has many tests that create their own throwaway schema. Even with smaller pools, this is not a good fast dev-loop shape over remote Postgres.
  • A separate follow-up should redesign the DB integration harness around fewer schema creations, shared package-level fixtures with explicit table resets, or narrower helper variants per table family. That is larger than the targeted #182 fixes above.
