Implementation Plan: Issue #166 Readiness Serving/Freshness Contract

Approved and implemented

Task Summary

Define and implement the stable readiness freshness/confidence contract that dashboard, iOS, MCP, and later confidence UI can consume without duplicating backend logic. This issue is broader than the already-executed 2026-05-28-readiness-serving-freshness-closure.html plan: that plan closed bounded restamp/backfill wiring, while this one should formalize the API shape and consumer semantics.

Current Behavior

  • internal/health/types.go already exposes readiness_confidence, readiness_cap_reason, readiness_components, and per-component freshness, confidence, sample_count, and missing_reason on BriefingResponse.
  • internal/storage/briefing.go builds date-aligned readiness evidence from daily cache plus same-day raw metric fallback, including missing and stale states.
  • /api/health-briefing returns the full BriefingResponse; /api/readiness-history returns score and band only.
  • internal/mcpserver/tools.go has get_health_briefing and get_readiness_history, but tool descriptions still describe the older readiness formula and do not call out freshness/confidence metadata.
  • Dashboard page rendering currently reads confidence and cap reason into the page data, but confidence UI is intentionally not the goal of this issue.

Desired Behavior

  • One documented server-owned readiness state vocabulary: fresh, stale, missing, data-accruing, low-coverage, and capped/provisional states.
  • API consumers can decide display state from response fields only; no client should infer freshness from dates or recompute coverage.
  • Existing score values remain behavior-compatible unless tests expose a mismatch between score and metadata.
  • Dashboard and MCP continue to work, with richer metadata available and documented for future confidence UI.

Assumptions And Unknowns

  • Assumption: the primary contract should be attached to /api/health-briefing first because it already owns BriefingResponse.
  • Assumption: /api/readiness-history should stay lightweight unless the confidence UI needs historical confidence states.
  • Unknown: whether data_accruing should be represented as a new readiness freshness enum or mapped through confidence=provisional plus reason.
  • Unknown: whether MCP needs a separate concise readiness contract tool or simply better descriptions for existing tools.

Files Likely To Change

  • internal/health/types.go - add or tighten response structs/enums only if the current fields cannot express the contract cleanly.
  • internal/storage/briefing.go - normalize evidence mapping and reasons if stale/missing/low-coverage cases are inconsistent.
  • internal/storage/readiness_evidence_test.go or related tests - cover fresh, stale, missing, low-coverage, and data-accruing/provisional cases.
  • internal/ui/handler.go and UI tests - only if response wrapping or dashboard API shape needs explicit metadata preservation.
  • internal/mcpserver/tools.go - update readiness tool descriptions and, if approved, expose concise contract metadata.
  • README.md, docs/ARCHITECTURE.md, or a small new API doc - document the contract for dashboard and MCP/debug consumers.

Implementation Steps

  1. Write a short contract table before code edits: fields, allowed values, producer, and intended consumer behavior.
  2. Audit current readiness evidence outputs against that table for fresh, stale, missing same-day value, low HRV sample count, missing sleep-stage details, and illness/stress cap scenarios.
  3. Add focused tests for the current mapping. Prefer tests around pure or near-pure evidence builders before touching handlers.
  4. If the current fields cannot express data_accruing cleanly, add a small explicit reason/status field rather than changing existing score semantics.
  5. Update MCP descriptions and docs so the contract is discoverable.
  6. Run focused tests first, then full Go test/vet before PR.

Impact

  • API: additive metadata only; no removal or rename of existing JSON fields.
  • Data/migration: no schema migration expected.
  • Auth/permissions: no change.
  • UX: no new confidence UI in this issue; it prepares that work.
  • Deployment: normal app deploy after tests if code changes are needed.

  • go test ./internal/ui ./internal/mcpserver -count=1 if handlers or MCP descriptions are touched.
  • go test ./...

  • Optional direct DB smoke with ~/.health-db: inspect one current /api/health-briefing-equivalent row and confirm metadata matches actual same-day availability.

Risks And Edge Cases

  • Changing numeric readiness behavior under a metadata issue would blur scope; keep score changes out unless a contract test reveals a bug.
  • Adding too many enums could make client logic harder; prefer a small stable vocabulary plus reason strings.
  • Historical readiness points may not have enough evidence to expose detailed metadata without extra queries.

Rollback Plan

Revert additive metadata and documentation changes. No database rollback should be required. Existing consumers should continue to work throughout because the plan avoids removing current fields.

Open Questions

  • Should /api/readiness-history gain historical confidence metadata now, or should that wait for the confidence UI issue?
  • Should data_accruing be a freshness enum, a cap reason, or a separate serving state?
  • Which doc should be canonical for API consumers: README, architecture doc, or a dedicated API contract section?

Implementation Result

Implemented on 2026-06-06. The change is additive: existing readiness_confidence, readiness_cap_reason, and readiness_components fields remain in place, and clients can now prefer the grouped readiness_serving object.

  • Added ReadinessServingState with status, confidence, reason, and component evidence.
  • Added serving status values: fresh, missing, stale, data_accruing, low_coverage, and capped.
  • Kept readiness score behavior unchanged; the new object summarizes existing evidence/cap metadata for consumers.
  • Kept serving state synchronized when coherence or illness safety caps update readiness metadata after initial scoring.
  • Updated MCP descriptions and README documentation so consumers know to use readiness_serving instead of guessing.
  • Added tests for missing evidence priority, sparse-HRV data-accruing status, illness cap status, low-coverage status, and ComputeBriefing response exposure.
