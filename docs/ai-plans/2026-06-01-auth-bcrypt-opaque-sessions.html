Implementation Plan: Bcrypt Passwords and Opaque Sessions

Issue #156 Approval required before implementation

Task Summary

Harden Health Dashboard web authentication by replacing unsalted SHA-256 password storage and reusable password-hash cookies with bcrypt password hashes and server-side opaque sessions.

The intended PR should close #156 Harden authentication with bcrypt passwords and opaque sessions.

Inspected Current Behavior

Password Storage

internal/registry/registry.go stores health_registry.users.password_hash as hex(sha256(password)). CreateUser, MigrateFromEnv, and HashPassword all use that format.

Login Cookies

internal/ui/handler.go sets auth=username|sha256hash in multi-user mode and auth=sha256hash in single-user env mode. Guard validates cookies by comparing the hash against the stored password hash.

ForwardAuth

Trusted Authentik ForwardAuth requests currently issue the same local auth cookie so sessions survive Authentik token expiry. In multi-user mode this leaks the stored password hash into the browser cookie.

Schema

EnsureSchema auto-creates health_registry.users. There is no sessions table today. Existing startup DDL already uses additive CREATE TABLE IF NOT EXISTS / ALTER TABLE IF NOT EXISTS style.

Desired Behavior

  • New and changed passwords are stored as bcrypt hashes, with no plaintext persistence and no reusable password hash in cookies.
  • Legacy SHA-256 password hashes continue to authenticate once, then rehash to bcrypt after a successful password login.
  • Browser sessions use random opaque session IDs stored server-side with explicit expiry.
  • Add an explicit logout route that invalidates the server-side session and expires the cookie. Current inspected routes only register /login and /setup; logout is new work, not an existing hook.
  • ForwardAuth keeps the current UX, but creates or refreshes an opaque local session instead of writing the password hash to a cookie.
  • Existing legacy username|hash and bare-hash cookies become invalid after deployment, forcing a one-time login or ForwardAuth refresh.
  • Single-user env-based installation remains a supported installation mode, not a deprecated emergency path.
  • Existing X-API-Key access to guarded dashboard/API routes is a separate bearer-auth surface. This PR should not expand it; either preserve it deliberately with tests or split restriction into a follow-up issue if breaking clients is possible.

Assumptions and Decisions

  • Use golang.org/x/crypto/bcrypt; because CI runs -mod=vendor, implementation must update go.mod, go.sum, and vendor/.
  • Use bcrypt cost 12 by default, but keep it as a package constant so it can be adjusted if local tests show unacceptable latency.
  • Generate session tokens from at least 32 bytes of crypto/rand. Store session tokens as SHA-256 digests, not raw token values, so a database leak does not immediately reveal live cookie values.
  • Cookie name can remain auth for compatibility with existing request paths, but the value becomes a random token.
  • All auth cookies should remain HttpOnly and SameSite=Lax. Add a central cookie helper that sets Secure when the request is HTTPS or carries X-Forwarded-Proto: https, while still allowing plain localhost development.
  • Session expiry should remain 30 days to preserve current user experience unless we decide otherwise before implementation.
  • Single-user env mode should use opaque sessions too. If health_registry is unavailable, store session state in the existing tenant schema instead of treating the mode as less secure.

Files Likely to Change

  • internal/registry/registry.go - password hashing helpers, legacy-hash detection, bcrypt verification, rehash update, multi-user session table DDL and session CRUD.
  • internal/storage/* - single-user session table DDL and CRUD in the tenant schema when registry is not available.
  • internal/registry/*_test.go - bcrypt verification, legacy SHA-256 migration, session creation/expiry/deletion tests.
  • internal/ui/handler.go - login, setup auto-login, ForwardAuth local session issuance, guard cookie validation, new logout route, cookie security helper, and API-key behavior tests/documentation.
  • internal/ui/*_test.go - handler-level cookie/session behavior where practical without external DB dependencies.
  • cmd/server/main.go - env seeding should pass plaintext UI_PASSWORD to a bcrypt-aware registry path instead of pre-hashing it before MigrateFromEnv.
  • README.md - deployment note: existing users will need a one-time login after the cookie format changes; password hashes are upgraded on login.
  • go.mod, go.sum, vendor/ - add vendored bcrypt dependency.

Proposed Implementation Steps

  1. Add password helper functions in internal/registry: HashPasswordBcrypt, VerifyPassword, IsLegacySHA256Hash, and UpdatePasswordHash.
  2. Change CreateUser and setup/admin user creation to store bcrypt hashes for new users.
  3. Change the env-seeding contract deliberately: cmd/server/main.go should stop pre-hashing UI_PASSWORD. Add a bcrypt-aware MigrateFromEnv replacement or overload that receives plaintext, stores bcrypt for fresh env-seeded admins, and leaves existing legacy SHA-256 rows untouched until a successful password login proves the plaintext.
  4. Add health_registry.sessions with id_hash TEXT PRIMARY KEY, username TEXT REFERENCES users(username) ON DELETE CASCADE, created_at, expires_at, and optional last_seen_at.
  5. Add an equivalent single-user session store in the active tenant schema, for example auth_sessions with id_hash, created_at, and expires_at. It does not need username because the env-mode tenant is singular.
  6. Add registry session CRUD: create random token, store digest, resolve token to user if unexpired, delete token on logout, and opportunistically prune expired sessions.
  7. Update both multi-user and single-user guard paths to resolve auth as an opaque token. Old username|hash and bare SHA-256 cookies should fail closed and redirect to /login.
  8. Update password login: verify bcrypt or legacy SHA-256, rehash legacy on success, create a session, set cookie to the raw random token.
  9. Update setup auto-login to create a session only after user creation succeeds. Admin-created users should not mint sessions because the admin API returns JSON for a different account.
  10. Update ForwardAuth local-cookie issuance to create a session for the resolved registry user instead of copying PasswordHash. Do not return early just because some auth cookie exists; overwrite invalid, expired, or legacy-format cookies after trusted ForwardAuth resolves the user.
  11. Add /logout as a POST-preferred route that deletes the current server-side session and expires the browser cookie. If a GET link is needed for existing navigation constraints, keep it idempotent and CSRF-low-risk by only deleting the current session.
  12. Leave X-API-Key behavior unchanged in this PR unless implementation inspection shows a safe narrow restriction. Add explicit tests or documentation so this bearer-auth surface is not accidentally confused with browser sessions.
  13. Document the one-time relogin and the legacy rehash behavior in README.

Auth, Migration, and UX Impact

  • Auth: Password hashes are no longer bearer-equivalent session credentials. Cookie theft remains a session risk, but DB password-hash theft no longer becomes browser login.
  • Migration: Existing health_registry.users.password_hash rows can remain as SHA-256 until each user logs in successfully. Env-mode UI_PASSWORD does not persist a password hash, so it can verify directly against the current environment value and then issue an opaque session. Bcrypt hashes are self-identifying via the $2a$/$2b$/$2y$ prefix.
  • UX: Existing local sessions will be invalidated once. ForwardAuth users should be silently re-sessioned on the next trusted proxied request.
  • Deployment: Startup DDL adds one registry table in multi-user mode and one tenant-local session table in single-user mode. No destructive migration is planned. Rollback leaves the new sessions tables unused.
  • API key scope: The current UI guard accepts X-API-Key as an alternate bearer credential. This plan treats that as pre-existing behavior and not as part of session hardening unless explicitly expanded before implementation.
  • Security boundary: Do not log raw session tokens, bcrypt hashes, plaintext passwords, or full cookie values.

Manual QA Checklist

  • Fresh setup wizard creates an admin user, sets an opaque cookie, and opens the dashboard.
  • Single-user env install with only UI_PASSWORD logs in, writes an opaque server-side session, and accepts the session on the next request.
  • Existing username/password user with SHA-256 hash can log in once and is rehashed to bcrypt.
  • Old username|hash cookie redirects to login instead of authenticating.
  • Old bare SHA-256 single-user cookie redirects to login instead of authenticating.
  • Logout expires the browser cookie and deletes the corresponding server-side session.
  • Trusted ForwardAuth request for username/email creates an opaque local session and reaches the dashboard, including when the request arrives with a stale legacy auth cookie.
  • Untrusted ForwardAuth headers are still ignored by the existing CIDR/flag guard.
  • Admin user creation stores bcrypt hashes, does not return or set a session token for the created user, and the created user can log in normally.

Risks and Edge Cases

  • Dependency risk: Adding bcrypt requires vendoring golang.org/x/crypto. If vendoring fails in the local sandbox, the PR cannot be completed without network access or an approved dependency update path.
  • Single-user mode: This mode is supported and must not remain on reusable hash cookies. The tenant-local session table must be created in the same startup path as other single-tenant tables.
  • ForwardAuth lookup: Username and email paths must create sessions for the actual registry username, not the raw header value when email matching is used.
  • Stale cookies: Trusted ForwardAuth must replace invalid legacy cookies. Otherwise users behind Authentik could repeatedly depend on headers and lose the local-session benefit after Authentik expiry.
  • Session cleanup: Expired sessions should not grow without bound. A lightweight delete on create/resolve is enough for this PR.
  • API-key auth: Keeping current X-API-Key access avoids breaking machine clients but leaves a broad bearer-auth path. Restricting it is a separate risk-managed change unless explicitly approved for this PR.
  • Clock behavior: Session expiry uses server time. Tests should avoid brittle exact timestamps.
  • Rollback: If rolled back after users are rehashed to bcrypt, older code that expects SHA-256 will not be able to verify those passwords. See rollback plan.

Rollback Plan

Code rollback is straightforward for the session tables because they are additive and can remain unused. Password-hash rollback is not fully transparent once multi-user accounts have been rehashed to bcrypt: the previous code cannot validate bcrypt hashes. Single-user env mode can still fall back to UI_PASSWORD after rollback. If emergency rollback is needed after deployment, either restore the new auth code quickly or manually reset affected multi-user passwords through a controlled admin/SQL path. For this reason, deploy should include a smoke test immediately after merge.

Open Questions

  • Should session expiry remain 30 days exactly, or should we shorten it while touching the session model?
  • Do we want a visible admin/settings note about active sessions now, or keep session management internal for this PR?

Implementation Update

Implemented after approval on 2026-06-01.

  • Added bcrypt password hashing with legacy SHA-256 verification and rehash-on-login support.
  • Pinned golang.org/x/crypto to the currently latest verified release, v0.52.0, with refreshed vendored dependencies.
  • Added health_registry.sessions for multi-user opaque browser sessions.
  • Added tenant-local auth_sessions for supported single-user env installs.
  • Changed browser auth cookies to opaque random tokens; old hash-shaped cookies no longer authenticate.
  • Preserved X-API-Key auth behavior for mobile sync, MCP, and existing machine clients.
  • Updated trusted ForwardAuth handling to issue/replace local opaque sessions instead of copying password hashes.
  • Added /logout to delete the current server-side session and expire the browser cookie.
  • Added README notes for bcrypt, opaque sessions, one-time relogin, and single-user session support.

Known Limitations

  • Session management remains internal; there is no admin UI for listing or revoking all active sessions.
  • X-API-Key remains a broad bearer credential by design in this PR. Narrowing dashboard API-key access should be a separate compatibility decision.
  • Rollback after multi-user accounts rehash to bcrypt still requires either restoring this auth code or resetting affected passwords.
