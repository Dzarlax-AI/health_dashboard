Implementation Plan: Startup DDL Noise Reduction

Approval required before implementation

Task Summary

Reduce noisy production startup logs from idempotent schema/index checks such as ALTER TABLE ... ADD COLUMN IF NOT EXISTS and CREATE INDEX IF NOT EXISTS when the schema is already current.

The goal is not to hide real migration failures. The goal is to avoid taking heavy DDL locks on every restart when catalog metadata already proves the column or index exists.

Observed Production Evidence

  • After deploy, the container started and served traffic, but logged multiple context deadline exceeded lines from EnsureIndexes.
  • Follow-up catalog checks confirmed all logged columns and indexes already exist in both health and health_mariia.
  • pg_stat_activity showed a long-running diagnostic psql query touching metric_points. That query could hold an AccessShare lock, while ALTER TABLE needs AccessExclusive.
  • internal/storage/indexes.go currently uses one shared longCtx() for all migrations and index checks, so after one blocked DDL waits until deadline, later statements inherit the canceled context and log immediately.

Current Behavior

Startup Path

cmd/server/main.go calls db.EnsureIndexes() for each tenant during startup and when a tenant is created.

EnsureIndexes

internal/storage/indexes.go always executes every listed ALTER TABLE ... IF NOT EXISTS and every CREATE INDEX IF NOT EXISTS.

Timeout Shape

All statements share the same 5-minute longCtx(). One lock wait can consume the whole context and turn the remaining statements into follow-on noise.

Fresh Installs

EnsureAllTables() already creates many current columns for new tenants, but EnsureIndexes() still carries older compatibility migrations.

Desired Behavior

  • If a required column already exists, skip its ALTER TABLE entirely.
  • If a required index already exists, skip its CREATE INDEX entirely.
  • If a column or index is missing, still create it automatically.
  • Use a fresh context per DDL statement so one lock wait does not poison the rest of startup.
  • Use a bounded PostgreSQL lock_timeout around startup DDL so blocked migrations fail fast with a clear log instead of holding startup for minutes.
  • Keep real missing-schema failures visible and actionable.

Files Likely to Change

  • internal/storage/indexes.go - replace unconditional DDL loops with catalog-aware column/index checks and per-statement contexts.
  • internal/storage/indexes_test.go - add unit tests for skip-vs-create decision logic, likely via small pure helper functions instead of requiring a live Postgres instance.
  • docs/ai-plans/2026-05-28-startup-ddl-noise-reduction.html - update with implementation results and verification.

Proposed Implementation

  1. Introduce small metadata structs for required columns and indexes in indexes.go.
  2. Add helpers that query information_schema.columns and pg_indexes under the tenant's current search_path.
  3. For each migration, run columnExists(table, column); execute ALTER TABLE only when missing.
  4. For each index, run indexExists(indexName); execute CREATE INDEX only when missing.
  5. Wrap each DDL execution in its own context and transaction with local lock_timeout, for example SET LOCAL lock_timeout = '5s', then execute the DDL.
  6. Log skipped checks at most in a low-noise aggregate line, or do not log skips at all. Log missing-and-created and failed-created paths with the table/index name.
  7. Keep EnsureIndexes() best-effort for startup compatibility, matching current behavior, but make failures more specific.

Data and Deployment Impact

  • No data model change is proposed. This changes how existing migrations are checked and applied.
  • Fresh installs and newly created tenants still get automatic columns and indexes.
  • Existing production tenants should skip most DDL on startup after catalog checks.
  • If a real migration is missing but blocked by active traffic, startup should continue with a concise warning rather than a cascade of timeout logs.

Risks and Edge Cases

  • Catalog checks must respect tenant search_path; hardcoding health would break health_mariia and future tenants.
  • Index names are schema-local in Postgres, so checks should include the current schema or use to_regclass safely under search_path.
  • Skipping DDL based on name alone could miss a wrong index definition. For this pass, index-name existence likely matches current IF NOT EXISTS semantics, which also does not validate index definition.
  • A very short lock_timeout can defer a genuinely needed migration until the next restart. This is acceptable only because startup currently treats these checks as best-effort and logs failures instead of aborting.

Rollback Plan

Revert the PR. The old startup behavior is noisy but known to continue booting when DDL times out. No data rollback is needed because the change only gates whether existing idempotent DDL statements are attempted.

Implementation Result

  • internal/storage/indexes.go now models startup column migrations and expression indexes as metadata with table/column or index names.
  • EnsureIndexes() performs tenant-scoped catalog checks via current_schema() and skips DDL that is already present in the current tenant schema.
  • Column DDL that is genuinely missing still runs with a 15-second context and transaction-local lock_timeout=5s.
  • Index DDL keeps a longer 5-minute statement context so a legitimate missing expression index can build on a large existing table after it acquires the lock.
  • If catalog checks fail, the old best-effort behavior remains as a fallback: the idempotent DDL list is attempted and failures are logged.
  • internal/storage/indexes_test.go adds focused tests for the skip-vs-create decision logic.
