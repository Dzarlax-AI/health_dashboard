Issue #157: Confidence and Uncertainty Indicators

Plan to add dashboard UI for readiness freshness, coverage, and confidence using the server-owned readiness_serving contract delivered by issue #166 / PR #177.

Date: 2026-06-26 Status: implemented and verified Scope: dashboard UI + tests No production code changed by this plan

Task Summary

The dashboard should make it clear when the readiness score is fresh, still accruing data, stale, missing core inputs, low coverage, or adjusted by a safety cap. Users should not have to infer whether a quiet score means "all OK" or "not enough reliable data yet".

The implementation must not invent presentation-only heuristics. It should render the canonical ReadinessServingState object already exposed by /api/health-briefing.

Current Behavior

  • internal/health/types.go defines ReadinessServingState with status, confidence, reason, and component summaries.
  • internal/health/readiness.go maps evidence into fresh, missing, stale, data_accruing, low_coverage, and capped.
  • internal/health/readiness_evidence_test.go already pins the backend serving contract, including data-accruing, low-coverage, missing, and capped cases.
  • internal/ui/handler.go passes only legacy top-level fields to the dashboard: ReadinessConfidence, ReadinessCapReason, and ReadinessRawScore.
  • internal/ui/templates/pages/dashboard.html renders a coarse note only when confidence is not final. It does not distinguish all serving states or show a positive fresh/covered state.
  • The template already has suitable UI patterns nearby: methodology badges and compact stress-flag chips.

Desired Behavior

  • Show a compact readiness trust badge near the existing methodology badge in the hero score block.
  • Render all server statuses in human language: fresh, missing, stale, still settling, low coverage, and adjusted.
  • Show a subtle positive state when data is fresh and confidence is final, for example "Fresh data" or "Full confidence".
  • Use tooltips or accessible titles to explain low-confidence reasons without leaking implementation details such as enum names.
  • Dim the score area only when confidence is genuinely low or the status is missing, stale, or low coverage. Provisional/accruing and capped states should be visible but not visually treated as broken.
  • Keep copy concise and non-technical across English, Russian, and Serbian localizations.
  • Preserve existing score thresholds, methodology badge behavior, and API compatibility.

Assumptions

  • The first implementation targets the readiness hero score only, because readiness currently has the server-owned serving/freshness contract.
  • EnergyBank and metric cards should not get similar badges until they have equally explicit serving contracts.
  • Existing top-level readiness fields remain available as fallback for older paths, but the dashboard should prefer ReadinessServing.
  • No new database schema or migration is needed.

Implementation Steps

  1. Add a dashboard readiness-serving view model in the UI layer rather than placing enum mapping directly into the template.
  2. Map server statuses to stable visual severities: fresh to positive, data_accruing to pending, capped to neutral, missing and stale to warning, low_coverage to low confidence.
  3. Build a short tooltip from the server reason and core components. Prefer plain phrases such as "HRV has too few samples today" over raw enum names.
  4. Render the badge next to the readiness methodology badge in the hero label row. Keep the old legacy note path only as fallback if ReadinessServing is nil.
  5. Add a short visible note under the score only for states that require attention: missing, stale, data-accruing, low-coverage, or capped.
  6. Add CSS for the badge, tooltip title affordance, and low-confidence dimming. Verify the hero layout does not shift or overlap.
  7. Add EN/RU/SR localization keys for labels, notes, and reason copy.
  8. Add focused template tests for the rendering matrix and keep backend readiness tests unchanged unless a gap is discovered.

Manual QA Checklist

  • Desktop: readiness hero shows methodology and trust badges without wrapping awkwardly.
  • Mobile: badge row, score, status, and note stay readable and do not overlap the narrative or EnergyBank blocks.
  • Fresh/final fixture: positive badge appears subtly and no dimming is applied.
  • Data-accruing fixture: the user sees that data is still settling, not that recovery is bad.
  • Missing/stale fixture: the user sees that the score is limited by missing or old inputs.
  • Low-coverage fixture: score area is visibly lower-confidence and tooltip explains why in plain language.
  • Capped fixture: badge explains that the displayed score was adjusted, without implying missing data.
  • English, Russian, and Serbian labels fit within the hero layout.

Risks

  • Duplicating backend logic: avoid by mapping only display labels/severity from ReadinessServing.Status, not recomputing freshness in UI.
  • Over-warning users: keep fresh/capped/accruing visually calm; reserve dimming for genuinely low-confidence states.
  • Hero clutter: use compact badges and the existing methodology/stress-chip visual language.
  • Localization overflow: test long RU/SR strings on mobile and shorten copy if necessary.

Rollback Plan

  • Revert the UI view model, template, CSS, and i18n changes in one PR if the display proves confusing.
  • Because the backend contract already exists and no schema changes are planned, rollback does not require data migration.
  • Keep legacy ReadinessConfidence fallback during implementation to reduce rollback risk.

Open Questions

  • Should the positive fresh/full-confidence badge always be visible, or only visible when the user hovers/taps details? Recommendation: show it subtly so silence does not have to mean "unknown".
  • Should this PR include only readiness, or also start a pattern for EnergyBank? Recommendation: readiness only for #157, because EnergyBank lacks the same serving contract today.
  • Should component coverage be summarized as a percentage in the first pass? The current contract exposes component presence/freshness/sample counts, not a single canonical percentage. Recommendation: show component coverage text now and add numeric percentage only if the backend defines it.
