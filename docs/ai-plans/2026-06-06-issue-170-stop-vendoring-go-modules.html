Implementation Plan: Issue #170 Stop Vendoring Go Modules

Approved and implemented

Task Summary

Decide and implement the dependency workflow change from committed vendor/ plus -mod=vendor to normal Go module resolution, if approved.

Current Behavior

  • The repository contains a committed vendor/ tree and vendor/modules.txt.
  • .github/workflows/ci.yml runs go build -mod=vendor ./..., go vet -mod=vendor ./..., and go test -mod=vendor ./....
  • actions/setup-go has cache: false.
  • Dockerfile copies the full repository before building and runs go build -mod=vendor.
  • go.mod uses Go 1.25.0 and current dependencies are represented in go.sum.

Desired Behavior

  • go.mod and go.sum are the reviewable dependency boundary.
  • CI builds, vets, and tests without -mod=vendor, with Go module caching enabled.
  • Docker build has a stable module download layer: copy go.mod/go.sum, run go mod download, then copy source and build.
  • Contributor docs describe normal Go module workflow.
  • Implementation does not upgrade dependencies unless required by no-vendor build validation.

Assumptions And Unknowns

  • Assumption: smaller PR diffs and OSS readability are more important than hermetic offline builds for this repository.
  • Assumption: GitHub Actions and Docker builders may access the public Go module proxy.
  • Unknown: whether any deployment environment requires offline Docker builds from a checked-in vendor tree.
  • Unknown: whether branch protection currently requires the existing check name exactly; this can be handled in issue #152.

Files Likely To Change

  • vendor/ - remove committed vendored dependencies if the decision is no-vendor.
  • .github/workflows/ci.yml - remove -mod=vendor, enable Go cache, and update comments.
  • Dockerfile - add module download layer and build without vendor mode.
  • README.md, CONTRIBUTING.md, AGENTS.md, CLAUDE.md - update build/dependency notes where relevant.
  • .dockerignore - add only if needed to keep Docker context clean after vendor removal.

Implementation Steps

  1. Confirm no explicit offline-build requirement exists in docs or deployment notes.
  2. Run go mod tidy and inspect whether go.mod/go.sum change.
  3. Update CI commands to remove -mod=vendor and enable setup-go cache.
  4. Restructure Dockerfile around go mod download and normal go build.
  5. Remove vendor/ in one commit so dependency deletion is easy to review separately from logic changes.
  6. Update contributor docs and project agent docs to remove vendor assumptions.
  7. Validate local Go commands and Docker build; then rely on GitHub CI for clean checkout verification.

Impact

  • Build: CI and Docker become network-dependent during module download.
  • Runtime: no intended runtime image behavior change except build-stage dependency resolution.
  • Security/review: dependency review moves to go.mod/go.sum instead of large vendor diffs.
  • Deployment: normal GHCR build path should continue, but needs CI and Docker validation.

Test Plan

  • go mod tidy
  • go test ./...
  • go vet ./...
  • go build ./...
  • docker build .
  • After PR: verify GitHub Actions Build, Vet & Test and Docker build jobs pass from a clean checkout.

Risks And Edge Cases

  • Network or Go proxy outage can break builds that previously used the committed vendor tree.
  • Large vendor deletion can obscure other changes; keep the PR focused.
  • Docker layer caching must be structured correctly or builds get slower.
  • If existing branch protection keys off exact check names, preserve names or coordinate via issue #152.

Rollback Plan

Restore vendor/, restore -mod=vendor in CI and Dockerfile, run go mod vendor, and revert docs to vendored dependency workflow.

Open Questions

  • Do we accept network-dependent CI/Docker builds for this repository?
  • Should Docker use default Go proxy or an explicitly configured GOPROXY?
  • Should this PR be split into two commits: config/docs first, vendor deletion second?
