Readiness Sleep Capture Confidence Plan

Summary

Add a read-only sleep capture reliability layer for Recovery Stability so partial Apple Watch sleep recordings are distinguished from physiologically meaningful poor recovery. The first PR should classify capture quality, expose confidence in feature/target payloads and monitoring, and run a probe on existing tenants. It should not change readiness chips, dashboard verdicts, Telegram copy, production baselines, or user-visible scoring.

Why This Exists

The monitoring contract cleanup fixed a false warning class by applying the correct 3-day maturity lag to rolling_3d. After deploy, remaining Maria warnings are real data-quality warnings, not monitoring bugs.

Tenant Signal Window Observed Result Dominant Reason
health recovery_stability/rolling_3d 2026-05-11..2026-05-24 14/14 eligible, ok none
health_mariia recovery_stability/rolling_3d 2026-05-11..2026-05-24 6/14 eligible, warn sleep_total_out_of_range
health_mariia chronic_load/chronic_label 2026-04-30..2026-05-13 0/14 eligible, warn event_window_data_missing downstream of invalid Recovery rows

Raw inspection showed that Maria has a late sleep schedule, with many sleep segments starting around 03:00-05:00 and ending around 09:00-13:00. The immediate failing rows are short captured totals rather than missing rows: 2026-05-15 = 3.99h, 2026-05-18 = 1.37h, 2026-05-20 = 3.35h. Under the current strict rule, any night under 4h is ineligible, and any one ineligible night makes multiple 3-day rolling labels ineligible.

Current Behavior

  • health.ComputeSleepEfficiency treats sleep_total < 4h as sleep_total_out_of_range.
  • rolling3dTarget requires all three future nights to be individually eligible.
  • A partial capture night and a real short-sleep night are collapsed into the same ineligible reason.
  • Downstream Chronic labels see missing Recovery rolling rows and surface event_window_data_missing.
  • Monitoring now shows concrete issue dates, but it does not yet classify whether the issue is a behavior signal or a sensor/capture reliability signal.

Desired Behavior

  • Classify sleep capture quality separately from sleep efficiency.
  • Preserve strict Recovery target semantics in the first PR unless evidence supports changing them.
  • Expose confidence fields next to Recovery features and coverage data so operators can see when bad labels are caused by partial capture.
  • Run a read-only probe comparing current strict rolling eligibility with confidence-aware alternatives.
  • Keep product behavior unchanged until we have evidence that a fallback improves stability without hiding real poor sleep.

Proposed Classification

Class Candidate Conditions Meaning Initial Action
good_capture sleep_total in [4h, 14h], staged components present, plausible awake/stage consistency Normal Recovery input Keep current target eligibility
partial_capture_short sleep_total in (0h, 4h), staged fragments present, late-start or truncated-looking segment pattern Likely watch/source captured only part of the night Mark low confidence; do not promote to product score yet
missing_capture No sleep_total row for the target night Device off, sync gap, or no sleep tracking Keep ineligible; surface as data gap
coarse_only_capture sleep_total plus sleep_unspecified, no real stages Source has sleep duration but no architecture Keep separate from staged Recovery evidence
stage_mismatch_capture sleep_total in range, staged components present, but staged sum differs materially from total Captured data is internally inconsistent enough to reduce confidence Mark low confidence; keep current target eligibility semantics
invalid_total_capture sleep_total is non-positive or above the plausible nightly ceiling Invalid source total, not a meaningful Recovery label Mark very low confidence and keep ineligible
real_short_sleep_candidate Short total without staged or coarse context that can explain it as partial capture Potential real recovery stressor Probe only; do not change chips without evidence

late_sleep_pending remains a reserved concept for future report/readiness timing work; the first implementation does not emit it.

Implementation Steps

  1. Add pure health-layer types for capture class, confidence score, and reason codes.
  2. Build classifier from already available daily sleep rows first; avoid schema changes.
  3. Optionally enrich classifier with segment-derived architecture fields already produced by the sleep architecture layer.
  4. Write unit tests for short capture, missing capture, coarse-only capture, valid capture, and late-schedule examples.
  5. Extend Recovery feature/coverage JSONB payloads with capture fields, bump feature version if the feature payload changes.
  6. Add a read-only probe for health and health_mariia: strict eligibility, confidence-aware 2-of-3 alternative, and reasons by date.
  7. Do not change target eligibility or product surfaces until probe results are reviewed.

Scope Guard

  • No schema migration; use JSONB feature/coverage payloads.
  • No changes to current readiness chips, dashboard verdicts, Telegram copy, or production baselines in the first PR.
  • No silent promotion of <4h nights to eligible Recovery labels.
  • No tenant-specific hardcode for Maria; late-schedule handling must be data-driven.
  • No change to daily_scores sleep aggregation until we separately prove the day-boundary or source-pick logic is wrong.

  • Confirm existing valid Recovery rows keep the same target values and eligibility reasons.

Risks

  • Over-correcting partial capture could hide real short sleep and make Recovery too optimistic.
  • Keeping strict 3/3 rolling eligibility may continue to produce sparse labels for users with poor watch discipline.
  • Late-schedule handling can become tenant-specific if not based on observed sleep timing distributions.
  • Daily bucket logic may still need a separate follow-up if we find nights crossing local-day boundaries.

Rollback Plan

Revert the code-only PR. Because the first PR should only add JSONB payload fields, monitoring details, tests, and read-only probe output, rollback is code-only and does not require data cleanup.

Open Questions

  • Should partial_capture_short remain ineligible but count as a different monitoring bucket, or should a later PR allow 2/3 rolling eligibility with low confidence?
  • What confidence threshold is acceptable before product surfaces can use fallback Recovery values?
  • Should late sleepers get a tenant-level adaptive report readiness delay based on observed wake times?
  • Should Chronic labels ignore low-confidence Recovery rows differently from missing Recovery rows?

Read-Only Probe Result

Probe command: go run ./cmd/readiness_sleep_capture_probe --schema health,health_mariia --from 2026-05-01 --to 2026-05-24

Low Capture is a confidence flag, not an exclusive class. It can overlap with Partial Short, Missing Capture, Coarse Only, or Stage Mismatch, so it may be non-zero even when the partial/missing class columns are zero.

Tenant Rows Strict 3/3 Candidate 2/3 Rescued Low Capture Partial Short Missing Capture
health 24 24/24 (100.0%) 24/24 (100.0%) 0 6 0 0
health_mariia 24 12/24 (50.0%) 23/24 (95.8%) 11 12 8 4

This supports the product hypothesis: Maria's sparse Recovery rolling labels are mostly capture-reliability failures. The PR still stops at evidence and diagnostics; promoting a 2-of-3 fallback requires a separate decision.

Approval Gate

Implementation must not start until this plan is explicitly approved. Approval means the next PR may add sleep capture confidence fields, tests, monitoring diagnostics, and read-only probe tooling only. It must not change user-visible readiness behavior or promote low-confidence short sleep rows to eligible production labels without a separate approval.
