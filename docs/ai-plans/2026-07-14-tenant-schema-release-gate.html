Tenant Schema Release Gate

Approval required before production-code changes

Prepared 2026-07-14 · related to issue #198 · based on merged origin/main

Task Summary

Add an exact-set pre-production and post-production gate which proves that every registered tenant schema was migrated, every physical tenant schema and role is accounted for, and database isolation still holds. The target image provides an explicit mutating migration mode and a separate read-only audit mode.

Approved Decisions

  • Use both pre-start and post-start audits.
  • Keep audit detection-only; migration is a separate explicitly confirmed command.
  • Use one immutable image digest for migration, audit, runtime, and postflight.
  • Use a short maintenance window instead of adding an online provisioning lease.
  • Verify all tenant pairs, not a single representative foreign schema.
  • Keep default output pseudonymous and safe to attach to an issue.

Current Behavior

  • cmd/tenant_isolation inventories only active registry schemas through CanonicalSchemas.
  • Verification selects only the first other schema for denial probing.
  • Existing-tenant migration writes __tenant_identity, while clean provisioning uses _health_tenant_provisioning.
  • VerifyProvisionedSchema checks required object names, but there is no durable schema-contract version/checksum.
  • The runtime image currently contains only /app/server.
  • Startup performs schema initialization, so a target-image audit cannot prove target compatibility before those mutations run.
  • The Compose file supports HEALTH_IMAGE, but its fallback remains mutable :latest.

Desired Release Flow

  1. Resolve target digest
  2. Inventory current fleet
  3. Stop service
  4. Migrate all schemas
  5. Run exact-set audit
  6. Start pinned digest
  7. Wait for readiness
  8. Repeat audit

The service is not started with the target image if migration or the authoritative pre-start audit fails.

Data and CLI Contract

Every active schema gets one permanent __tenant_identity row containing immutable tenant identity plus schema_contract_version and schema_contract_checksum. The active registry row stores the same contract metadata. The target binary contains the expected values.

/app/tenant_isolation --mode migrate-contract --all --primary-schema ... --confirm
/app/tenant_isolation --mode audit --all --primary-schema ...

migrate-contract is idempotent and mutating. audit performs read-only catalog scans and rollback-only runtime denial probes. Both return nonzero on incomplete coverage.

Implementation Steps

  1. Contract first: add failing tests for a deterministic manifest/version/checksum and incomplete catalog detection; implement the shared contract without changing production wiring.
  2. Permanent identity: extend __tenant_identity and registry metadata; prove interrupted marker/registry updates are detected and retryable.
  3. Clean-install convergence: switch provisioning and startup to the shared contract path; retain the transient provisioning marker only for recovery ownership.
  4. Exact inventory: enumerate registry rows in all states, permanent marked schemas, marked roles, and nonterminal operations; compare exact sets and recheck the digest at audit end.
  5. Isolation proof: audit owner/grants/default ACLs and execute rollback-only tenant-to-registry and all-pairs tenant denial probes.
  6. CLI: add explicit migration and read-only audit modes, structured pseudonymous JSON, stable reason codes, and nonzero failure exits.
  7. Runtime artifact: include the CLI in the same image as the server and verify both binaries in container smoke tests.
  8. Deployment gate: implement the maintenance-window wrapper with one resolved digest and explicit recovery output.
  9. Documentation: update configuration and architecture docs, including the fact that admin credentials remain part of the current runtime architecture.

Manual QA and Production Checklist

  • Prepare a root-only migration environment; confirm it is not mounted into logs or committed.
  • Resolve and record target and previous immutable digests before downtime.
  • Confirm no out-of-band tenant registry changes will occur during the maintenance window.
  • Run current inventory, stop only health-receiver, then run migration and pre-start audit.
  • Start the pinned digest, verify /readyz, restart count, and recent logs.
  • Run post-start audit and retain only sanitized JSON evidence.
  • Close issue #198 only when production isolation is enabled and this postflight passes.

Risks and Edge Cases

  • A failed authoritative gate leaves the application stopped. The wrapper must print a clear, reviewed recovery command and previous digest.
  • Contract migration must remain additive and backward-compatible; destructive migrations need a separate design.
  • Large future tenant counts make all-pairs probes quadratic. That is acceptable for the current fleet; catalog checks may later reduce runtime probes.
  • Direct registry writes outside the stopped application can still race the maintenance window and are operationally prohibited.
  • The audit cannot claim that admin credentials are absent from the main application; provisioner separation is out of scope.
  • The local branch is currently behind origin/main and contains an unrelated untracked audit plan. Implementation must begin in a fresh branch/worktree from origin/main without overwriting it.

Rollback Plan

Record the previous digest before the service is stopped. Do not automatically reverse schema or privilege changes. If the gate fails, either fix and rerun the idempotent target migration or explicitly restart the previous digest after confirming compatibility. Never drop tenant schemas, roles, markers, registry metadata, or data as part of automatic rollback.

Assumptions and Open Questions

  • Assumption: tenant creation occurs through this service; direct registry writes are excluded during deployment.
  • Assumption: the current small fleet tolerates a short maintenance window.
  • Assumption: the first contract migration is additive and can be retried safely.
  • No blocking product decision remains. Exact contract version numbering and checksum encoding are implementation details covered by deterministic tests.
