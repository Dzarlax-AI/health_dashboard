AI provider adapters и прямая поддержка OpenAI API

Перевести AI-брифинг с Gemini-специфичной реализации на расширяемый registry отдельных provider-адаптеров, добавить прямой OpenAI Responses API и переключатель активного провайдера в Admin UI. Gemini остаётся полностью поддержанным; OpenRouter сознательно отложен и позднее добавляется как третий адаптер.

Состояние репозитория перед реализацией

  • Текущий checkout: main, он отстаёт от локального origin/main на 38 коммитов.
  • В рабочем дереве уже лежат три чужих незакоммиченных HTML-плана; они не относятся к этой задаче и должны быть сохранены.
  • До изменения production-кода нужно безопасно синхронизировать исходную ветку и повторно проверить затронутые файлы. План основан на текущем checkout и read-only просмотре соответствующих версий из origin/main.

Текущее поведение

  • internal/ai/gemini.go одновременно реализует Gemini model discovery, HTTP transport, request construction и response parsing.
  • internal/ai/blocks.go принимает Gemini key/model напрямую и вызывает неэкспортируемый generateWithPrompt.
  • storage.AIConfig, env defaults, tenant/global layering, Admin API и UI используют только gemini_* поля.
  • Admin UI сохраняет ключ во время загрузки списка моделей и затем возвращает полный ключ обратно браузеру.
  • Три leaf-блока генерируются параллельно, затем генерируется RECOMMENDATION. Этот порядок, single-flight и пяти­минутный failure backoff нужно сохранить.
  • inputs_hash учитывает health-входы, но не provider, model, reasoning, output limit или версию prompt. Поэтому простая смена модели не гарантирует регенерацию.
  • Rule-based health bullets остаются авторитетным слоем; AI только дополняет их интерпретацией.

Принятые продуктовые и архитектурные решения

  • Переключатель находится в Admin UI и действует installation-wide через health_registry.global_settings.
  • На первом этапе поддерживаются прямые Gemini и OpenAI API.
  • OpenRouter не маскируется под OpenAI и позднее добавляется отдельным provider-адаптером.
  • У каждого provider собственные key/model/settings; смена активного provider не удаляет настройки другого.
  • Автоматического fallback между провайдерами нет: конфигурационные и transport-ошибки должны быть видимы в логах и Admin UI.
  • По умолчанию остаётся Gemini для полной обратной совместимости существующих установок.
  • OpenAI используется через Responses API. Для Luna reasoning задаётся явно как none, чтобы не унаследовать более дорогой и медленный default.
  • OpenAI requests используют store: false; prompts и responses не пишутся в application logs.

Нейтральный контракт

Provider должен принимать provider-neutral GenerationRequest с instructions, user input, language, output limit и дополнительными настройками, а возвращать нормализованный текст и usage metadata. Адаптер сам переводит этот контракт в vendor request: Gemini получает systemInstruction/contents, OpenAI — instructions/input/max_output_tokens/reasoning/store.

Registry и описание UI

Registry хранит стабильный ID, display name, factory/instance адаптера и описание поддерживаемых provider-specific полей. Admin handler получает allowlist и UI metadata из registry, поэтому добавление нового provider не требует нового условного блока в orchestrator. Vendor-specific parsing и параметры остаются внутри адаптера.

Admin UI и Admin API

  • Добавить provider selector Gemini / OpenAI и показывать поля активного адаптера без перезагрузки страницы.
  • Сохранять конфигурацию обоих адаптеров одним явным действием Save; изменение поля ключа не должно ничего писать в БД.
  • GET возвращает configured: true/false, но не полный секрет. Пустое password-поле означает «сохранить текущий ключ»; отдельное явное действие очищает ключ.
  • Model input остаётся редактируемым. Provider может предложить варианты через ListModels, но UI не блокирует новую валидную model ID, отсутствующую в discovery response.
  • POST /api/admin/ai-models принимает provider и опциональный временный key для discovery, не сохраняя его. Stored key используется только когда новый key не передан.
  • Server-side validation запрещает неизвестный provider, неизвестный reasoning effort и недопустимый token limit.
  • Добавить локализованные подписи и ошибки для EN/RU/SR.

Кэш и data flow

  1. Текущая AI-конфигурация разрешается по существующему приоритету tenant settings → global settings → env.
  2. Registry выбирает активный adapter. Отсутствующий ключ активного provider означает AI disabled; скрытого fallback на другой provider нет.
  3. К базовому health hash каждого блока добавляется generation fingerprint: provider ID, model, reasoning, max output tokens и явная prompt revision.
  4. При неизменном fingerprint сохраняется текущая per-block дедупликация.
  5. При смене provider/model все четыре блока получают новый hash и регенерируются. Старый корректный текст может оставаться видимым до успешной атомарной замены соответствующего блока, сохраняя non-blocking UX; новые вызовы другому provider при этом не выполняются автоматически.
  6. Failure backoff должен различать generation fingerprint, чтобы ошибка старой конфигурации не задерживала первый запрос после переключения.
  7. Логи используют нейтральные сообщения с provider ID и block ID, но никогда не содержат key, prompt, health JSON или полный vendor response.

Ручной QA

  • Существующая Gemini-конфигурация отображается и работает после обновления без повторного сохранения.
  • Переключение на OpenAI показывает OpenAI fields и не стирает Gemini key/model.
  • Luna генерирует четыре блока на синтетическом payload; plain-text и длина соответствуют текущему prompt contract.
  • После смены provider/model блоки получают новый fingerprint и обновляются.
  • Неверный OpenAI key показывает понятную admin error и не переключает вызовы на Gemini.
  • При отключённом AI rule-based briefing и Telegram report продолжают работать.
  • В browser responses и application logs отсутствуют API keys и raw health prompts.
  • EN/RU/SR Admin UI не содержит Gemini-specific подписи для OpenAI fields.

Риски и edge cases

  • Поведенческий drift: Gemini и Luna могут по-разному соблюдать 40–70-word contract. Нужны одинаковые fixtures/evals, без переписывания prompt до обнаружения измеримого дефекта.
  • Reasoning default: GPT-5.6 при пропущенном effort может включить более тяжёлый режим; значение none должно быть явным.
  • Vendor parameters: нельзя слепо передавать Gemini temperature/options в OpenAI. Каждый adapter формирует только поддерживаемые поля.
  • Response variants: OpenAI может вернуть refusal, incomplete status или несколько output items; parser не должен принимать пустой/частичный результат за успех.
  • Rate limits: три параллельных leaf calls сохраняются; 429 проходит через существующий failure backoff без скрытого provider fallback.
  • Secret handling: текущий UI возвращает и временно сохраняет key во время discovery. Этот паттерн необходимо удалить для обоих providers.
  • Cache race: provider может смениться во время in-flight generation. Single-flight остаётся общим для date/lang; следующий poll сверяет новый fingerprint и исправляет результат без параллельной записи двух providers.
  • Model discovery: OpenAI model listing не является надёжной capability registry. Поэтому model field должен оставаться редактируемым.
  • Stale checkout: implementation нельзя начинать на текущем отстающем checkout без повторной сверки с актуальной веткой.

Влияние на данные, auth и deployment

  • Database: новых таблиц/колонок нет; используются новые ключи существующей global_settings. Schema contract version не меняется.
  • Auth: Admin endpoints остаются под существующим adminGuard. Новых публичных endpoints нет.
  • Privacy: OpenAI получает тот же health JSON, который сейчас получает Gemini. store: false обязателен; raw payload не логируется.
  • Deployment: без OpenAI key поведение остаётся Gemini-only. Переключение provider выполняется после deploy через Admin UI, без restart.
  • External calls: automated tests не используют реальные API keys. Реальный smoke test выполняется только после явной настройки key оператором.

Rollback

  1. В Admin UI выбрать Gemini; сохранённая Gemini-конфигурация остаётся на месте.
  2. Если проблема в новом release шире provider selection, откатить приложение на предыдущий immutable image/commit.
  3. Новые KV settings безвредны для старой версии и не требуют удаления.
  4. DB rollback/migration не нужен, так как DDL не меняется.

Предположения и открытые вопросы

  • Принято: provider selection installation-wide, как текущая Gemini config.
  • Принято: direct OpenAI only на первом этапе; custom Base URL и OpenRouter вне scope.
  • Принято: default provider Gemini; default OpenAI model gpt-5.6-luna; default reasoning none.
  • Принято: нет автоматического cross-provider fallback.
  • Требуется при реализации: актуальная ветка и повторная сверка после 38 отсутствующих коммитов.
  • Требуется для post-implementation smoke test: OpenAI API key, введённый пользователем через Admin UI; в код или test fixtures он не записывается.

Фактический результат реализации

Что изменено

  • Добавлены provider-neutral interface, descriptor registry и generation fingerprint в internal/ai/provider.go.
  • Существующий Gemini transport оформлен как adapter; запросы теперь поддерживают context cancellation, а ошибки не включают raw upstream body.
  • Добавлен прямой OpenAI Responses adapter: Bearer auth, store: false, gpt-5.6-luna по умолчанию, явный reasoning effort и безопасный разбор completed/incomplete/refusal responses.
  • Block orchestrator маршрутизирует четыре блока через активный adapter. Cache fingerprint включает provider, model, reasoning, output limit и prompt revision; failure backoff также разделён по fingerprint.
  • AI config хранит независимые credentials/model каждого provider. Существующие Gemini env/settings продолжают работать; legacy GEMINI_MAX_TOKENS остаётся fallback.
  • Admin UI получил provider selector, masked key replacement/explicit clear, editable model suggestions, conditional reasoning и общий output limit. Model discovery больше не сохраняет key как side effect.
  • Admin GET возвращает только configured, но никогда API keys. Ошибки discovery не отдают browser raw vendor responses.
  • Добавлены EN/RU/SR labels, обновлены README, .env.example и twin-файлы AGENTS.md/CLAUDE.md.

Известные ограничения и follow-up

  • Переключение provider не удаляет прежние credentials и не очищает старый текст до успешной новой генерации.
  • DB schema и migration не менялись; rollback выполняется выбором Gemini в Admin UI или откатом application release.
