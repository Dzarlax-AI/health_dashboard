Health Dashboard - follow-up plan for issue #173

Illness Autonomic Prodrome Detection

Created: 2026-06-03. Scope: planning only. No production code changes are included in this branch yet.

Summary

The first illness suspicion implementation added an evidence-bound, non-diagnostic layer that detects converging respiratory, oxygen, autonomic, temperature, and subjective signals. Production validation found an important follow-up: a known illness window can show several days of autonomic strain before the respiratory signal becomes strong enough for the v0 detector.

Proposed decision: add a conservative autonomic_prodrome / autonomic_illness_load pattern inside the existing illness suspicion surface. It should catch repeated elevated sustained heart-load plus elevated resting heart rate under normal or low activity context, while never producing high confidence by itself and never using diagnostic language.

Current Behavior

The current detector is intentionally respiratory-first. It is good for acute same-day respiratory evidence, but it treats sustained heart-load as visible context rather than a contributing illness signal. That prevents exercise-related false positives, but it can miss early illness or recovery-load windows where autonomic strain is present before respiratory rate or oxygen evidence converges.

Validation pattern Observed v0 behavior Why it matters
Known-positive illness window with repeated strong sustained HR load, elevated RHR, normal or low activity, and no early respiratory spike. Early days return none because sustained HR load is non-contributing and respiratory evidence is absent or weak. The dashboard can appear overly positive while the user is already sick or entering a sick/recovery state.
Later day in the same window with strong respiratory evidence plus autonomic support. Returns high, which confirms the v0 respiratory pathway works once the respiratory signal arrives. The gap is not the whole illness detector; it is the missing autonomic prodrome layer.
Known-negative sedentary day with low activity and no illness. Must remain none or at most weak/low evidence. The new mode must not classify ordinary sedentary behavior, gaming days, or stress-only days as illness.

Desired Behavior

  • Keep the existing respiratory/oxygen illness suspicion behavior unchanged.
  • Add an autonomic pattern that can surface early illness or recovery-load evidence before respiratory evidence arrives.
  • Use objective data first. Subjective sick check-ins may confirm the pattern, but must not be the primary detector.
  • Never raise high confidence from autonomic-only evidence.
  • Use non-diagnostic wording: "autonomic strain consistent with illness or recovery load", not "you are sick".
  • For moderate autonomic suspicion, keep the EnergyBank safety cap conservative at active_recovery; do not force rest.
  • Expose the pattern clearly in server/UI data so the dashboard does not call an autonomic-only event a respiratory illness.

Proposed Policy

Autonomic Load Day

A date is an autonomic load day when the system sees objective cardiovascular strain that is unlikely to be explained by high activity.

  • sustained_hr_load_z >= 2.0 with activity_context normal or low.
  • Plus at least one support signal: elevated RHR, low HRV, weak SpO2 cluster/drop, illness-compatible stress flag, or recent neighboring autonomic load.
  • High activity context blocks autonomic illness escalation unless respiratory/oxygen evidence independently qualifies.
  • Unknown activity context should be treated cautiously: enough for low confidence, but not enough for moderate without repeated days or RHR support.

Confidence Rules

Local Experiment Results

After this plan was created, a local read-only experiment was run against two private production profiles over the recent historical window. Exact health values are intentionally not recorded in this public artifact; the purpose is to validate relative rule behavior and false-positive risk.

Experiment-driven amendment: implement the combined RHR-gated repeated-load rule as the v1 autonomic prodrome path. Keep HRV, SpO2, and stress flags as explanatory support signals, but do not let them independently upgrade an autonomic-only day to moderate confidence.
  • The known private February illness window is missed by the current v0 detector on early autonomic days, then detected once respiratory evidence becomes strong.
  • The combined candidate catches the early autonomic window before the respiratory peak on Profile A.
  • A known sedentary negative-control day remains outside the autonomic candidate set.
  • Profile B shows compact candidate clusters rather than daily noise under the combined rule.

Implementation Steps

  1. Add an explicit illness pattern field such as pattern with values like respiratory, oxygen, autonomic_prodrome, and mixed.
  2. Add a date-aligned rolling autonomic summary in storage. It must use the evaluated date and nearby prior dates, not compressed raw metric slices.
  3. Teach ComputeIllnessSuspicion to evaluate autonomic pattern days separately from respiratory/oxygen primary signals.
  4. Update reason text so autonomic-only suspicion says "autonomic strain" or "recovery load", not "respiratory stress".
  5. Keep ApplyIllnessSafetyCap conservative: moderate autonomic suspicion may cap to active_recovery, high remains unavailable without respiratory/oxygen convergence.
  6. Add local probe support for private date windows and summarize validation results without publishing raw values.
  7. Update the plan with actual implementation notes, checks run, and known limitations before opening the implementation PR.

Test Plan

  • One isolated sustained HR load day remains low or none.
  • High activity context blocks autonomic illness escalation.
  • Autonomic-only evidence never yields high confidence.
  • Respiratory/oxygen high-confidence behavior remains unchanged.
  • Subjective sick check-in cannot create moderate/high confidence without objective evidence.
  • Reason strings do not contain diagnostic wording.
  • Moderate autonomic suspicion caps EnergyBank at active_recovery, not rest.

Manual QA Checklist

  • Open the dashboard for a current sick day and confirm the illness card appears when objective evidence qualifies.
  • Confirm the card copy says autonomic strain/recovery load when respiratory evidence is not present.
  • Confirm readiness and EnergyBank explanations do not overclaim and do not contradict the illness card.
  • Confirm the private known-positive window shows earlier suspicion than the current v0 detector.
  • Confirm the private known-negative sedentary day does not become a moderate illness suspicion.

Risks

Main risk: false positives from non-illness autonomic load, including work stress, sleep debt, gaming, alcohol, heat, dehydration, sensor fit, or missing activity data. The mitigation is to require repeated or supported evidence, block high-activity contexts, keep confidence capped at moderate, and keep wording explicitly non-diagnostic.
  • Some true early illness windows may still remain low confidence if only one signal is present.
  • Activity context quality matters; missing or stale steps/calories can weaken confounder detection.
  • Adding a pattern field is additive, but UI and MCP clients should tolerate empty or unknown values.

Rollback Plan

  • No database migration is expected.
  • The implementation can be reverted by removing the autonomic confidence branch and pattern-specific copy.
  • If validation is noisy, ship the probe and tests first, but leave autonomic escalation disabled behind a constant until thresholds are tuned.

Open Questions

  • Should a one-day autonomic event with strong RHR support show low or moderate? Proposed answer: low unless there is repeated context or subjective confirmation.
  • Should unknown activity context allow moderate autonomic suspicion? Proposed answer: only with repeated days and RHR/HRV support.
  • Should the UI show "possible illness" for autonomic-only moderate, or a softer "recovery load" label? Proposed answer: use softer wording until respiratory/oxygen evidence converges.
