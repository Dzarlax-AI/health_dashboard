PR review remediation · 2026-07-13

  • Runtime scheduling now fires an unchanged due report, detects last-minute schedule edits, accepts additional runtime tenants in readiness, and prevents API-only bootstrap from creating a usable blank UI password.
  • Tenant pool creation and metadata validation are coalesced per schema without holding the manager-wide lock across registry or database I/O. Request cancellation is isolated from shared work. Transient metadata failures and confirmed credential-version drift fail closed without closing pools captured by background workers or discarding callbacks.
  • Credential rotation uses safely quoted PostgreSQL utility SQL. Runtime hot pool replacement is intentionally unsupported: a version drift remains fail-closed until a successful service restart establishes new-version pools, and the previous secret must remain available until that verification succeeds.
  • Import commit owns and locks its lease through promotion and finalization. Failure and staging cleanup are lease-scoped, while legacy installs add heartbeat_at and lease_token before abandoned-import cleanup runs.
  • Accepted ingest records still finalize caches when completion-status bookkeeping fails. Recovery failures are logged instead of disappearing.
  • Telegram delivery completion uses a fresh bounded context after sending. Malformed or truncated HTTP 200 acknowledgements are classified as ambiguous, preventing prompt retries and rich-message fallback duplicates; valid provider rejections remain definitive.
  • Operational responses no longer expose raw tenant-provisioning errors, setup reconciliation is cooldown-protected, explicit tenant scope avoids eager all-pool validation, and CI restart recovery uses bounded polling.

Migration and clean-install contract

  • All application DDL is additive/idempotent; legacy large tables avoid volatile-default rewrites.
  • Existing users backfill isolation metadata with db_isolation_ready=false. Runtime isolation refuses them until CLI proof succeeds.
  • Fresh isolated provisioning runs table creation twice, verifies required tables/indexes/columns, then atomically activates the user with readiness true.
  • Existing-install order: deploy compatible code with isolation disabled → inventory/manifest → canary apply/verify → remaining tenants primary-last → enable isolation → deploy immutable image.
  • Rollback restores ownership/effective grants and readiness false from checksum-protected manifests before the legacy image starts.
