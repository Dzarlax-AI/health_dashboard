Интеграция с основным сервером в PR #280

Статус. Теневой контур, серверные режимы prepare и serve, атомарная публикация и возврат читателей реализованы в ветке PR #280. Локальные сценарии проверяют переключение и откат на изолированных синтетических профилях; описанные ниже результаты только подготовки относятся к более раннему этапу. Общая приёмка истории по актуальному реестру, мерж и production-выкат требуют отдельного решения и разрешения.

Цель — провести тот же путь через обычный бинарник Health на изолированном стенде. После принятого синка Health сохраняет входы, пересчитывает обе даты переноса, подготавливает одну ревизию сна для Готовности и EnergyBank и умеет вернуть прежний маршрут. Дневной сон рассчитывается SQL из dbt, который запускает Go. Формулы Готовности и EnergyBank остаются в Go. Правила активности и релиз клиента вне этого PR.

Первый шаг через штатный POST /health

Старый формат можно обслуживать с SQL из dbt до обновления Health Sync. Приём сохраняет исходный пакет и source. После штатного почасового пересчёта Go исполняет макрос dbt внутри записи daily_scores. Остаются текущие выбор источника по сумме и приоритету, проверка расхождения, отбор совместимых стадий и сохранение предыдущего блока, если новые входы неполные. Готовность и EnergyBank используют штатный пересчёт после обновления дневных данных.

По умолчанию используется прежний SQL. Для синтетического стенда нужны HEALTH_LEGACY_SLEEP_DBT_ENABLED=1 у сервера и legacy_sleep_dbt_enabled=true в настройках выбранного профиля. Значение false возвращает прежний SQL со следующего пересчёта профиля. Оба пути используют одну таблицу и семантику, поэтому переключение не требует копирования строк и повторного приёма сырья. Для общего выключения убрать флаг процесса при перезапуске.

Приёмка сравнивает штатный /health для двух изолированных профилей на одном синтетическом пакете. Сверяются балл, категория, компоненты живой Готовности и история. Живая Готовность по прежним правилам может брать свежие стадии из сырых точек. EnergyBank читает дневной блок из daily_scores. Совпадение компонентов подтверждает совместимость с Go. Общий блок сна для обоих читателей относится к отдельному этапу serve.

Тест отката выключает флаг, пока PostgreSQL удерживает первый дневной результат принятого синка. В этот момент уже принятые пакеты и снимки остаются неизменными. Начатый пересчёт завершает обе даты через dbt, следующий синк применяет прежний SQL. Исторический наблюдавшийся снимок остаётся неизменным после обеих корректировок. Для перехода на dbt достаточно существующего формата синка. Если новый Health Sync будет присылать исходные кандидаты для серверного выбора, сервер сначала должен принять новый блок в штатном /health и сохранить совместимость со старым пакетом. Текущий экспериментальный приём кандидатов по /health/sleep/v2 работает в режиме подготовки.

Кандидаты сна через штатный POST /health

Контракт согласован и реализован в локальной ветке PR #280. Старые и обновлённые клиенты используют один синк с тем же API-ключом. Оба продолжают передавать прежние data.metrics. Новый клиент сможет добавить data.sleep_candidates_v1. В режиме prepare кандидаты попадают только в подготовку, а читатели продолжают использовать прежние правила. В режиме serve используется опубликованная ревизия в пределах, описанных ниже.

Пакет и подтверждение

Форма нового блока. Остальные поля штатного пакета сохраняются.

{
  "data": {
    "metrics": [],
    "sleep_candidates_v1": {
      "batch_id": "20db6637-ec3d-4021-a80d-310e99139a86",
      "candidates": [
        {
          "source_id": "opaque-source-id",
          "candidate": {
            "id": "opaque-night-id",
            "revision": 1,
            "wake_zone": "Asia/Singapore",
            "stages": [
              {
                "id": "opaque-interval-id",
                "kind": "asleep_unspecified",
                "start_at": "2026-11-18T22:00:00+08:00",
                "end_at": "2026-11-19T06:00:00+08:00"
              }
            ]
          }
        }
      ]
    }
  }
}

metrics в примере сокращён для показа структуры. Обновлённый Health Sync продолжает отправлять совместимые точки сна. Он сохраняет стабильные ID источника, ночи и интервалов, меняет ревизию ночи при исправлении и повторяет отправку того же пакета с тем же batch_id. Сервер берёт приоритет из профиля и определяет дату пробуждения в явной местной зоне. Неизвестная зона не угадывается по месту текущего синка. Такие записи пока идут через прежние метрики. Пропуск нового блока не означает удаление ночи.

Сохранить ответ 200 {"status":"ok","id":…}. После коммита нового блока отдавать заголовок X-Health-Sleep-Candidates-Ack со значением batch_id. Если заголовка нет, подтверждён только обычный синк. Будущий клиент должен считать кандидатов неподтверждёнными до получения своего идентификатора. В режиме off неизвестный пакет принимается как обычный синк без новых заданий для кандидатов. Повтор уже подтверждённого пакета возвращает прежний ID и тот же заголовок даже при off или выключенном глобальном флаге.

Приём, повтор и обработка

  1. В обработчике /health оставить штатный путь для пакетов без блока. Для расширения проверить глобальный флаг, prepare, изолированный пул и соответствие tenant реестру. Повторно проверить режим в транзакции под существующей блокировкой. Размер всего тела ограничен штатным лимитом. Для нового блока переиспользовать валидацию sleepwire.Candidate, лимит стадий и ограничить пакет 32 кандидатами. Дубли ключей одного кандидата в пакете отклонять.
  2. В одной транзакции сохранить полное тело в health_records, квитанцию по batch_id со ссылкой на запись и задания для новых ревизий. Переиспользовать очередь sleep_rollout_packets, хранить связь с исходными совместимыми данными сна. Контракт схемы v15 добавляет sleep_rollout_batches и ссылку задания на сырой пакет через штатную аддитивную миграцию. При конфликте или ошибке транзакции не выдавать подтверждение расширения. Ошибка валидации активного расширения возвращает 400, конфликт данных при том же ID или ревизии возвращает 409.
  3. Побайтовый повтор ранее подтверждённого тела с тем же batch_id возвращает исходный id и подтверждает тот же batch_id без новой записи и постановки задания. Более старая ревизия не меняет подготовленного кандидата. В новом пакете её совместимые метрики обрабатываются по правилам старого клиента. Перенос ночи по новому кандидату влияет только на подготовленную витрину. Обычные метрики смешанного пакета обрабатываются периодически отдельной очередью, в том числе при off. Точки, дневной кеш и отметка завершения коммитятся вместе. Работник кандидатов проверяет эту отметку перед подготовкой. Повтор экспериментального пакета требует совпадения его сохранённого legacy_payload. Если ревизия пришла впервые через смешанный пакет, экспериментальный маршрут отвечает 409.

Проверки и откат

  • На двух изолированных профилях проверить старый и смешанный пакеты, выключенный режим, чужой ключ и отсутствие записи в чужую схему. Сверить прежнюю форму ответа, сохранённые источники и результаты в daily_scores, Готовности и EnergyBank.
  • На одном пакете проверить конкурентный точный повтор, потерянный ответ после коммита, конфликт ревизии, ошибку между записью сырья и очереди, рестарт после подтверждения и перенос на соседнюю дату с поздним старым повтором. Ожидаются одна квитанция на пакет, одна запись на ревизию и отсутствие частичного подтверждения. Пересчёт обеих дат виден только в режиме подготовки.
  • Выключить prepare при незавершённой обработке. Штатный синк продолжает принимать совместимые метрики. Уже подтверждённые пакеты и задания сохраняются, а накопленная очередь подхватывается при повторном включении. Сравнить наблюдавшиеся снимки до и после выключения при одинаковом штатном трафике.

На одноразовом PostgreSQL двукратно проверены оба формата, сохранение исходного source, конкурентный повтор с тем же ID, конфликт, отказ при вставке второго кандидата и перенос ночи на соседнюю местную дату. После имитированного сбоя штатный пакет восстановился при перезапуске, а два подтверждённых задания остались в очереди при off и завершились после возврата в prepare. Поздний старый повтор не сместил ночь. Наблюдавшийся снимок EnergyBank совпал побайтово. Прошли серверные интеграционные тесты, make test-unit contract-check и сборка cmd/server. Интеграционный тест

После ревью повторили три серверных сценария дважды на локальном PostgreSQL. В off и с выключенным глобальным флагом точный повтор вернул прежний ID, а изменение тела вернуло 409. Ошибка чтения режима вернула 503 без сырой записи. Смешанный пакет восстановился при перезапуске за 1001 обычной записью. Ошибки записи точек и дневного кеша не разблокировали кандидата. Уникальные 420 ккал из смешанного пакета появились в daily_scores до расчёта подготовленного результата. Два разных экспериментальных legacy_payload для уже принятой через /health ревизии получили 409. make test-unit contract-check прошёл.

Повторное ревью выявило риск устаревшей записи, остановки очереди на битой дате и преждевременного уведомления для смешанной сессии. Отложенная обработка сравнивает время исходного приёма для пересекающихся точек. Новая некорректная дата получает 400. Ранее сохранённый необрабатываемый пакет остаётся в журнале со статусом failed, после него очередь продолжает работу. Смешанная квитанция сохраняет ID и число частей X-Sync-Session. Уведомления ждут завершения сессии или её штатного тайм-аута. Дневной кеш смешанной части коммитится до подготовки кандидата, а применённое поколение передаётся координатору. В локальном сценарии сохранились свежие 500 ккал и исходная ссылка на новый пакет, уникальные 420 ккал дошли до другой даты. В сценарии из трёх частей координатор получил одно уведомление, SQL записал один дневной агрегат на каждую из двух дат.

Серверная совместимость после следующего ревью. Пересекающиеся обычные и смешанные точки упорядочиваются по исходному приёму в обе стороны. Повторы покрытия сна тоже учитывают исходную квитанцию. Проверяется полное время измерения, включая смещение. Исправленный пакет той же ревизии заменяет только неработающую зависимость кандидата, а первоначальный пакет остаётся в журнале. При поступлении метрики Готовности сессия пересчитывает баллы отдельно от уже записанных дневных агрегатов.

Для локальной проверки подготовленных дат у cmd/sleep_shadow есть режим -audit-server-schema с параметрами -audit-server-tenant, -audit-server-from и -audit-server-through. Он требует одноразовую PostgreSQL через Unix-сокет и собственный логин tenant. Одна транзакция только для чтения сверяет заявленные даты с текущими формулами Go, различает кандидата, подтверждённое отсутствие и дату без подготовленного блока, отмечает расхождения результата и показывает состояние очереди. Это проверка одного профиля. Атомарные serve и возврат читателей реализованы; полная приёмка по актуальному реестру остаётся отдельным этапом выката.

Оба входа кандидатов используют HEALTH_SLEEP_V2_ENABLED=1 и режим профиля prepare или serve; публикация дополнительно требует HEALTH_SLEEP_SERVE_ENABLED=1. Приём совместимых метрик продолжает работать при выключенной подготовке. Мобильное обновление, приёмка профилей, мерж и production требуют отдельных действий. Экспериментальный /health/sleep/v2 остаётся входом прежней репетиции.

Защитить сравнение и переключение от конкурентных записей блокировкой или условной публикацией по версиям. Опубликовать одну согласованную ревизию для всех зависимых читателей профиля и направить записи после границы в это поколение. При несовпадении оставить прежний путь активным, обновить затронутые результаты и повторить проверку. После успеха возобновить очередь с первого пакета за границей. Контроль перед переключением и на пилоте

Для каждого активного профиля на зафиксированных входах независимо рассчитать историю Готовности и EnergyBank действующими формулами Go и сверить результат по каждой ожидаемой местной дате всего принятого диапазона. Для каждой даты проверить значение или ожидаемое отсутствие результата. После изменения диапазона проверить объединение прежних и новых дат, включая очистку выпавших. В отчёте указать ожидаемое и фактическое число сверенных дат для каждой метрики и профиля. Для сравнения живой выдачи отдельно зафиксировать один момент оценки и соответствующую местную дату профиля. По целочисленным значениям, ключам, статусам, категориям, пропускам и флагам требуется точное совпадение и ноль расхождений. Для дробных компонентов требуется |факт − эталон| ≤ max(1e-9, 1e-9 × |эталон|). Разницы с прежним путём описать отдельно через изменившиеся входы сна. Для пустого профиля отчёт подтверждает отсутствие истории и ожидаемый статус живой выдачи.

Откат

Когда начинать. Если после включения подтверждена потеря принятого пакета или задания, появились дубли, изменился наблюдавшийся снимок, нарушилась привязка профиля, смешались ревизии либо обнаружено необъяснённое расхождение с эталоном на тех же входах, немедленно остановить расширение и начать откат затронутых профилей. При первом превышении порога задержки, нагрузки или возраста очереди остановить расширение и оставить текущий пилот на одно следующее полное согласованное окно наблюдения. Если при достаточном числе синков в повторном окне превышен хотя бы один порог, начать откат. Если данных недостаточно, оставить расширение остановленным до полноценного окна. При прохождении повторной проверки расширение можно возобновить по критериям приёмки.

  1. Зафиксировать границу отката. Остановить расширение, зафиксировать последний принятый пакет для затронутых профилей, остановить обработку за этой границей и дождаться завершения активных писателей нового пути. Продолжать сохранять поступающие пакеты в устойчивой очереди. Сохранить контрольные точки и ранее опубликованное поколение для диагностики. При смене образов использовать заранее проверенную пару, совместимую с текущим контрактом схем.
  2. Подготовить прежний путь до возврата читателей. Проверить, что прежний путь актуален на той же границе и ревизии входов, если он продолжал работать во время пилота. Иначе восстановить затронутые дневные результаты и зависимые окна из сохранённых входов и догнать все пакеты до границы, включая принятые во время пилота. При восстановлении снимков изменять только синтетические строки. Если слот уже занят наблюдением, включая наблюдение из пилота, сохранить его и пропустить запись синтетического снимка. Сырьё и очередь сохраняются. Восстановление расчётов
  3. Проверить и переключить. Сверить подготовленный прежний путь на зафиксированной границе по обеим датам переноса, Готовности, текущему EnergyBank и истории наблюдений. В той же транзакции, которая возвращает читателей и писателей на прежний путь, сверить зафиксированную границу очереди, активную привязку и идентичность схемы, ревизию сна и версии всех остальных входов, использованных при восстановлении и сверке. Защитить проверку и переключение от конкурентных записей блокировкой или условной публикацией по версиям, как при прямом переключении. При расхождении вернуть прежний путь можно только после обновления затронутых результатов и повторной сверки. Очередь продолжает принимать пакеты. После успешного переключения возобновить обработку с первого пакета за границей и проверить штатный синк и повтор, свежесть, обработку очереди и сохранность наблюдений. Считать откат завершённым после этих проверок. До повторного включения разобрать причину отката и воспроизвести проблемный сценарий на изолированной базе.

Перед запуском. На репетиции проверить новые синки по обе стороны границы, изменение настройки между сверкой и переключением в обоих направлениях, запрет первого пилота при появлении непринятого профиля, смену привязки, возобновление после сбоя и откат при занятом наблюдением слоте. Отдельно проверить немедленное начало отката при нарушении целостности и остановку расширения с повторным окном при первом превышении порога. Требуется отдельное согласование производственного пути, результатов репетиции, списка профилей пилота, численных пределов и окна выката. Production и реальные данные в рамках этого обновления плана не менялись.

Точный повтор №2 сохранил ревизию сна и наблюдения.

Сверка с отдельной схемой, где ожидаемые входы заданы вручную, подтвердила Готовность и EnergyBank за 8, 9 и 10 марта. Пакет №3 обработан после возврата. Публикация сна и откат через cmd/server

Для публикации требуются оба серверных флага HEALTH_SLEEP_V2_ENABLED=1 и HEALTH_SLEEP_SERVE_ENABLED=1. Для изолированного профиля команда cmd/sleep_shadow проверяет UUID, контракт схемы и ожидаемый диапазон. Оба формата используют POST /health. В режиме serve кандидат должен иметь обычный пакет для продолжающего работать прежнего расчёта. До From действует прежний выбор сна. В диапазоне From…Through используется только опубликованная ночь: явно очищенная или отсутствующая строка скрывает прежний сон, а отсутствие результата передаётся предусмотренным статусом пропуска. После Through при наличии выбирается каноническая ночь; если её нет, допускается прежний сон клиентов старого формата. Все стадии одной даты берутся из того же результата, что и длительность.

  1. На локальном Unix-сокете под ролью tenant выполнить аудит с параметрами -audit-server-schema, -audit-server-tenant, -audit-server-from и -audit-server-through. Диапазон для включения заканчивается текущей местной датой. -rebuild-server-preparation восстанавливает зависимые результаты за уже подготовленные даты. Каждый день коммитится отдельно. При повторе совпавшие дни пропускаются.
  2. После проверки отчёта передать те же параметры и отпечаток -switch-server-evidence в -switch-server-mode serve. Под блокировками сервер заново сверяет входы, очередь и проверенные даты и одним коммитом обновляет режим и границу. Ожидающий пакет или изменившийся отпечаток требуют новой сверки.
  3. Для возврата снять свежий аудит того же диапазона. -switch-server-mode off фиксирует границу только после завершения принятых обычных пакетов и закрытия дат в журнале зависимых расчётов. Кандидаты, исходные пакеты и наблюдения остаются в базе. После возврата контрольный повтор сверяется по исходному идентификатору. Изменение глобального флага не заменяет эту процедуру.

В режиме serve штатный брифинг рассчитывает сон, Готовность и текущий EnergyBank в одном снимке базы. Наблюдение в свободном пятиминутном слоте сохраняется в транзакции кандидата. При ошибке слот и обе даты откатываются вместе, пакет остаётся в очереди. Занятый слот сохраняет наблюдение. Исторический график EnergyBank рассчитывает синтетические точки закрытия дня при чтении, сохраняя приоритет наблюдавшихся снимков. Формулы Готовности и EnergyBank остаются в Go.

Интеграционный тест использует маршруты cmd/server, штатный брифинг и PostgreSQL с двумя изолированными профилями. Проверены выключенный флаг, приоритет и запасной источник, очистка прежней даты, переход UTC → Asia/Singapore, сбой записи свободного слота, повтор пакета, отказ переключения при устаревшем отчёте, откат с ожидающим обычным пакетом и повтор после перезапуска. Интеграционный тест

После ревью локальный полный пересчёт повторно сверяет ревизии сна и отслеживаемых входов перед завершением; короткая проверка ревизии заменяет полное сканирование истории под блокировкой публикации. При смене местной даты во время ожидания публикация продолжает пересчёт до новой даты. Наблюдения в занятых слотах сохраняются. В изолированном PostgreSQL проверены права tenant на запись отслеживаемых входов без доступа к общей таблице ревизий и восстановление прежних зависимостей после возврата; отдельные детерминированные гонки полуночи и TRUNCATE пока не проверены.

После ревью точный повтор ищется по сохранённой квитанции до проверки нового формата. При неизвестной зоне корректные обычные метрики обрабатываются без подтверждения кандидата. Готовность в смешанной сессии обновляется по свежим входам, даже если дневной агрегат уже готов. Успешная замена восстанавливает ошибочный пакет только при покрытии его кандидатов и пригодных обычных метрик.

На синтетике подготовка и аудит используют ту же границу дат, что и выдача. Карточка сна показывает опубликованную длительность. Тест конкурентного отката подтверждает, что ожидавший блокировку расчёт EnergyBank записывает результат прежней ветки. Проверка графика подтверждает, что часовой пояс отображения сохраняет момент синтетического снимка.

Перед пилотом остаются подключения реальных кандидатов и приёмка истории всех активных профилей, замеры нагрузки и выбор порогов. Локальная команда сверяет каждый заявленный диапазон по одному профилю. Общий допуск по реестру остаётся шагом выката. Архитектура сна на уровне сырых сегментов и отдельные модели хронической нагрузки сохраняют свои собственные входы. Health Sync и production в этот прогон не входили.
