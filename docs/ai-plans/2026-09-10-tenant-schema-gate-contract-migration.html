Tenant schema-gate contract migration

Approval required before implementation

Task summary

Restore a deployable tenant-schema release path. The production gate correctly detects three active tenants with stale contract metadata, but its migration preflight rejects that expected stale state before attempting any tenant migration.

Observed behavior

The read-only production audit reports only contract version/checksum mismatches and the restricted verification result schema_contract_mismatch, with all 36 isolation-denial probes succeeding. prepareContractMigrationFleetSnapshot permits the former findings but rejects the latter. The current verifier uses the same result code for both a stale marker contract and unsafe structural failures such as a missing tenant table, so broad allow-listing would weaken the gate.

Desired behavior

A structurally sound active fleet with an allowed older contract may enter the existing stopped-service migration flow. Missing tenant tables, bad identity markers, access violations, changing inventory, and other unsafe conditions must still fail closed. No API, authentication, tenant authorization, or data semantics change is intended.

Likely files

  • internal/tenants/migration.go — distinguish an expected stale contract from a structural contract failure during restricted verification.
  • internal/tenants/contract_migration.go — allow only that new, migration-safe finding during fleet preparation.
  • internal/tenants/*_test.go — add regressions for accepted stale metadata and rejected missing/unsafe schema conditions.
  • docs/ai-plans/2026-09-10-tenant-schema-gate-contract-migration.html — record implementation and release evidence.

Implementation and verification

  1. Add the narrow stale-contract classification without changing authorization probes or their failure handling.
  2. Allow that classification in contract-migration preflight only; retain all other fail-closed paths.
  3. Add focused tests for the production-shaped stale contract and for a structurally missing tenant schema.
  4. Run focused Go tests, formatting, and the existing disposable-DB tenant audit/migration suite.
  5. Commit, open a focused PR, wait for required CI, then deploy via deploy-tenant-schema-gate.sh and verify post-start audit plus a live authenticated dashboard route.

Risks and rollback

Incorrectly treating all schema_contract_mismatch results as safe could migrate a malformed tenant. The fix therefore introduces a distinct reason and tests the unsafe alternative. Deployment uses the existing gate; it preserves a private recovery snapshot and never rolls back a database automatically. The production database has not been changed by the failed attempts.

Open questions

None blocking: the intended scope is limited to preserving the gate's existing contract-transition policy while making its diagnostic classification precise.

Approval gate

Do not modify production code or run a new migration until this plan is explicitly approved.
