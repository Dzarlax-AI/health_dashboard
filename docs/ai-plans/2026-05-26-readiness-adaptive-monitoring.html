Readiness Adaptive Monitoring Plan

Make the naive-layer readiness monitoring adapt to tenant-specific input freshness without hiding real data gaps. This is the implementation approval gate for the adaptive monitoring change.

Date: 2026-05-26 Repo: health_processing Scope: admin monitoring, read-only Status: implemented

Task Summary

The current monitoring flags event_window_data_missing for forward-looking targets because recent labels need future days to mature. A fixed mature-window shift improves this, but it is still not tenant-aware. The next change should compute a defensible coverage window per tenant and target using target contract lag plus observed upstream input freshness.

Current Behavior

  • Coverage currently reports over a 14-day window.
  • Forward-looking labels have expected lag: Acute Risk uses t+1..t+3; Chronic Load uses t+1..t+14.
  • A fixed mature-window branch now shifts acute by 3 days and chronic by 14 days.
  • Live SQL showed the fixed shift removes expected chronic warnings for health and health_mariia/chronic_acute_density.
  • health_mariia/chronic_label stays warning because the mature upstream Recovery window has real sleep-related gaps.

Desired Behavior

contract_end = as_of_date - target_contract_lag_days
input_stable_end = latest date where upstream inputs are stable enough
coverage_end = min(contract_end, input_stable_end)
coverage_start = coverage_end - 13 days

Monitoring should also emit a stale-input signal when input_stable_end falls too far behind contract_end. That keeps freshness problems visible instead of silently shifting the window backward.

Assumptions

  • Target writer semantics remain authoritative; monitoring must not reinterpret labels.
  • Target contract lag is deterministic and not user-specific.
  • Tenant-specific adaptation belongs in input freshness, not in target definitions.
  • First implementation can use constants for stale thresholds.

Implementation Steps

  1. Add explicit target contract metadata: floor, contract lag, and input-stability source.
  2. Extend ReadinessCoverageRow with window and stale-input fields.
  3. Implement inputStableEnd helpers per source type.
  4. Compute coverage over min(contract_end, input_stable_end).
  5. Add stale-input status thresholds: ok 0-2 days, warn 3-7 days, critical over 7 days or no stable date in 30 days.
  6. Update overall status to include stale-input status.
  7. Render evaluated window and stale-input note in the admin monitoring table.
  8. Run targeted and full test suites.
  9. Update this plan with actual changes and checks after implementation.

Risks

  • Over-adaptation could hide stale pipelines if stale-input warnings are too weak.
  • Input stability may duplicate writer assumptions if implemented too deeply.
  • UI could become noisy if every row shows too much metadata.

Rollback Plan

Revert the monitoring storage/UI commit. No schema changes or data mutations are planned, so rollback is a code-only revert.

Open Questions

  • Should the first implementation keep stale thresholds as constants, then promote them to settings later if needed?

Recommendation: fold stale-input status into coverage rows and keep thresholds as constants for the first implementation.

Implementation Result

  • Added per-target contract lag and input-stability source metadata in internal/storage/readiness_redesign_monitoring.go.

Known Limitations

  • Freshness labels are currently plain English strings in the admin fragment; they can be localized in a follow-up if this surface becomes user-facing beyond operator diagnostics.
  • The live DB sanity check used SQL equivalent to the storage logic rather than calling the HTTP endpoint against a running deployed server.
