EnergyBank v2 Verdict Bands Cutover

Approval required before implementation

Task Summary

Finish the urgent EnergyBank v2 verdict cutover by correcting how personal verdict bands are derived from energy_snapshots, then clean up stale cutover comments/docs. The dashboard already overrides v1 verdicts from v2 snapshots, but the current band calculation appears to overweight intraday rows.

Current Behavior

  • GetHealthBriefing still builds the legacy v1 EnergyBank first.
  • When a v2 snapshot exists for lastDate, internal/storage/briefing.go overrides Current, Capacity, DrainSoFar, flags, ActionVerdict, and VerdictReason.
  • The override calls ComputeUserVerdictBands, ChooseVerdictV2, BuildVerdictReasonV2, then stress-flag overrides.
  • ComputeUserVerdictBands currently computes percentiles over eligible snapshot rows directly. Multiple intraday rows for one date therefore count as multiple data points.

Evidence

Cutover code exists

briefing.go already replaces v1 verdicts when energy_snapshots data exists, so this is not a from-scratch cutover.

Band computation is row-weighted

Current query over 180 days returned n=650, p20=44, p50=59, p80=72. Distinct-date latest-row analysis from the explorer returned n=178, p20=34, p50=43.5, p80=52.6.

Formula-version mixing risk

Latest formula has only 19 distinct eligible days. That is below the documented 30-day gate, but raw snapshot rows from the same short period can make the dataset look mature.

Todoist intent

The task asks for final verdict threshold retuning after enough v2 data. The evidence says the first fix is the definition of "enough data", not manual constants.

Desired Behavior

  • Personal verdict bands should be derived from one representative snapshot per local date, not every intraday recompute row.
  • The 30-point readiness gate should count distinct eligible days.
  • Band computation should not silently mix old and current formula versions in a way that makes the latest formula look more mature than it is.
  • If the latest formula has fewer than 30 distinct eligible days, return documented defaults with NDataPoints set to the distinct-day count.
  • Dashboard and Telegram behavior should remain non-blocking: if bands cannot be computed, fall back to defaults and log.

Assumptions

  • One row per date should use the latest ts_bucket for that date, matching the daily/EOD interpretation of verdict thresholds.
  • formula_version is meaningful for threshold comparability; personal bands should prefer the latest formula's distinct-day sample.
  • Falling back to DefaultV2VerdictBands until 30 current-formula days exist is safer than using mixed or row-weighted personal bands.
  • No destructive schema migration is needed for this fix.

Likely File Changes

  • internal/storage/energy_bands.go - change the query to latest row per date and current formula gating.
  • internal/storage/energy_config_test.go or a new energy_bands_test.go - add focused storage tests around band sampling.
  • internal/storage/briefing.go - update stale half-cutover comments only if implementation confirms they are obsolete.
  • ENERGY_BANK.md and/or SCORING.md - small status correction if docs still describe this path as pending.
  • This plan file - update with actual changes and verification after implementation.

Implementation Steps

  1. Add tests that seed energy_snapshots rows with multiple intraday snapshots per date and verify percentiles count one latest row per date.
  2. Add a test where the latest formula_version has fewer than 30 distinct eligible dates and older versions have enough rows; expect default bands with the latest-version day count.
  3. Keep existing exclusions for imputed_sleep, imputed_activity, and bootstrap_tail.
  4. Update ComputeUserVerdictBands to select latest eligible formula version, then latest row per date within that formula version.
  5. Return personal bands only when the distinct-day sample is at least energyBandsMinPoints.
  6. Run focused storage tests and full go test ./....
  7. Update Todoist task status only after tests pass and the plan's completion section is filled.

Risks

  • Thresholds may move materially downward once intraday overweighting is removed.
  • Filtering to latest formula version may temporarily return defaults until 30 current-formula days accumulate.
  • Existing user expectations may have adapted to the inflated thresholds; Telegram wording should be watched after deploy.
  • Tests need to avoid brittle assumptions about exact percentile interpolation beyond the behavior under test.

Rollback Plan

  • Revert the ComputeUserVerdictBands query change to the previous row-weighted behavior if verdicts are clearly worse.
  • No schema rollback should be required.
  • If production behavior is uncertain, temporarily force defaults by raising the personal-band gate while collecting more current-formula days.
