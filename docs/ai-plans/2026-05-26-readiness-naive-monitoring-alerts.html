Implementation Plan: Readiness Naive-Layer Monitoring and Alerts

Approval required before implementation

Task Summary

Implement Readiness redesign plan §6.4: monitoring and operator alerts for the naive layer backed by target_snapshots, naive_baselines, source_epochs, and chip_calibrations. The goal is to catch data/source failures and baseline drift before they silently make dashboard chips look trustworthy.

Current Behavior

  • RunIncrementalBackfillForDatesAt already runs readiness-redesign writers after aggregate cache refresh.
  • The admin API already exposes read-only operational contract rows via /api/admin/readiness-redesign/operational-contract.
  • Binary chip cutoffs are stored in chip_calibrations and can be recomputed per tenant.
  • The admin UI can preview chip state, but it does not summarize health of the naive layer or flag coverage/drift failures.
  • Live DB check on 2026-05-26 showed current rows through 2026-05-26, but uneven recent coverage: recovery rolling_3d 80%, passive rolling_3d 60%, chronic_label 13.3%, chronic_acute_density 0% over the recent 15-row window.

Desired Behavior

Add a bounded, read-only monitoring surface that summarizes the naive layer per tenant and highlights only actionable states. It should distinguish ordinary forward-window warmup from real failures.

SignalPurposeInitial behavior
Target coverage Detect missing eligible rows by sub_score/target_kind over rolling 14 days. Warn below configured/default floor, with reason breakdown.
Positive-rate drift Detect classifier label distribution shifts versus a 90-day baseline. Warn when 30-day rate deviates by more than 2 standard errors from the 90-day baseline, only when sample size is sufficient.
Source epoch gap Detect an active epoch with an ended range and no successor. Critical alert in admin summary.
Unknown / pending chip rate Detect when chip-facing rows turn unknown or pending unusually often. Warn when recent unknown/pending rate is elevated versus rolling baseline.

Recommended Approach

Build one storage read model and one admin endpoint first. Render it in the existing admin tenant panel. Do not send Telegram alerts in the first PR unless the read-only surface proves the thresholds are sane.

This avoids creating a noisy alerting loop before we can see how the metrics behave across health and health_mariia. The endpoint response can later feed a Telegram digest or proactive notification without changing the SQL semantics.

Assumptions and Unknowns

  • Default threshold floors should be conservative and per-target, not one global percentage.
  • Forward-window targets may be legitimately ineligible near the right edge; the summary must expose eligibility reasons before declaring failure.
  • Open question: should the first implementation include Telegram notifications, or only admin UI warnings?
  • Open question: should thresholds be hardcoded constants initially or stored in settings for tenant overrides?

  • AGENTS.md and CLAUDE.md - only if the implementation adds durable operational semantics worth documenting.

Implementation Steps

  1. Define storage structs for per-tenant monitoring summary, per-target coverage rows, drift rows, source-epoch alerts, and unknown-rate rows.
  2. Add SQL helpers that operate in the tenant-bound schema and take an explicit asOfDate plus window sizes.
  3. Compute coverage over 14 days with reason breakdown from target_snapshots.eligibility_reason.
  4. Compute classifier positive-rate drift for event_t1_t3, event_strict_t1_t3, chronic_label, and chronic_acute_density when sample size is sufficient.
  5. Detect source-epoch catalogue gaps from source_epochs.
  6. Compute chip unknown/pending rate by reusing or mirroring LoadOperationalContractRows state semantics.
  7. Add the admin JSON endpoint with the same tenant scoping conventions as operational-contract: current tenant by default, explicit schema, and read-only schema=all.
  8. Add a compact admin UI panel with status chips, reason breakdowns, and last computed timestamp.
  9. Run tests and live read-only SQL checks against both tenants before considering any proactive notification follow-up.

Impact

  • Data model: no migration expected for the first PR; it reads existing tables.
  • API: one new admin-only read endpoint.
  • Auth: use existing adminGuard; no public exposure.
  • Deployment: normal Go deploy; no external services.
  • UX: admin-only diagnostic panel; no dashboard user-facing chip changes.

Manual QA Checklist

  • Admin page loads for the current tenant.
  • Tenant selector refreshes monitoring without mixing schemas.
  • schema=all works as read-only aggregation.
  • Warnings show reason breakdowns, not just red labels.
  • Forward-window ineligibility near today's date is not mislabeled as an ingest outage.

Risks and Edge Cases

  • Noisy thresholds could create false urgency; start read-only and conservative.
  • Chronic targets have legitimate forward-window lag; coverage floors must account for target type.
  • Small positive counts can make drift math meaningless; suppress drift warnings below minimum sample sizes.
  • Multi-tenant timezone differences mean all windows must anchor on tenant-local dates, not UTC.
  • Existing operational-contract state logic must not drift from the new unknown-rate calculation.

Rollback Plan

Because the first PR is read-only, rollback is a normal code revert: remove the endpoint, storage read model, UI panel, and tests. No data migration or cleanup should be required.

Open Questions

  • Should the first PR include Telegram alerts, or should alerts wait until the admin panel has been observed for a few days?
  • Should initial threshold floors be constants in Go, or tenant settings surfaced in admin?
  • Which targets should count as actionable for same-day alerts versus informational diagnostics only?

Approval Gate
