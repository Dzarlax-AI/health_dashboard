Implementation Plan: HealthKit Import Deduplication and Bulk Batching

Approval required before implementation

Task Summary

Implement issue #195: replace the current slow row-by-row Apple Health XML import path with a high-throughput staged import, and define correct deduplication/source-of-truth semantics across HealthKit XML export, native iOS health-sync, legacy Health Auto Export style ingest, Admin UI import, and CLI import.

The key product decision is that an Apple Health XML export is an authoritative HealthKit snapshot for historical backfill at the time it was exported. Live/mobile data ingested after that point is considered fresher for exact conflicts, because the mobile app reads the current Apple Health state and may include post-export corrections. Older live rows that predate the XML import may still be superseded by the export.

Inspected Current Behavior

Exact row dedup

metric_points has UNIQUE(metric_name, date, source). Production duplicate scan during the real import showed duplicate_groups=0.

Live/mobile ingest

InsertPoints uses ON CONFLICT(metric_name,date,source) DO UPDATE with special sleep guards. It already uses pgx.Batch chunks.

XML point import

BulkInsertPoints creates one health_records row per batch, then executes one INSERT ... ON CONFLICT DO NOTHING per point.

Admin UI import

Defaults are batch=500, pause=150ms. After parsing it deletes Auto Export rows for the imported date range and force rebuilds caches.

CLI import

cmd/import shares BulkInsertPoints, then runs full aggregate and score backfill.

Workouts

UpsertWorkout already updates by external_id, but it is called one workout at a time from XML import paths.

Real Import Observations

  • The July 2026 Admin UI XML import completed successfully after deployment of PR #194.
  • Final observed counts after import/backfill: metric_points=7,659,555, xml_rows=7,484,128, workouts=1,012, xml_workouts=849.
  • The import was very slow because it performed millions of row-by-row inserts and UI defaults added many small-batch pauses.
  • The current implementation did not create exact duplicate rows, but it does not encode authoritative XML snapshot semantics.

Desired Behavior

  • Apple Health XML import is authoritative for historical rows that predate the import/export snapshot.
  • Re-importing the same XML export is idempotent.
  • Importing a newer XML export can update corrected historical values.
  • Live/mobile sync keeps updating recent data, data after the export range, and exact conflicts that arrive after the XML import.
  • Admin UI and CLI XML imports share one core import implementation.
  • Large XML imports use set-based DB operations rather than per-row round trips.
  • Cache invalidation and backfill happen once after the committed import.
  • Workout XML import is batched or staged, not one upsert call per workout.

Proposed Data Model

  • Add an import_runs table for logical imports: id, origin, source_name, started_at, finished_at, status, min_date, max_date, parsed_points, inserted_points, updated_points, skipped_points, parsed_workouts, upserted_workouts, error.
  • Add coverage metadata for committed XML imports, at minimum by import_run_id, metric_name, source, and local date or compact date range. This prevents broad unsafe deletes and lets future code reason about which historical slices were actually covered by an export.
  • Add provenance columns to metric_points. Target shape is origin TEXT DEFAULT 'live', import_run_id BIGINT NULL, and possibly source_record_id TEXT later if exact HealthKit UUID-level sample IDs become available. Enforce NOT NULL and FK constraints only after safe validation, if at all.
  • Add provenance columns to workouts. Target shape is origin TEXT DEFAULT 'live', import_run_id BIGINT NULL, with the same nullable-first migration rule.
  • Create one logical health_records row per XML import run and attach promoted points to it. Do not create one raw record per parser batch, and do not relax the current non-null metric_points.health_record_id constraint in this PR.
  • Use temporary or unlogged staging tables per import transaction for points and workouts. Prefer session-local CREATE TEMP TABLE ... ON COMMIT DROP to avoid persistent cleanup risk.
  • Keep the existing exact uniqueness key (metric_name, date, source) for now. Do not attempt semantic cross-source deduplication in this PR.

Safe Schema Migration

  • Do not add large-table constraints or indexes in a way that can block production startup. metric_points already has millions of rows.
  • Prefer nullable provenance columns first, with cheap constant defaults only where PostgreSQL can apply them without a table rewrite. Enforce NOT NULL later only if a backfill and validation path is explicit.
  • If foreign keys are added from metric_points.import_run_id or workouts.import_run_id, add them as NOT VALID first and validate separately, or skip the FK in the first PR and rely on application-level writes.
  • Create any large supporting indexes with CREATE INDEX CONCURRENTLY outside the current startup DDL transaction, or document a manual one-off migration command. Small new tables may still be created by startup DDL.
  • Multi-tenant mode must create the metadata tables per tenant schema and must not assume the default health schema in SQL strings.

Source-Of-Truth Policy

  • XML import vs XML import: newer committed import wins on exact key.
  • XML import vs older live/mobile/HAE: XML wins inside the covered import range on exact key when the existing row predates the XML import snapshot.
  • Live/mobile after XML: live/mobile is treated as fresher and can continue inserting and updating rows, including exact conflicts inside a previously XML-covered historical range.
  • Live/mobile exact conflict with XML-covered historical row: keep current InsertPoints update semantics for rows arriving after the XML import. Do not add a blanket guard that freezes XML-origin rows forever; that would make HealthKit retrospective corrections from the app invisible.
  • Newer XML import vs newer live/mobile: a later XML export can still supersede live/mobile rows if it is intentionally imported as a newer HealthKit snapshot. The deciding dimension is snapshot/import freshness, not the label "XML" by itself.
  • Rows missing from a newer XML snapshot: do not globally delete by min_date/max_date. Only delete or supersede rows in coverage groups proven by staging metadata, and only where the existing row is older than the import snapshot. If exact HealthKit sample IDs are unavailable, treat deletion semantics as group-level and conservative.
  • HAE cleanup: replace broad post-hoc RemoveAutoExportForRange with transactional staged replacement where possible. If cleanup remains, make it provenance-aware and only after XML rows are safely staged.
  • Workouts: stable external_id rows continue to upsert by external_id. XML workouts with synthetic applexml: ids need covered-range replacement or a more stable identity based on immutable fields; otherwise a corrected workout can become a duplicate.

Import State Machine

  1. Create import_runs with status='running' and create one associated health_records row for the XML import in durable metadata before staging starts, so a later staging rollback can still mark the run failed.
  2. Parse XML and stream points/workouts into staging using pgx.CopyFrom or similarly set-based chunks. Accumulate coverage metadata while staging.
  3. If parsing or staging fails, rollback staged data, mark the durable run failed, do not delete old rows, and do not run cache invalidation or backfill.
  4. Promote staged points/workouts in one final transaction: conservative stale-row cleanup for covered groups, set-based upsert, import counter update, and status='committed'.
  5. Only after commit, invalidate affected aggregate rows and run one cache rebuild/backfill pass.
  6. Admin UI and CLI must use the same state machine. Differences should be presentation only: progress reporting, dry-run, and command-line logging.

Implementation Steps

  1. Add safe schema support: import_runs, import coverage metadata, nullable provenance columns, and any small-table indexes. Defer large-table concurrent indexes to an explicit migration command if needed.
  2. Create storage types for import runs, coverage rows, import freshness, and import counters.
  3. Implement a staged point import API using pgx.CopyFrom into a temporary staging table, then set-based insert/upsert into metric_points.
  4. Preserve exact deduplication with ON CONFLICT(metric_name,date,source) DO UPDATE for XML imports where the incoming XML row is authoritative.
  5. Implement conservative stale-row cleanup for staged coverage groups. Do not delete by broad date range alone.
  6. Implement staged or batched workout upsert with provenance, aggregate counters, and duplicate prevention for synthetic XML workout ids.
  7. Refactor Admin UI import to stream parser batches into the staged importer, update status from returned counters, and run one final cache rebuild.
  8. Refactor CLI import to reuse the same storage importer, preserving dry-run and logging.
  9. Remove or de-emphasize the old row-by-row BulkInsertPoints path. Keep a compatibility wrapper only if tests or seed tools still need it.
  10. Update documentation and issue #195 PR linkage when opening the implementation PR.
  11. After implementation, update this plan with actual changes, tests, and known limitations.

Data, API, and UX Impact

  • Database: Adds import metadata tables and provenance columns. Existing rows should continue reading as live/default origin without requiring an immediate full-table rewrite.
  • API: No public API contract change is expected. Admin import status may expose richer counters.
  • UI: Import should complete much faster. Defaults can move toward larger batches and pause=0 after backend throughput is fixed.
  • Deployment: Startup migrations must be safe on multi-million-row metric_points. Avoid long exclusive locks.
  • Backfill: Existing force backfill remains, but it should start only after import commit and not repeatedly during import.

Risks and Edge Cases

  • Adding non-null columns, validating foreign keys, or creating normal indexes on large tables can lock production. Use nullable-first DDL, NOT VALID constraints, and concurrent/manual indexes where needed.
  • XML authoritative updates may overwrite a live row that was actually newer than the export if freshness handling is too broad. The import must compare provenance/import timing, not only metric date range.
  • Without exact HealthKit sample IDs, authoritative deletion is necessarily conservative. Coverage-group cleanup can remove stale rows in covered groups, but it should not claim perfect sample-level reconciliation.
  • Long-running transactions over millions of staged rows can pressure Postgres. If a single parse transaction is too risky, use persistent staging keyed by import_run_id and keep only the final promote transaction short.
  • The current exact key does not deduplicate semantically identical samples across different source names. This PR should not pretend to solve cross-source semantic deduplication.
  • Set-based updates may bypass existing sleep guards from InsertPoints. This is intentional for authoritative XML import but must be called out in tests.
  • Temporary staging tables inside pooled connections must not leak between imports. Use transactions and ON COMMIT DROP.
  • Large force backfill after import can still be expensive even if insert is fast. That is separate from insert throughput.
  • Admin UI import already completed once with old semantics; follow-up migration should not attempt to rewrite that historical import automatically unless explicitly requested.

Rollback Plan

  • Keep old BulkInsertPoints available behind a narrow compatibility wrapper until staged import is verified, but do not use it for Admin UI or CLI XML imports after this change.
  • If staged import fails before commit, transaction rollback drops staging rows and leaves existing metric_points untouched.
  • If a bad import commits, rollback is data-level: delete rows by import_run_id where safe, inspect any rows superseded by the import, and restore from backup or rerun a corrected newer import. Document the exact SQL before production use.
  • Code rollback reverts storage/import changes. Provenance columns/table can remain inert because reads should not depend on them.

Open Questions

  • Should historical rows from the completed July 2026 import be backfilled with origin='apple_health_xml', or should provenance start only after this PR?
  • Should exported_at be user-supplied, parsed from XML metadata if available, or simply equal to import start time? This timestamp defines when XML is fresher than previous live/mobile rows.
  • Do live/mobile payloads expose any source-side modification timestamp, or is server ingest time the only reliable freshness marker?
  • Should Admin UI expose an explicit checkbox like "Treat this export as authoritative for covered dates" or should XML import always behave that way?
  • Should the first implementation use temp staging in one transaction, or persistent staging plus a short promote transaction if real-export imports remain long-running?
  • Can XML workout synthetic ids be made stable enough from immutable fields, or should XML workouts always use covered-range replacement for synthetic ids?
  • Do we want a separate issue for semantic cross-source deduplication by HealthKit UUID/sample metadata if Apple XML exposes enough identifiers?

Implemented Changes

  • Added storage.ImportSession for Apple Health XML imports: durable import_runs, one logical health_records row, temp staging tables, pgx.CopyFrom, coverage rows, and set-based promote.
  • Added provenance columns for metric_points and workouts, plus startup creation of import_runs and import_run_coverage.
  • Changed live InsertPoints and UpsertWorkout conflict updates to restore origin='live' and clear import_run_id, so later live/mobile data stays fresher than an older XML snapshot.
  • Implemented XML point promote with staging deduplication, conservative stale-row cleanup by staged coverage group, and conflict updates guarded by received_at <= snapshot_at.
  • After subagent code review, fixed live conflict updates to refresh received_at, so later XML imports cannot overwrite newer live/mobile corrections just because the row was originally old.
  • After subagent code review, added HealthData@exportDate extraction for XML and zip imports and pass it as snapshot_at; import start is now only a fallback when export metadata is unavailable.
  • Implemented staged workout promote and synthetic applexml: duplicate replacement by stable workout window fields.
  • Refactored Admin UI import and cmd/import to share the same staged storage path. Parse/staging errors now abort without cleanup/backfill; cache invalidation/backfill runs only after commit.
  • Kept BulkInsertPoints as a compatibility path for existing seed/helper callers, but Admin UI and CLI no longer use it.
  • Updated AGENTS.md and CLAUDE.md with the new XML import semantics.

Known Limitations After Implementation

  • XML deletion remains coverage-group conservative because Apple Health XML sample-level stable IDs are not persisted for metric points.
  • P2 follow-up: large production imports still hold a staging transaction during parse. If this is too heavy in real use, move to persistent staging keyed by import_run_id and keep only promote transactional.
  • Existing July 2026 XML-imported rows are not retroactively backfilled with origin='apple_health_xml'. Provenance starts with imports performed after this change.
