Implementation Plan: Recovery Candidate 2-of-3 Evidence

Evidence-only PR

Task Summary

Add a separate Recovery Stability candidate target that evaluates rolling_3d with a 2-of-3 eligible-night rule. The current strict rolling_3d target remains unchanged and continues to feed Chronic Load and any product surfaces.

Current Behavior

  • recovery_stability/rolling_3d requires all three forward nights t+1..t+3 to be eligible.
  • Sleep capture confidence is already written to Recovery feature payloads and target coverage JSONB.
  • The live May probe after deploy showed health_mariia strict coverage at 12/26 but candidate 2-of-3 at 24/26.

Desired Behavior

  • Add a new target kind, rolling_3d_candidate_2of3, for Recovery only.
  • Candidate target is eligible when at least two of the three forward nights are eligible; value is the mean of eligible nights.
  • Coverage JSONB records strict eligibility, candidate eligible count, missing dates, per-day reasons, and per-day capture classes.
  • Naive EWMA45 and other Recovery baselines are written for the candidate target so the probe can compare candidate target MAE against the same floor family.
  • No user-visible readiness chip, Telegram copy, dashboard verdict, Chronic target dependency, or production threshold changes.

Files Likely to Change

  • internal/storage/readiness_redesign.go - add target-kind enum value.
  • internal/storage/recovery_stability_writer.go - write candidate target and candidate baselines.
  • internal/storage/recovery_stability_writer_integration_test.go - prove strict target remains blocked while candidate target is eligible.
  • cmd/readiness_sleep_capture_probe/main.go - read candidate target rows when present and report candidate MAE vs EWMA45.
  • docs/ai-plans/2026-05-27-recovery-candidate-2of3-evidence.html - update after implementation with checks and live probe output.

Implementation Steps

  1. Add TargetKindRolling3dCandidate2of3 as a text enum constant only. No schema migration is required.
  2. Refactor Recovery rolling target construction enough to share the same per-day coverage fields between strict and candidate outputs.
  3. Save the new candidate target alongside daily and strict rolling targets.
  4. Extend Recovery naive baseline writing so candidate target receives the same floor predictions as strict rolling.
  5. Extend the sleep capture probe to report persisted candidate target coverage and MAE against ewma_45d.
  6. Run targeted tests, full tests, and a read-only probe against health and health_mariia.

Test Plan

  • go test ./internal/storage -run "RecoveryStability|ReadinessMonitoring" -count=1
  • go build ./cmd/readiness_sleep_capture_probe
  • go test ./...
  • After deploy/backfill: run go run ./cmd/readiness_sleep_capture_probe --schema health,health_mariia --from 2026-05-01 --to 2026-05-26.

Impact

  • Data model: adds new rows in existing target_snapshots and naive_baselines.
  • API/UI: no new endpoint and no user-visible behavior change.
  • Deployment: requires a Recovery backfill for target dates that should receive candidate rows.
  • Rollback: reverting the code stops writing candidate rows; existing rows are inert because no product path reads them.

Risks and Edge Cases

  • If downstream code accidentally starts using all Recovery rolling target kinds, candidate rows could pollute product logic. The PR must leave Chronic explicitly pinned to rolling_3d.
  • A 2-night mean is noisier than a 3-night mean. The probe must report MAE, not just rescued coverage.
  • Missing future days near the fresh edge should remain ineligible until the same 3-day maturity window has passed.

Open Questions

  • What MAE threshold is good enough to promote candidate 2-of-3 later? This PR records evidence but does not promote.
  • Should the candidate target later use capture confidence as a weight? Not in this PR; mean of eligible nights keeps the first evidence path explainable.

Approval Gate

The user approved proceeding with the evidence-only candidate path in chat after the deployed capture-confidence results. Implementation must stay inside this plan's non-product scope.
