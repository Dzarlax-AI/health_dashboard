Implementation Plan: DB Test Closure

Approved and implemented in bounded Makefile/docs scope

Task Summary

Finish the DB test-system work by turning the current foundation into practical test lanes with clear runtime budgets, fewer broad storage runs, and documented criteria for when the testing problem is considered closed.

Current State

  • make test-unit exists and passes.
  • HEALTH_DB_TESTS=1 is the explicit DB-test activation flag.
  • internal/testdb provides shared DB lifecycle primitives.
  • Storage and UI DB helpers now use shared package-level schemas under mutexes.
  • Representative UI DB tests pass in about 10.7s.
  • EnergyBand DB group passes under a 60s timeout after moving to testEnergyDB, but still takes about 55.6s over remote Postgres.
  • Many storage writer groups still call the broad testDB(t): acute risk, chronic load, passive efficiency, recovery stability, monitoring, operational contract, onboarding status, illness evidence, and indexes.

Desired End State

  • Developers have clear commands for fast unit, UI DB, energy DB, readiness DB, and full DB verification.
  • No routine workflow depends on a broad remote-Postgres package run.
  • The DB lanes are honest: explicit DB execution fails if DB is unavailable, and unit execution never silently pays DB cost.
  • Heavy DB groups are either split into named lanes or intentionally marked as slow/manual.
  • The remaining test debt is documented as specific follow-up work, not an open-ended “tests are bad” problem.

Target Test Lanes

  • make test-unit - pure/default suite, required in CI; runs HEALTH_DB_TESTS= CGO_ENABLED=0 go test ./....
  • make test-db - routine DB contract aggregate: test-db-ui-fast, test-db-energy-smoke, and test-db-readiness. This is the normal DB edit-loop.
  • make test-db-ui-fast - representative UI/admin DB handler checks; passed in 11.2s on the current remote Postgres path.
  • make test-db-energy-smoke - one EnergyBank verdict-band DB contract check; passed in 5.8s as part of make test-db.
  • make test-db-readiness - targeted readiness schema/baseline/calibration DB tests, not readiness monitoring and not every readiness-adjacent writer family; initial target under 90s with an explicit -run regex committed in the Makefile.
  • make test-db-ui - full ./internal/ui DB package sweep; manual/domain verification, currently about 41.4s.
  • make test-db-energy - full EnergyBank verdict-band DB group; manual/domain verification, currently about 21.8s after batching seed inserts.
  • make test-db-storage - full ./internal/storage DB package run; manual/pre-merge only, not routine dev-loop.

Implementation Steps

  1. Add named Make targets for test-db-energy and test-db-readiness using focused -run patterns. Keep commands single-lane and non-parallel. The Energy regex starts as TestComputeUserVerdictBands; the Readiness regex must be enumerated from actual test names before implementation.
  2. Run each lane once with real Postgres and collect timings. Do not run broad lanes repeatedly during implementation.
  3. For any lane over its initial budget, identify the top slow test group from verbose output and migrate exactly one group at a time.
  4. Prefer helper specialization over broad refactors: e.g. readiness-only, energy-only, UI tenant. Keep destructive DDL isolated.
  5. Document slow/manual status for any lane that remains expensive because it does real writer/backfill work over remote Postgres.
  6. Update docs with closure criteria and exact commands.
  7. Update both existing DB-test HTML plans with final timings and known limitations.

Manual QA Checklist

  • Confirm no broad go test ./internal/storage run is part of the normal dev-loop docs.
  • Confirm targeted DB lanes run sequentially and each has its own timeout.
  • Inspect leftover test schemas with the configured Postgres connection if a DB lane is interrupted.
  • Confirm shared test pools stay bounded at low connection counts.

Risks And Edge Cases

  • Over-splitting lanes can make verification confusing. Keep lane names tied to real workflows.
  • Shared fixtures can leak state. Continue using mutexes and reset-before-test; keep destructive tests isolated.
  • Remote Postgres latency may keep some DB lanes slower than ideal. Do not chase impossible unit-test speeds for tests that intentionally verify SQL behavior.
  • Broad make test-db-storage may remain manual; that is acceptable if targeted lanes are clear and reliable.

Closure Criteria

  • make test-unit passes and is the CI/default lane.
  • test-db exists, is documented, and passes as the routine DB contract aggregate without pulling full UI, full Energy, or full Storage sweeps.
  • test-db-ui, test-db-energy, and test-db-storage remain documented manual/domain sweeps.
  • DB tests cannot silently pass when explicitly requested without DB access.
  • The full storage DB lane remains manual/pre-merge, with known slow groups documented instead of hidden behind routine commands.
  • No more ad-hoc guidance like “run broad storage and hope”; every common verification need maps to a named command.
