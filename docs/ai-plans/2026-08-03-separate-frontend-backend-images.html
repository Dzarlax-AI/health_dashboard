Separate frontend and backend container images

Establish two minimal, immutable image contracts from the monorepo without changing production routing or deploying the React UI yet.

1. Task summary and boundaries

In scope

  • An explicitly named backend Dockerfile preserving both Go binaries.
  • A multi-stage Vite build with a non-root static runtime.
  • Local image build and contract-smoke commands.
  • Health endpoints, cache policy, and OCI version metadata.
  • Documentation for building and inspecting both images.

Out of scope

  • Publishing a second GHCR image lane — issue #216.
  • Production Compose, reverse-proxy, or DNS changes — issue #217.
  • Switching / from the Go UI to React.
  • Migrating the remaining settings/admin/metrics routes.
  • Changing API, database, tenancy, authentication, or secrets.

2. Current architecture

  • The root Dockerfile builds a single non-root Alpine image containing /app/server and /app/tenant_isolation.
  • The current CI smoke test and amd64/arm64 publish jobs implicitly build that root file. Production consumes the resulting backend image.
  • apps/web is a pnpm/Vite/React workspace. Its build emits dist/index.html, hashed JS/CSS chunks, and one currently un-hashed hero image.
  • Browser API calls already use same-origin /api/*. Vite only supplies a development proxy; production routing is deliberately external to the frontend image.
  • The backend already exposes /healthz and database-aware /readyz. The frontend has no runtime image or health endpoint.
  • The API contract is contracts/openapi.json, currently version 0.2.0.

The existing root Dockerfile is renamed rather than duplicated. Existing CI references are updated to Dockerfile.backend so the currently published backend image retains the same runtime behavior. Creation of a separate frontend publishing job remains in #216.

4. Static delivery and security decisions

  • Pin both build and runtime base images by digest.
  • Use pnpm install --frozen-lockfile and the repository-pinned pnpm version.
  • Build with production fixtures disabled; fixture data must never be emitted into the runtime image.
  • Move the hero image into Vite's asset graph so it receives a content hash.
  • Serve hashed assets with long-lived immutable caching and index.html with revalidation/no-cache semantics.
  • Return 404 for unknown paths in this image contract instead of silently swallowing leaked legacy routes.
  • Keep all JS, CSS, and images same-origin and baked into the image; reject any unexpected remote runtime asset reference in smoke checks.
  • Declare no frontend runtime secrets, database credentials, API keys, or tenant/schema selector.

The smoke test will assert:

  • Both images start as non-root and expose the expected port.
  • The backend still contains both executable contracts.
  • The frontend runtime contains no Node/pnpm toolchain, source tree, lockfile, or secret-like environment values.
  • Both images expose matching revision/API-contract labels.
  • Frontend /healthz succeeds; / serves the built app; a missing path returns 404.
  • Hashed assets are immutable, HTML is revalidated, and output contains no external CDN/runtime asset URL.
  • The current backend database/bootstrap/restart container smoke remains green in CI.

8. Manual QA checklist

  • Open the frontend container root at desktop and mobile widths.
  • Confirm the meadow background, readiness ring, primary cards, typography, and all three locales retain the approved visual language.
  • Confirm health-section navigation uses real icons and reflows as 4 columns on wide screens, 2 on medium screens, and 1 on mobile.
  • Confirm a standalone frontend correctly reports API unavailability rather than showing fabricated health data.
  • Inspect network requests: all JS, CSS, and images originate from the same local origin.
  • Inspect response headers for HTML, hashed assets, health, and missing paths.
  • Stop/restart both containers and confirm deterministic behavior.

9. Risks, edge cases, and rollback

  • Existing release breakage: a missed root-Dockerfile reference could stop backend CI. Mitigation: repository-wide search plus current container smoke.
  • Multi-architecture base mismatch: pinned digests must support amd64 and arm64. Verify manifests before choosing them.
  • Stale frontend shell: long-cache index.html could strand old asset URLs. Keep HTML non-immutable while hashing every asset.
  • Route masking: SPA fallback could conceal proxy mistakes. Use explicit 404 behavior until a React client-side route actually requires fallback.
  • Secret leakage: Vite variables are compile-time public. Do not accept secret build args and inspect the final image/output.
  • False compatibility: labels supplied incorrectly could claim mismatched builds. The smoke target compares required values across both images.

Rollback: before issue #216, no production service references the frontend image. Reverting this change restores the root backend Dockerfile and prior CI references. No database, API, tenant, or persistent-volume rollback is required.

10. Assumptions and open questions

  • Assumption: reverse-proxy routing will keep /api/* and legacy pages on the backend; the frontend container does not proxy API traffic itself.
  • Assumption: OCI labels are the compatibility metadata interface for #215; an HTTP version endpoint is unnecessary unless #216 proves otherwise.
  • Assumption: the primary dashboard visual output remains stable; the user-approved health-section navigation correction replaces exposed icon keys and the orphaned 3+1 grid.
  • Open question deferred to #216: final GHCR repository names, tags, provenance/SBOM publication, and cross-image compatibility-gate implementation.
  • Open question deferred to #217: exact Traefik rules, canary host/path, CSP enforcement point, and rollback switch.
