Implementation plan · 2 August 2026

Separate the web frontend and Go backend inside one monorepo

Introduce a separately built TypeScript web application without breaking the current multi-tenant backend, authentication, mobile clients, admin workflows, or rollback path. The dashboard moves first; the existing Go-rendered interface remains available while the rest of the UI is migrated incrementally.

Chosen: incremental migration React + TypeScript + Vite Separate Docker images One shared API for web and mobile

Task summary

Current state

A single Go binary owns ingestion, MCP, JSON APIs, authentication, HTML templates, embedded JavaScript/CSS, static assets, admin pages, and settings pages. CI builds and deploys one container image.

Desired state

One repository contains an independently built web application and the existing Go backend. Web and native clients consume the same explicit API contract. Frontend and backend images can be tested, released, rolled back, and developed independently.

Why the split is needed

  • The embedded template/CSS/JavaScript model is becoming a constraint on UI iteration and component reuse.
  • A dedicated frontend build enables typed API access, component tests, visual regression tests, and predictable responsive behavior.
  • Separate images prevent a frontend-only change from rebuilding or releasing the data-processing server.
  • A shared contract prevents web and mobile from gradually implementing different interpretations of health data.
  • An incremental cutover protects the recently stabilised multi-tenant and deployment boundaries.

Approaches considered

A · Rejected

Full rewrite and cutover

Move dashboard, sections, metrics, settings, admin, and login in one release.

Fast final-state arrival, but a large authentication, routing, and regression blast radius.

B · Rejected

TypeScript bundle inside the Go image

Build React and embed its output in the existing binary.

Improves frontend development, but does not deliver independent images or releases.

C · Chosen

Separate images with a strangler cutover

Add apps/web, move the dashboard first, and keep Go pages as fallback.

Small reversible steps with the intended operational boundary from the start.

Frontend boundary

  • apps/web: React, TypeScript, Vite.
  • Static production image with no database or backend credentials.
  • Same-origin calls to backend paths; no browser-visible service secrets.
  • Frontend owns presentation, routing for migrated pages, localisation, loading, empty, error, and stale states.

Backend boundary

  • Go remains the only owner of health rules, tenant resolution, authorisation, persistence, ingestion, notifications, and MCP.
  • Existing Go package layout stays in place during phase 1; moving it under an artificial folder adds no product value.
  • JSON contracts become explicit and contract-tested before more clients depend on them.
  • Legacy HTML routes remain deployable until their replacement reaches parity.

Implementation sequence

1

Freeze and document the shared client API

Inventory dashboard and section responses, extract stable transport DTOs from template-specific view models, document authentication modes, add contract fixtures, and define compatibility rules. Do not make a cosmetic endpoint rename the prerequisite for the first UI migration.

2

Create the frontend workspace and design foundation

Add React + TypeScript + Vite, typed API access, localisation, test harness, layout primitives, health score card primitives, and a deterministic readiness-ring component. Capture the current friendly background direction as source assets and tokens.

3

Migrate only the dashboard

Rebuild readiness, Energy Bank, sleep quality, health briefing, AI briefing, freshness and insufficient-data states. Preserve the rule that the dashboard leads with useful information rather than a generic “not enough data” message. Keep legacy detail links operational.

4

Split image builds and CI

Produce an immutable backend image and frontend image. Run Go and frontend checks independently, then run an integration lane that boots both images and validates routing, authentication propagation, API access, and fallback pages.

5

Canary the route split

Add the frontend service to the production compose stack, route only the dashboard to it, verify health and logs, then make the route switch. Rollback is a router change back to the still-shipped Go dashboard.

6

Migrate the remaining UI in bounded route families

Move health sections and metrics next. Move settings/admin only after read-only screens are stable. Delete Go templates, fragment handlers, and embedded static assets only after every route has an accepted replacement and rollback window has elapsed.

Test plan

Automated

  • Go unit, DB, tenant-isolation, and current UI contract suites remain green.
  • TypeScript strict type-check, lint, unit tests, and production build.
  • Contract tests validate required fields, nullability, enums, locale behavior, and additive compatibility.
  • Component tests cover loading, partial, stale, error, and unavailable signal states.
  • Visual regression tests pin ring geometry at supported breakpoints so the readiness circle cannot drift or distort.
  • Browser integration tests validate dashboard → legacy detail navigation and auth expiration.
  • Container integration tests boot both images, exercise `/`, `/api/dashboard`, a legacy Go page, `/health` auth rejection, and backend health.

Manual QA

  • Russian, English, and Serbian locale switching.
  • Desktop, tablet, and narrow mobile widths.
  • Readiness ring remains circular, centred, and correctly layered.
  • Score text alignment and vertical spacing match approved UI.
  • Fresh data, partial data, no new data, stale wearable, and AI-generating cases.
  • Authentik session, local cookie fallback, logout, and denied admin access.
  • Two tenants return isolated data under concurrent requests.
  • Old section, metrics, settings, and admin routes remain usable.

Risks and mitigations

RiskMitigationRollback signal
Tenant context is lost between proxy and API. Keep tenant resolution exclusively in the Go guard; add cross-tenant negative tests and integration probes. Any mismatched tenant identity or response immediately blocks cutover.
Browser and mobile contracts drift. One canonical contract, compatibility fixtures, additive changes by default, and shared generated or validated client types. Contract check failure blocks either image release.
Two deployments create routing ambiguity. Write an explicit path ownership table; integration-test Traefik-equivalent routing before production. 404/redirect loops, missing auth headers, or asset failures revert the dashboard route.
Frontend release depends on an incompatible backend. Publish compatibility metadata and test frontend against the intended backend image pair before deploy. API compatibility probe failure prevents promotion.
Design regresses while code is reorganised. Approve reference screenshots, component states, and visual regression thresholds before route cutover. Readiness-ring geometry, excessive whitespace, or hierarchy regression blocks UI acceptance.

Rollback plan

  1. Keep the Go dashboard route and embedded assets in the backend image during the first production window.
  2. Pin both frontend and backend by immutable image digest.
  3. If frontend health or integration probes fail, route / back to the backend without a database rollback.
  4. If an API contract regression appears, restore the previous backend digest and keep the frontend at its last compatible digest.
  5. Do not remove legacy templates until the follow-up removal issue confirms parity, usage, and rollback-window completion.

Out of scope for the first phase

  • Moving the Go module or packages solely to make the folder tree look symmetrical.
  • Rewriting health scoring, storage, ingestion, notification, MCP, or tenant-isolation logic.
  • Migrating admin mutations, import workflows, setup, and local login to React.
  • Moving the iOS source repository into this monorepo. The shared artifact is the API contract, not necessarily the client source tree.
  • Introducing a heavyweight monorepo orchestrator before the build graph requires one.
  • Removing legacy endpoints or templates during dashboard cutover.

Open questions carried into the issues

  • Whether the first formal contract remains on the current /api/* paths or introduces /api/v1/* aliases. This must be decided from the existing iOS call inventory, not by aesthetics.
  • Whether typed clients are generated from OpenAPI or validated from shared JSON Schema. The first contract issue will select one canonical source of truth.
  • The exact production frontend server image and security headers, selected and pinned during the container issue.
  • The compatibility window and telemetry threshold required before deleting the old Go dashboard.

Implementation update · issue #213

The frontend workspace and shared UI foundations were implemented on codex/frontend-workspace-foundations. This remains a development-only fixture: production routing, real dashboard composition, and separate container images are intentionally unchanged.

What changed

  • Added a pinned pnpm workspace with React, TypeScript strict mode, Vite, ESLint, Vitest, and Playwright under apps/web.
  • Generated checked-in TypeScript client types from the canonical contracts/openapi.json contract.
  • Added same-origin typed API helpers with explicit loading, ready, partial, stale, unavailable, unauthenticated, and error states.
  • Added constrained en, ru, and sr localisation plumbing.
  • Added source-owned design tokens, surfaces, status panels, supporting score cards, and a deterministic SVG score gauge.
  • Copied the approved morning-meadow asset into the frontend source tree with an identical checksum; no runtime CDN dependency was introduced.
  • Added .gitattributes with an LF policy after the clean baseline exposed CRLF drift in generated OpenAPI and shell scripts.

Verification completed

  • Full Go suite passed from the merge commit baseline after LF normalisation and again after the completed frontend changes.
  • TypeScript type-check, ESLint, 16 Vitest tests, and the Vite production build passed.
  • 17 Playwright checks passed across 320, 375, 768, 1024, and 1440 px in all three locales.
  • Geometry checks verify square bounds, shared SVG/content centre, no horizontal overflow, and no ring movement between normal, partial, and stale states.
  • Loading, unavailable, and error fixtures verify that no readiness score is fabricated.
  • Desktop and 375 px screenshots were inspected against the approved readiness-ring and morning-meadow direction; state switching was also exercised in the in-app browser with no console errors.
Known boundary: the fixture uses deterministic sample values only to exercise components. It does not yet compose the live dashboard API responses. That work belongs to issue #214. Production Traefik routing, Docker images, settings/admin pages, and the Go fallback are unchanged.
