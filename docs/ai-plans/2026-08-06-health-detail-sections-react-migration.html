Activity, Cardio и Recovery в React

Три оставшихся health-раздела переезжают на приятную визуальную линию главной и обновлённого Sleep, но собираются из одного набора компонентов. Маршруты метрик остаются отдельным следующим проходом.

1. Что делаем

/activity

Шаги, активные калории, упражнения, движение и личная 30-дневная норма.

/cardio

VO₂ max, SpO₂, частота дыхания и их персональные тренды.

/recovery

Readiness, HRV, пульс покоя, контекст сна и сохранённый AI-блок Recovery.

Не входит: /metrics, /metrics/{name}, настройки, admin, login и удаление legacy handlers.

2. Текущее состояние

  • React уже владеет / и /sleep; остальные health-разделы рендерятся Go-шаблоном internal/ui/templates/pages/section.html.
  • Backend уже отдаёт общий /api/section/{key} с summary, KPI-строками, конфигурацией графиков и пояснениями.
  • Маршруты используют разные семантики: Activity — дневной SUM, Cardio/Recovery — преимущественно AVG, readiness — виртуальный ряд.
  • Клиентская функция getMetricData() сейчас жёстко отправляет AVG; её нужно сделать параметризованной, не меняя backend-контракт.
  • Отдельный AI-блок есть у Recovery. Для Activity/Cardio отдельные AI-блоки не генерируются.

3. Визуальная и компонентная линия

Согласованная линия зафиксирована прямо в этом плане: общий порядок Hero → Context → KPI → History → Explanation и три карточки маршрутов в разделе 1. Временный сравнительный макет не требуется для понимания или реализации плана.

9. Риски и границы

  • Семантика агрегаций: ошибка AVG/SUM визуально правдоподобна, поэтому закрепляется config- и loader-тестами.
  • Ложные нули: missing points не нормализуются в 0; пустой день не становится плохим днём.
  • Слишком общий компонент: config описывает композицию, но не превращается в универсальный JSON renderer.
  • AI: отдельные Activity/Cardio блоки не добавляются в этот scope. Это самостоятельное изменение prompt/cache pipeline.
  • Большой диапазон «Всё»: отображение использует доступную дневную агрегацию и ограничивает DOM/графическую плотность, не выбрасывая исходный диапазон.

10. Rollback и деплой

Схема БД не меняется. Legacy handlers сохраняются. До cutover новые маршруты проверяются через canary rule. Route-level rollback генерирует новый release.env, который возвращает /activity, /cardio и /recovery backend’у; immutable pair digest предыдущего релиза сохраняется. Production deployment всё равно проходит обязательный tenant schema release gate и health checks.

12. Что реализовано

  • Добавлен один HealthDetailPage для /activity, /cardio и /recovery; различия задаются через HealthSectionConfig.
  • Общий loader сохраняет обязательный briefing, загружает независимые ресурсы через settled-результаты и применяет server chart contract для SUM/AVG.

  • Hero, context, KPI, графики, period picker и раскрывающиеся explainers переиспользуются всеми тремя маршрутами. Главный показатель не дублируется в KPI.
  • Добавлены normal/partial/empty fixtures, RU/EN/SR, line/bar charts и явные missing-состояния без подстановки нулей.
  • Production canary/cutover rules расширены тремя маршрутами; legacy handlers сохранены для rollback.

14. Известные ограничения и продолжение

  • «Всё» для readiness ограничено текущим backend endpoint максимумом в 365 дней; metric-графики Activity/Cardio/Recovery используют весь доступный серверный диапазон.
  • Fixtures покрывают unauthenticated на уровне page-state тестируемой логики, но не добавляют отдельную query-кнопку для этого состояния.
  • Полный dark/desktop/RU/EN/SR visual matrix остаётся частью CI и pre-merge review; текущий ручной прогон сфокусирован на наиболее рискованной мобильной композиции.
  • Следующий самостоятельный проход — React-миграция /metrics и /metrics/{name}.
