Issue 158: Subjective Signal Validation

Read-only analysis completed

Task Summary

Build a read-only validation workflow for GitHub issue #158: check whether readiness, EnergyBank, and stress-derived signals align with subjective morning check-in answers. This is evidence gathering only. The default outcome is no scoring change.

The issue precondition is strict: run the analysis only for tenant schemas with at least 30 answered subjective_checkins rows excluding late_answered. If no tenant clears the gate, the implementation should produce a short blocked-status report and stop.

Current Behavior

  • internal/storage/subjective_checkin.go stores one row per (date, source) with answers great, ok, meh, sick and status values including answered and late_answered.
  • daily_scores contains the day-level readiness cache in readiness, plus stress fields such as sustained_hr_load and stress_flags.
  • energy_snapshots contains EnergyBank v2 snapshots with date, signed bank, deltas, formula_version, components, and flags.
  • internal/storage/stress_validation.go and internal/storage/stress_observability.go already provide read-only stress validation primitives, but they do not use subjective check-ins.
  • Existing analysis scripts under analysis/phase* use direct psql subprocess calls, libpq env vars, deterministic splits, and Markdown reports. This task can follow that pattern without touching production server paths.

Analysis Design

Primary Cohort

  • subjective_checkins.answer IS NOT NULL
  • status <> 'late_answered'
  • source = 'telegram' unless future sources are explicitly included
  • Join on local date to daily_scores.date and latest EnergyBank snapshot for that same date

Metrics

  • Counts by answer and excluded status
  • Median, IQR, min/max by answer bucket
  • Pearson and Spearman readiness-vs-ordinal correlations
  • Stress flag prevalence by answer bucket
  • meh/sick detection counts for low readiness, rest/active-recovery EnergyBank verdicts, and stress flags

The report should avoid personal dates in the headline tables where possible. If date samples are needed for debugging, show small anonymized examples such as relative row numbers or redact exact dates in the public issue comment.

Risks and Edge Cases

  • Small sample sizes can produce unstable correlations. Mitigation: hard precondition at 30 rows, report confidence limitations, and avoid threshold tuning.
  • Subjective answers may be imbalanced, for example many ok rows and few sick rows. Mitigation: report bucket counts and avoid over-reading sparse buckets.
  • EnergyBank intraday snapshots can overweight busy sync days. Mitigation: latest snapshot per local date only.
  • Readiness and EnergyBank may intentionally disagree on illness-safe days. Mitigation: report each signal separately and avoid declaring one canonical "truth".
  • Exact dates and tenant names are sensitive. Mitigation: anonymize schema labels and avoid publishing row-level raw data.
