План исправления Telegram webhook после переноса UI на API

Одобрено и выполнено 5 августа 2026

Краткое описание

Вернуть Telegram callback-кнопкам рабочий публичный маршрут, не открывая остальные /api-эндпоинты. Исправление ограничивается отдельным Traefik router для /api/telegram/webhook/ и controlled recreate только контейнера health-receiver.

Подтверждённое текущее поведение

  • Production Compose отправляет весь обычный /api через middleware authentik-auth.
  • Telegram присылает X-Telegram-Bot-Api-Secret-Token, но не X-API-Key, поэтому не попадает в существующий machine/API-key router.
  • Публичный /api/telegram/webhook/… сейчас возвращает 302 на Authentik.
  • Go backend успешно монтирует webhook handler при старте, но в логах после отправки опроса нет входящих callback-событий.
  • Оба production-контейнера healthy, restart count равен нулю; ошибки Gemini 503 к callback-проблеме не относятся.
  • Локальный personal_ai_stack/deploy/health/docker-compose.yml совпадает с production-копией по содержимому.

Желаемое поведение

  • Только /api/telegram/webhook/ маршрутизируется прямо в Go backend без Authentik.
  • Защита остаётся двухуровневой внутри приложения: секретный сегмент URL и constant-time проверка заголовка Telegram.
  • Остальной /api продолжает использовать Authentik либо существующий X-API-Key router.
  • Нажатие актуальной кнопки сохраняет ответ, закрывает spinner через answerCallbackQuery и запускает положенный report flow.

Предположения и неизвестные

  • Используем PathPrefix(`/api/telegram/webhook/`), потому что handler ожидает секрет после завершающего slash.
  • Router получит приоритет выше browser API и API-key routers; предлагаемый приоритет — 320.
  • Смена labels потребует recreate только health-receiver; отдельный restart Traefik или Authentik не нужен, так как Traefik читает Docker labels динамически.
  • Старый Telegram update может быть уже просрочен. Финальная пользовательская проверка может потребовать новую кнопку или повторное нажатие сегодняшней.

Шаги реализации

  1. Добавить к health-receiver router health-telegram-webhook с HTTPS, host rule и точным path prefix; не назначать ему Authentik middleware.
  2. Оставить service target health-backend, TLS resolver и существующие browser/API-key routers без изменений.
  3. Проверить итоговый Compose с текущим release.env; убедиться, что секретные значения не выводятся.
  4. Повторно сравнить локальный Compose с production и загрузить только проверенные non-secret config files; production .env не трогать.
  5. Зафиксировать текущий immutable backend image и выполнить controlled recreate только health-receiver с тем же image reference.
  6. Провести postflight: container health, restart count, logs, HTTP routing и реальное нажатие Telegram-кнопки.

Влияние

  • Auth/permissions: публичным становится только endpoint, уже защищённый двумя Telegram-specific секретами внутри Go.
  • API: payload и response contract не меняются.
  • Данные/миграции: отсутствуют.
  • Deployment: краткий recreate backend-контейнера; frontend, PostgreSQL, Traefik и Authentik не перезапускаются.
  • UX: callback spinner закрывается, ответ опроса сохраняется, появляется локализованный Telegram toast.

План проверок

До production

  • docker compose --env-file release.env config --quiet в локальном deploy-каталоге.
  • Проверка rendered labels: новый router не содержит middleware; browser API router сохраняет authentik-auth.
  • Статическая проверка, что rule ограничен /api/telegram/webhook/, а не всем /api.

Production postflight

  • docker inspect: backend running/healthy, ожидаемый immutable image, без restart loop.
  • GET /healthz возвращает 200.
  • Запрос к webhook path с неверным секретом возвращает backend 403, а не Authentik 302.
  • Обычный browser /api без сессии по-прежнему перенаправляется в Authentik.
  • После нажатия актуальной кнопки Telegram прекращает spinner и показывает подтверждение; backend не пишет save/ack errors.

Риски и граничные случаи

  • Слишком широкий bypass: исключается точным path prefix и отдельной проверкой rendered rule.
  • Потеря защиты webhook: middleware снимается только на proxy-слое; обе Go-проверки остаются.
  • Случайная смена image: перед recreate сверяется текущий digest и используется тот же immutable reference.
  • Короткая недоступность backend: ограничивается recreate одного контейнера и контролируется healthcheck.
  • Старые кнопки: cross-day callback намеренно отклоняется stale-date guard; QA проводится на актуальной кнопке.

Rollback

  1. Вернуть предыдущий production Compose без router health-telegram-webhook.
  2. Recreate только health-receiver на том же immutable image.
  3. Проверить healthy state и восстановление прежнего 302 поведения webhook path.

Откат не затрагивает БД и не требует rollback данных.

Открытые вопросы

  • Блокирующих вопросов нет. Предлагаемый scope — один Compose router и production verification.
  • Отдельным follow-up можно добавить source-controlled regression harness для production routing; текущий personal_ai_stack deploy mirror не содержит такого тестового набора.
