Browser API session recovery

Prepared 2026-09-10 · Status: PR #241 review remediation implemented and verified locally; production deployment remains unapproved.

PR #241 review remediation — approval required

Review confirmed three gaps in the initial implementation. No source change for these findings has been made yet. This section supersedes the earlier “Open questions” and “Approval gate” for the remediation scope below.
  1. P1 — identity-header spoofing: guard currently accepts X-authentik-username and X-authentik-email on any request from a configured proxy CIDR. The new API and machine routers no longer run ForwardAuth, so an externally supplied identity header can reach that trust check through Traefik. The server must treat ForwardAuth identity as invalid on every /api/* and /health/* request, before username/email tenant lookup. Those requests must then require their explicit opaque-session, API-key, or endpoint-specific authentication mechanism.
  2. P2 — React entry routes: only DashboardApp starts recovery. Direct SPA entries such as /sleep, /activity, /cardio, and /recovery receive a valid Authentik document response but then render their sign-in fallback after the first API 401. Session recovery must be shared by every React data-loading page, with the same once-per-tab loop guard.
  3. P2 — legacy chart fetches: the Go dashboard can lose its local cookie after its document has rendered. static/charts.js currently parses the resulting 401 as data, which leaves charts empty. Its browser API calls need the same one-time document navigation through /auth/session.

Observed behavior

The React dashboard loads its mandatory /api/health-briefing request through Traefik's authentik-auth ForwardAuth middleware. When Authentik returns a login redirect, browser fetch follows it cross-origin and fails before a Response reaches the client. The UI consequently displays the raw message Failed to fetch.

Production evidence on 2026-09-10: the same browser route returned both 302 and 200 within seconds; the backend was healthy and no API 5xx responses were observed. This is an interactive-auth redirect path, not a health-data or insight-generation failure.

Desired behavior

  • Existing opaque Health browser sessions remain usable for their intended 30-day lifetime even when an Authentik SSO session is briefly absent or renewing.
  • Protected document routes continue to use Authentik ForwardAuth.
  • Browser API requests without a valid Health session or API key return a same-origin machine-readable 401, never a cross-origin Authentik redirect. ForwardAuth identity headers are accepted only by protected non-API document requests, including /auth/session.
  • The SPA makes one safe top-level navigation to restore SSO on a real 401; if sign-in cannot complete, it shows the existing sign-in state rather than retrying indefinitely or hiding an outage.

Recommended design

Do not add a background Authentik keepalive. It cannot make a cross-origin redirect fetchable and would create avoidable auth traffic. Keep Authentik on document routes; let the backend enforce the existing opaque, tenant-aware session cookie on /api/* after initial SSO has issued it.

Remove authentik-auth only from the browser-API Traefik router. The API remains protected by the Go guard through an API key where applicable or the opaque server-backed session cookie. The guard must reject ForwardAuth identity headers on /api/* even when the request peer is a trusted proxy. Change the unauthenticated API branch from a redirect to a JSON 401; preserve trusted identity handling and redirects for document navigation.

Risks and controls

Removing proxy ForwardAuth from an API route is security-sensitive. It is acceptable only if the backend guard remains fail-closed and ForwardAuth identity is categorically excluded from API authentication. The plan explicitly tests no-cookie and spoofed-header denial, valid local-session/API-key controls, and protected document-route identity handling before release.
  • Do not add credentials to browser storage or synthesize Authentik headers.
  • Do not broaden the unauthenticated route; /api/telegram/webhook/ and the existing API-key route retain their separate security contracts.
  • Do not automatically retry arbitrary network failures: a 5xx, offline state, or TLS failure must remain distinguishable from reauthentication.

Rollback

Restore the prior immutable release pair and reattach authentik-auth to health-browser-api. The change is additive to session handling and requires no database migration.

Actual implementation

  • Removed authentik-auth only from health-browser-api. Frontend pages, assets, legacy routes, and all other services remain protected by ForwardAuth.
  • Made the Go guard return 401 application/json with Cache-Control: no-store for unauthenticated /api/* requests. Document requests still redirect to login; setup navigation is unchanged for document requests.
  • Added the Authentik-protected backend route /auth/session. It lets the Go guard mint or refresh the opaque local session from trusted ForwardAuth headers, then safe-redirects to the original SPA path.
  • Added a per-tab, one-time SPA recovery navigation on a real 401 through /auth/session. A successful authenticated load clears its marker; a repeated failure shows the existing sign-in fallback rather than looping.
  • Added focused backend, browser recovery, and Traefik route assertions.
