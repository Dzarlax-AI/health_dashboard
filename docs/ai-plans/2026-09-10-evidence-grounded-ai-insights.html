Задача

Сделать один общий и три доменных инсайта (сон, восстановление, энергия) полезными для чтения дня. Они должны объяснять картину и связь сигналов, а не повторять уже показанные на экране цифры или карточки.

Сервер остаётся источником фактов, статусов данных, доказательств и разрешённого действия. AI получает только подготовленный evidence-пакет и пишет краткую интерпретацию в заданных границах.

Продуктовая граница: личное наблюдение, не медицинский мониторинг

Это пользовательский помощник для регулярного наблюдения за своим состоянием и привычками. Его задача — помочь заметить паттерн, понять, насколько он подтверждён, и выбрать спокойный следующий шаг. Это не диагностика, не клиническая система мониторинга и не оценка того, «здоров» ли пользователь.

Пересмотр B1 после prompt-system review

Причина: текущий provider path не генерирует пользовательский текст: prompt предписывает «не писать прозу», а schema принимает только template=server_default. Поэтому смена модели или полировка шаблонов не может сделать инсайт живым.

Новое решение: первый production срез хранит четыре независимых narrative slot-а: overall, sleep, recovery и energy. overall появляется лишь когда уже выбранный сервером DailyDecision опирается минимум на два свежих domain claim-а и связывает их в картину дня. Каждый domain slot появляется только при собственном distinct server-approved meaning — не ради пересказа карточки. Режим дня, recommendation и action остаются server-owned. Модель не получает права создавать claim, причинную связь, действие, диагноз, прогноз или объяснение внутренних правил.

Независимое обновление: factual response и server recommendation пересчитываются сразу после нового состояния данных. Изменение сна обновляет только sleep и, если состав решения изменился, overall; аналогично для восстановления и энергии. Worker запускается асинхронно с коротким debounce. Старый текст может остаться в audit storage до replacement, но при несовпадении hash не рендерится: экран сразу показывает полезный deterministic server text. Невалидный или failed результат не скрывает серверную картину дня.

Durable shape: factual daily_insight_bundles остаётся одним current snapshot, а AI lifecycle хранится в additive daily_insight_narrative_slots с ключом (date, lang, slot). В строке лежат current input hash, hash текста, generation state, lease/backoff и provider fingerprint. Поздний ответ не может заменить новый текст того же slot-а, а изменение одного domain не инвалидирует несвязанные domain slots.

Важно: это не свободное творчество поверх чисел. JSON Schema и claim IDs проверяют форму, но не доказывают смысл; runtime validator обязан проверить coverage обязательных claims, сохранение required qualifiers, ссылку каждого предложения на допустимый meaning_link и отсутствие новых чисел, периодов, причинности или action. Внутренние safeguards не становятся пользовательской прозой: если результат не проходит проверку, устарел или provider недоступен, отображается полезный deterministic server text. Этот раздел заменяет прежние положения плана о B1 как о framing_id-only overlay.

Модели: явное распределение задач и границы

Ключевое правило: модели не определяют физиологические факты, eligibility, action, качество данных или user-facing fallback. Они либо помогают разработке, либо выбирают framing из уже закрытого серверного каталога. Любая задача без модели должна оставаться полностью работоспособной.

Onboarding: ценность до персонального baseline

Новый пользователь не должен вручную запрашивать полгода истории и не должен ждать накопления 60 ночей, чтобы получить полезный экран. После первого успешного подключения Health Sync автоматически запускает один foreground sleep-only backfill последних 90 tenant-local дней. Он использует уже выданное HealthKit-разрешение, не включает workout/vitals replay, не блокирует обычную свежую синхронизацию и хранит account-scoped pending/completed state. Ошибка или остановка приложения оставляет pending, поэтому следующая foreground/manual sync безопасно повторяет попытку; успешный source query и server receipt помечают job completed. Существующая конфигурация с уже сохранённым checkpoint мигрируется в not_required, чтобы обновление приложения не отправило историю повторно без намерения пользователя.

120 дней остаются ручным диагностическим пределом для availability/research, а не onboarding requirement. Автоматический backfill уважает выключенные syncOnLaunch или sleep permissions: в этих режимах он не инициирует скрытый upload. После включения сна первый явно запрошенный или обычный foreground sync завершает pending job.

Главный serving-инвариант: ответ есть всегда

Eligibility ограничивает силу утверждения, а не право пользователя получить ответ. Каждый visible primary/domain section обязан иметь непустые title, observation и meaning, независимо от provider, feedback и наличия персонального sleep claim. insufficient_data — внутренняя точность ответа, не пользовательская фраза «я не знаю» и не пустая карточка.

Feedback — дополнительный, а не управляющий сигнал

Telegram/web check-in доброволен. Его отсутствие, задержка или непрочтённое уведомление никогда не меняют answer_kind, eligibility, action, battery, readiness или доступность экрана. Ответ, пришедший после показа текущего insight, не может повлиять на этот же insight. Только историческая серия явно записанных voluntary labels может позже участвовать в offline calibration/evaluation с версией модели; serving продолжает работать на объективных данных, если labels нет вовсе.

Текущее поведение — подтверждено в исходниках

  • BuildDailyInsightSnapshot строит primary и ровно три домена из HealthBriefing; видимый текст сейчас серверный.
  • GenerateDailyInsightNarrative требует вернуть только template: "server_default" и evidence IDs. ApplyDailyInsightNarrative намеренно не меняет слова на экране.
  • React использует primary.observation в hero и domain.insight.observation как дополнительную строку карточки. Дублирование фактической строки уже подавляется.
  • Отдельные жизненные циклы cache/lease/CAS/backoff для narrative уже есть; запрос остаётся асинхронным, а детерминированный fallback показывается сразу.
  • Legacy headline sleep_debt — отдельный однодневный пороговый сигнал, а не персональный reference. Поэтому он не может быть источником нового sleep-claim или AI-пересказа в hero без канонического основания Фазы A/B0.

Проверка сценария Bevel и фактическая калибровка

В текущем HealthBriefing есть последняя длительность сна, rolling average, SRI и rule-based headline sleep_debt. Но это не персональная модель накопленного sleep debt: старая логика срабатывает по одной ночи ниже фиксированного порога. В Today input также нет канонического bedtime: есть derived wake_time, однако время засыпания и его отклонение не передаются в snapshot.

Проверка на 180 исторических календарных днях показала, почему нельзя подменять потребность медианой или 75-м перцентилем. Правило «3 из 4 ночей на 0.5 ч ниже p75» сработало в 101 из 172 пригодных дней; то же правило относительно медианы — в 45 днях и девяти эпизодах. После строгих quality gates осталось 20 срабатываний на 92 днях, а на отдельно извлечённой ночной длительности — лишь 3 на 60. Это частотная проверка, не доказательство физиологической точности.

Критический блокер: агрегированная дневная и отдельно извлечённая ночная длительность расходятся более чем на 30 минут в 37 из 178 сопоставимых дней; в восьми ночная величина выше дневной. Неполная запись сна тоже встречается. Пока источник, дата ночи и статус полноты не унифицированы, их нельзя молча смешивать, превращать в нулевой сон или использовать для банка.

Следовательно, новый текст не может честно обещать «сохраняющийся дефицит», «телу нужно …» или повторить конкретное время засыпания. Это обязательная часть data model, а не работа для prompt.

Решение по результату: не включать B0 по этому proxy и не калибровать порог 0.5 ч под эти 85 check-ins. Сначала завершить Фазу A, получить явный completeness marker и повторить replay на canonical rows. Только затем применять проверку полезности на outcome, существующем до показа соответствующего insight.

Временная граница. B0 финализирует запись не раньше 18:00 на D, тогда как timely check-in относится к утру D. Их текущая пара может описывать только ретроспективную связь, но не способность B0 заранее предсказать это утро; она не меняет время финализации. Для Фазы D каждая observation обязана хранить input_available_at, prediction_at и outcome_at; поздняя правка ночи не может попасть в более ранний прогноз. Historical check-ins остаются exploratory, не запечатанным validation set. Такая последовательность допустима только в исследовании: check-in никогда не является prerequisite serving-ответа. Эффект wind_down — отдельный future exposure/outcome experiment, а не вывод из связи сна с самочувствием.

Последовательность следующих экспериментов

  1. До UI-работы проверить, может ли контролируемый ingest adapter ретроспективно выдать coverage commitment старых ночей или он появится только для новых sync generations. Backfill сам по себе не создаёт отсутствующую гарантию: без исторического восстановления первый definitive B0 reference теоретически возможен не раньше 64-й новой даты (60 reference + 4 current). Число 78 было минимумом удалённой политики «14 известных false» и не является прогнозом нового action. Новая cadence не требует дополнительной серии known-false, но фактический первый action всё равно требует вечернего true.
  2. После producer contract собрать 108-day availability report по настоящим complete+plausible+final ночам: раздельные причины unknown (нет coverage commitment, недостаточный reference, непригодна current-four-night, несовместим epoch) и число action events по семидневной cadence. Для каждого true без action report отдельно показывает recent final true либо вне-вечернее время; unknown остаётся coverage-метрикой, а не blocker.
  3. Не менять B0 threshold по историческим ответам. Для prospective cohort можно предложить утренний timely check-in до показа report/insight как voluntary research label, но ни ответ, ни action не ждут его: пропущенный или поздний label остаётся missing. Для sleep-state отдельно собирать сонливость, время после пробуждения, кофеин, болезнь и помеченный как non-PVT reaction test.
  4. Сравнивать по временным holdout-блокам три заранее фиксированные модели: последняя ночь, simple duration balance и candidate history model. Нулевая или неустойчивая прибавка к независимому outcome означает, что сложная модель не выходит в dashboard.

Воспроизводимость. Один production tenant; окно ночного proxy: 13 февраля — 11 сентября 2026. Переход знаменателей: 210 distinct source-priority days → 180 дней с daily sum в [3,14] ч → 118 дат, для которых существует 93-day lookback evaluation → 85 timely paired check-ins. timely = subjective_checkins.status='answered'; low-wellbeing = sick или meh; late/expired не входят. Сам read-only replay использует health.metric_points и health.subjective_checkins; health.daily_scores читалась только для отдельного coverage audit. Raw payloads, UI events и provider output не читались, production-данные не изменялись.

Научная граница будущих моделей

Доказано для плана: накопительную историю сна разумно исследовать отдельно от простой суммы часов. UMP валидировалась на трендах PVT при разных расписаниях сна/бодрствования; это делает её кандидатом для сравнения моделей влияния на внимание, но не формулой универсального «долга организма». Kitamura et al. оценивали optimal duration через несколько последовательных ночей расширенной возможности сна; это поддерживает метод калибровки, но не даёт норму для consumer dashboard.

Не считать доказанным: окно Oura/Bevel, их веса, Sleep Needed и банковскую формулу. По публичной документации Oura использует 14 дней и требует минимум пять ночей, а Bevel публично различает Goal, Needed, Debt и Bank; это UX-прецеденты, не переносимая научная спецификация.

Будущая проверка: не ограничивать сон специально. Собрать естественные наблюдения, до показа любого balance/state — отдельную самооценку сонливости, время после пробуждения, кофеин, болезнь и необычный график; опциональный короткий reaction test пометить как неэквивалентный лабораторному PVT. Сравнивать модели только по последующим временным блокам, без утечки будущих данных, с baseline «последняя ночь» и простыми balance-моделями. Если история нескольких ночей не улучшает прогноз независимого outcome, сложный state не становится dashboard feature.

Фактический статус реализации · 12 сентября 2026

Дополнение B1: реализованы non-serving historical materializer и anonymized candidate exporter. Они читают только retained cache/derived state, не читают raw payload, не создают bundle/provider request/tenant write и заменяют даты, IDs, values, units и display copy до записи candidate file. Они прошли live read-only smoke через tenant-authorized Compose Postgres; это не production rollout и не quality approval.

Готово в коде: Phase A/B0 и safety ladder. Сервер принимает versioned coverage commitment от Health Sync, связывает его с точной raw-точкой night_sleep_total, строит canonical completed_night_sleep, пересчитывает последние 108 дат при startup и не реже раза в минуту, а после 18:00 tenant-local переводит запись в final. Нулевая или неоднозначная длительность не становится завершённой ночью.

Serving: каждый primary/domain insight имеет typed answer_kind и непустой deterministic fallback. B0 выключен tenant flag по умолчанию; при включении он добавляет только recent_sleep_below_reference и вечерний wind_down на каждом confirmed current-evening claim. Отдельный action_event сохраняет семидневную cadence лишь для reporting/delivery. Normal B1 выключен: provider не вызывается без отдельного quality gate; tenant-only preview не является этим включением.

B1 локально: serving реализован как четыре independently cached slot-а: overall объясняет только уже server-owned DailyDecision, когда решение действительно объединяет минимум два свежих domain context; самостоятельный provider slot сейчас допускается только для сна с distinct server-approved смыслом. Одиночные recovery score и energy verdict остаются полезными deterministic карточками: они могут быть фактологическим основанием общего combined decision, но сами по себе не являются связью, ради которой нужно генерировать текст. Каждый provider slot получает closed rich packet: локализованные facts с разрешёнными display values, одну server-selected story relation и, при наличии, уже выбранное действие. Модель пишет один дружелюбный абзац в 1–3 предложения; она не может добавлять число, расчёт, причинность, диагноз, прогноз или действие. Validator проверяет cited IDs, язык, разрешённые числа и конкретные product anti-patterns; невалидный или устаревший overlay не скрывает server text. Независимые material hash, CAS lease/backoff и lifecycle сохраняют изоляцию: позднее изменение сна обновляет sleep и связанный overall, но не recovery. B1 boolean сам по себе недостаточен: сервер принимает corpus/evaluation artifact, повторно проверяет canonical checksum, три reviewed run и quality rule, сохраняет только approval metadata; до этого попытка включения получает 409. Approval привязан к exact provider/model/reasoning и SHA-256 literal prompt/response-schema/claim-packet contract; смена runtime-конфигурации или статического contract снова оставляет B1 выключенным до нового review. Эту проверку повторяют и HTTP, и background derived-state worker непосредственно перед provider generation. Normal tenant flag не включался; health использует только явно отмеченный preview.

Phase C локально: добавлены чистое вычислительное ядро manual versioned Goal и 14-day sleep_duration_balance, additive tenant-schema contract (текущая версия v11 после последующих B1 additions), iOS adapter contract и tenant-scoped API. iOS передаёт только полные tenant-local noon-to-noon coverage periods и source-selected, непересекающиеся asleep episodes; нулевой список episodes для полного period означает «сон не наблюдался», а отсутствие period остаётся unknown. Эти period commitments считаются содержательным upload и отправляются даже при нуле metric samples; это не даёт потерять известный пустой период в обычной синхронизации. Явный full resync имеет приоритет над одноразовым onboarding sleep-history job и не дублируется вторым проходом. Сервер атомарно заменяет один period при новой generation, пересчитывает materialized balance и отдаёт GET /api/sleep/balance, GET/PUT /api/sleep/goal. Баланс режет episodes по noon-to-noon окнам, включает прошлодневный nap ровно один раз, сохраняет complete outlier как low_confidence и возвращает incomplete без подстановки среднего при missing coverage или Goal. React presentation выводит эту границу явно и позволяет пользователю задать manual Goal от явной effective date; nullable wire-fields в OpenAPI означают «не оценивать», а не ноль. iOS read-only presentation отображает тот же server-owned balance, current Goal и incomplete/low-confidence boundary; редактирование остаётся web-действием, чтобы нативный dashboard не получил второй расходящийся write-flow. Исходники adapter готовы локально, но на физическое устройство и в production они ещё не устанавливались. Read-only сверка production schema 12 сентября подтвердила, что completed_night_sleep, sleep_period_coverage и sleep_duration_balance_snapshot там ещё отсутствуют: fleet migration и rollout действительно не выполнялись.

Статус-коррекция 14 сентября, production schema visibility: прежняя проверка выше остаётся историческим снимком 12 сентября. Новый read-only запрос к pg_catalog через tenant connection подтвердил наличие в schema health всех семи Phase A/C/B1 tables: completed_night_sleep, night_sleep_coverage_commitments, daily_insight_narrative_slots, sleep_period_coverage, completed_sleep_episode, sleep_goal и sleep_duration_balance_snapshot. У этого connection нет прав читать tenant settings, __tenant_identity или строки canonical sleep, поэтому результат не доказывает fleet audit, contract version/checksum, backfill, adapter coverage либо B0/B1 enablement. Их нельзя считать завершёнными без privileged tenant audit и availability report.

Контракт и проверка: добавлены schema-contract tables, required DB target, OpenAPI/client types, RU/EN/SR rendering, Health Sync coverage payload и unit/integration tests. Локально прошли релевантные Go package tests, contract generation/check и TypeScript typecheck плюс web tests (115 tests). Новый обязательный routine DB target проверяет на disposable schema PUT/GET /api/sleep/goal и GET /api/sleep/balance: Goal сохраняется, а без coverage ответ остаётся incomplete с JSON null, не выдуманным нулём. Полный iOS suite намеренно не запускался; на iPhone Simulator прошли focused NightSleepCoveragePayloadTests и SyncAttemptStateTests, включая no-empty-period-loss, noon-to-noon boundary, automatic 90-day sleep history, retry и приоритет ручного resync. Отдельный server parser test подтверждает, что тот же complete empty period принимается без metric points.

Остаётся до включения для пользователя: подготовлен CLI evaluator для замороженного B1 corpus: offline --validate проверяет и печатает checksum без provider key, а затем evaluator валидирует размер, требует narrative-eligible case в каждой из RU/EN/SR и проверяет обязательные product states, не принимая их только по labels — complete/incomplete/no-data sleep, limited history, late update и recovery/energy conflict должны совпадать со snapshot/provenance. Он запускает ровно три независимые generation для каждого eligible slot-а и кладёт рядом deterministic fallback для человеческой оценки. Отдельная проверка review привязывает оценку к checksum corpus, не даёт удалить неудобные cases и требует per-slot worksheet: верность claim/qualifier, безопасность, added meaning, semantic duplication с hero/card и язык. Improvement вычисляется только если все три прогона всех eligible slot-ов прошли этот rubric; порог — 70% pre-frozen eligible denominator, а all-cases rate публикуется отдельно. Draft v4 нельзя использовать: он не содержит нового overall context и имеет прежнюю identity. Нужны fresh candidate export, new frozen corpus и external review; даже положительный эксперимент не заменяет human product scoring и не включает tenant flag. Для Phase A теперь есть read-only daily_insight_availability: он повторяет B0 по canonical rows за 108 дней и выдаёт только aggregate states/reasons/action suppressions, поэтому post-migration product review не зависит от ручного proxy SQL. Далее нужно выполнить остановленную tenant schema migration через штатный fleet gate, проверить per-tenant adapter coverage и сгенерировать этот 108-day availability report, повторить DB integration в подтверждённой disposable schema, затем провести authenticated UI acceptance. Эти шаги не заменяются успешной сборкой и не должны обходиться включением флагов.

Предлагаемый контракт

  1. Сначала сервер строит версионированный DailyInsightNarrativeInputV2, не display snapshot: input_version, locale, tenant-local date, дискретную day_phase, типизированные факты с периодом наблюдения/coverage/provenance и вычисленные отношения.
  2. Serving policy до claim policy. Сервер выбирает answer_kind из ladder выше до обращения к provider и всегда рендерит deterministic observation+meaning. Claim catalog повышает ответ от factual/provisional до confirmed personal; он не может сделать section пустой. data_guidance получает machine-readable gap_reason и optional remediation_id, но текст/действие выбирает закрытый server catalog. Health/action и data-remediation различаются типом, visual treatment и evidence: «сделать вечер тише» никогда не маскируется под «заверши синхронизацию».
  3. Фаза A — каноническая ночная запись. Ввести schema-contract table completed_night_sleep с ключом wake_date D и полями: duration_hours, source, source_epoch, input_hash, capture_completeness, duration_assessment, claim_eligibility, observed_at, finalized_at, algorithm_version, diagnostics. Это единственный вход Фазы B; daily_scores.sleep_total, display sleep card и nap никогда не используются как fallback.
  4. Алгоритм Фазы A. D — tenant-local дата окончания night_sleep_total, заданная versioned producer contract отдельно от UTC/text prefix. Контракт реализует наш controlled Health Sync/ingest adapter, а не требует от Apple Health или устройства необратимого vendor-флага: он передаёт покрытый ночной interval и sync generation, то есть «complete as of generation». Позднее изменение от vendor создаёт новый input_hash и переоткрывает record. Запись старого формата, для которой это соответствие нельзя доказать, не угадывается по префиксу даты: она остаётся missing для definitive claim, но текущие factual cards продолжают работать. Кандидат принимается только из metric_points с metric_name=night_sleep_total, quality=ok и одной однозначной positive duration. quality=ok — только existing hard-impossible value gate; он не доказывает coverage. capture_completeness=complete возникает от coverage commitment; partial — при явном неполном payload, иначе unknown. Exact duplicate с тем же input_hash идемпотентен и не понижает status; distinct, несводимые кандидаты выбранного source дают conflicting. nap_total игнорируется, потому что не входит в этот metric. При нескольких sources используется существующий server source-priority; lower-priority источник не создаёт конфликт. duration_assessment имеет plausible/outlier/unknown: значение вне [3,14] ч сохраняется как наблюдённое outlier, а не превращается в partial. Definitive claim_eligibility=eligible требует complete+plausible+final; утреннее observation_eligibility=provisional допускает только settled-as-of-generation complete+plausible без action. missing — кандидата нет; imputed запрещён в V1; stale — сохранённый input hash больше не совпадает с текущим raw input.
  5. Финализация, утренний UX и поздние данные. Утром, как только есть coverage commitment и plausible candidate, сервер может показать один deterministic provisional sleep context с видимой маркировкой «по данным текущей синхронизации»; он объясняет только наблюдаемый паттерн, не даёт action и не вызывает provider. Это не пустая карточка и не definitive физиологический вывод. Запись для D получает final не раньше 18:00 tenant-local на D; тогда provisional observation либо подтверждается как definitive claim, либо исчезает/обновляется. Полный outlier сохраняется как final факт, но не участвует в claim. Её переводит не HTTP-read, а idempotent tenant-local finalizer: он запускается при ingestion, по существующему периодическому worker tick не реже раза в минуту и при startup reconciliation. Новый raw input с иным hash переоткрывает запись; он никогда не превращается в сон нулевой длительности. DST считается по tenant IANA location; если location отсутствует или невалидна, sleep context остаётся factual-only.
  6. Хранение, backfill и invalidation Фазы A. Новая таблица входит в tenant schema manifest, повышает schema-contract version и проходит обязательную stopped-service fleet migration этого репозитория. После миграции выполняется idempotent backfill последних 108 календарных дат для каждого active tenant: 94 дня нужны для reference, семь — для action cadence, остальное — операционный buffer. Backfill не изобретает отсутствующий coverage commitment: такие даты остаются unknown. Startup/provisioning запускает тот же writer, но не делает blocking full backfill на HTTP path. Изменение raw input пересчитывает только затронутый D, но помечает вычисления reference/cadence для дат [D, D+100] неактуальными: их не хранят как самостоятельную истину, а пересчитывают при следующем Today-read из канонических строк. В material hash Today входит digest всех canonical records текущих окон, поэтому поздняя правка старой ночи не может вернуть старый overlay из CAS/cache.
  7. Фаза B0 — утреннее наблюдение и definitive reference insight. Сервер считает только описательный recent_sleep_below_reference: медиана eligible+final канонических ночей в окне [D−93, D−4], минимум 60 из 90 календарных дат, в одном совместимом source/formula epoch; минимум три из четырёх ночей [D−3, D] должны быть не длиннее reference минус 0.5 ч. Утром D может быть только observation_eligibility=provisional, тогда как три предшествующие ночи final; copy явно отмечает current-sync state. После finalization все четыре ночи должны быть eligible+final: evaluation=true при выполнении условий, false — при тех же известных входах, но максимум двух коротких ночах; unknown — при missing/ineligible/conflicting/stale input, несовместимом epoch, недостаточной baseline или invalid timezone. Это historical reference, не sleep need. Server сам рендерит text; его полезность не зависит от AI.
  8. Фаза B0 — action event, presentation и конкуренция. Claim, in-product action и delivery event раздельны. На каждом evening Today=true при tenant-local времени в [18:00, 24:00) сервер показывает один wind_down: это мягкий non-medical шаг на текущий вечер, не notification и не расходуемый event. action_event существует дополнительно только если в предыдущих семи днях нет final true; его action_event_id=sha256(policy_version|source_epoch|D) используется только в reporting/delivery policy и больше не скрывает wind_down. unknown не стирает и не блокирует cadence: он логируется в coverage, но не превращает безопасный текущий факт в молчание. Любой provisional claim показывает observation без action. Две вкладки, locales и процессы получают один и тот же current action, а prefetch или failed render ничего не записывает. Если пользователь не открыл страницу в этот вечер, action не доставляется позже — это policy availability, не notification. Action подавляется при более сильном server safety guidance или дублировании в hero и sleep card.
  9. Фаза B1 — rich narrative slots. Она не меняет eligibility, factual snapshot, primary, recommendation или action. overall допустим только когда server-side DailyDecision опирается минимум на два свежих decision domains; sleep и recovery — только когда у domain есть distinct server-approved meaning. Один current energy verdict не запускает provider: его deterministic insight и action уже отвечают на вопрос без искусственного «объяснения» шкалы, хотя energy может быть фактологическим основанием общего server decision. Каждый eligible slot получает closed rich packet с локализованными facts, допустимыми display values, одной story relation, ID-происхождением и при наличии готовым action. Provider возвращает один цельный текст до 65 слов в 1–3 предложениях с закрытыми claim_ids/qualifier_ids/meaning_ids/position_ids; он может использовать только переданные numeric forms, но не новые расчёты, причины, прогнозы, диагнозы или действия. Server не приклеивает anchor: весь абзац проходит validation и либо накладывается, либо оставляет fallback. У каждого slot-а свой hash/fallback; поздний ответ не заменяет обновившуюся картину, а provider failure или null не скрывают server text и не считаются улучшением. До включения: 20–30 заранее зафиксированных privacy-minimized point-in-time snapshots во всех shipped locales, zero factual/safety violations и ≥70% pre-frozen narrative-eligible cases признаны владельцем продукта полезнее fallback. Fallback-only cases обязательны как safety controls, не имеют provider output и отдельно входят в published all-cases rate, но не размывают usefulness denominator. Если retained history не покрывает структурное состояние, разрешены максимум пять явно помеченных synthetic_controlled fixtures; они не являются фактами о пользователе и отдельно видны reviewer.
  10. Фаза C — описательный duration balance. Начать только с manual, versioned Sleep Goal с effective date; historical suggestion — отдельное будущее UX-расширение, не входящее в C. Ввести отдельные completed_sleep_episode для всех дедуплицированных, непересекающихся эпизодов сна (ночь и nap), не смешивая их с completed_night_sleep Фазы A. Для wake-date D balance-period — tenant-local [D−1 12:00, D 12:00): так ночной сон и предшествующий дневной nap попадают в одну воспроизводимую корзину. total_sleep_D — сумма пересечений episodes с этим периодом; UI обязан показывать calculated_through=D 12:00. Nap после этого момента относится к следующему периоду. Для будущих источников coverage contract обязан явно различать закрытый период и потенциально поздний эпизод; это не блокер A/B0. Полный outlier не исчезает: он участвует в арифметике, но помечает balance low_confidence и запрещает вывод model state/совета. Показатель balance_14d(D)=Σ(total_sleep_j−goal_j) для 14 последовательных balance-periods — воспроизводимая арифметика относительно цели, не физиологический debt. Если хотя бы один период неизвестен/partial/conflicting/imputed, current balance имеет incomplete, показывает coverage и дату последнего complete window, но не переносится как «актуальное состояние» и не подставляет средний сон.
  11. Фаза D — исследование восстановления, Need и следующего сна. estimated_baseline_need, modeled_sleep_state и recommended_sleep_duration проектируются и валидируются раздельно. Центральный outcome — не фиксированные восемь часов и не full readiness/battery как готовые labels: ночные sleep features (до сна → во сне) проверяются против sleep-independent утренней реакции (после сна): автономный residual из HRV/RHR/respiratory data, ночное восстановление батарейки без повторного вшивания текущей длительности сна и, при наличии, voluntary self-report. Full readiness и текущая EnergyBank остаются user-facing summaries, но не могут одновременно быть и predictor, и независимым доказательством, пока в их формуле есть сон. SpO₂ — отдельный quality/safety signal с device caveats, не коэффициент «сколько сна нужно». Baseline need может стать только явно помеченной preliminary/calibrated гипотезой: historical suggestion не превращается в truth после accept. Для state сравнить простые baseline-модели с воспроизведённой UMP; она остаётся исследовательским ориентиром для PVT-like performance, а не переводится в «долг в часах». Recommendation не изменяет balance_14d; efficiency используется отдельно для времени в постели, без дополнительной debt-надбавки. До этой фазы не выпускать claims persistent_sleep_debt, recovery_sleep_needed или late_bedtime, не взвешивать deep/REM и не давать stage «кредиты».
  12. Для primary и каждого домена сервер выбирает только eligible claim из закрытого Phase A/B catalog ниже, его evidence IDs и обязательные caveats. Cross-domain claim в V1 отсутствует; без перечисленных quality gates section получает eligible=false.
  13. Server-owned action catalog состоит только из существующего daily_decision и нового wind_down. daily_decision всегда главный; wind_down допускается только по точному sleep-claim. Модель не выбирает, не усиливает и не повторяет action.
  14. Провайдер возвращает строго NarrativeSlotV2: {version, locale, slot:{key:"overall",section}}, где Section={sentences:[{text,claim_ids,qualifier_ids,meaning_ids,position_ids}]}. В Section ровно одно interpretive предложение; выбранный server anchor в provider JSON отсутствует. null означает отказ только от модельной формулировки, а не пустой экран.
  15. Один валидатор перед сохранением и при чтении кеша отклоняет неизвестную версию/ключ/домен, duplicate/trailing JSON, неверную locale, новые periods/units/numbers, action/diagnostic/causal/prognostic language, чужой claim и непокрытый required qualifier. Он проверяет, что содержание каждого предложения полностью следует из его claims; claim IDs раскрываются сервером в evidence IDs. Provider никогда не выбирает action, state, факт, источник, доказательство или primary text.
  16. Измеримая text policy. Числа не запрещаются лексически: они разрешены только когда соответствующий claim уже содержит точное значение, единицу, период и правило округления. Сильнее запрета цифр — проверка того, что модель не усилила certainty и не придумала связь. Каждая локаль проходит frozen-corpus review; generic фразы без связи с сегодняшним claim не считаются улучшением.
  17. API получает отдельный optional overlay с version, input_hash, locale, generated_at и section {text, claim_ids, evidence_ids}. Старые observation, meaning, next_step и factual evidence не меняют семантику.
  18. React показывает overlay только при ready, совпавших input_hash/locale и fresh_for_snapshot=true; иначе сохраняет server explanatory copy. Hero имеет стабильный серверный заголовок, один AI-абзац и отдельное серверное действие.
  19. Канонический hash. DailyInsightNarrativeInputV2 сериализуется из fixed-order Go struct без map; domains и evidence сортируются по key/id. В hash входят input/policy/action versions, tenant-local date, discrete day_phase, flag state, closed claim IDs, evidence IDs/values/baselines/data states/confidence, ordered digest canonical records reference/current-four-night/cooldown окон и action_event_id. Исключаются generated_at, display timestamps, prose и одинаковые recalculation timestamps. Эквивалентный reordered input обязан дать тот же hash. Lease/CAS/backoff сохраняются; старые server_default записи устаревают через новую версию input/prompt.
  20. Ошибки чтения/записи narrative bundle становятся best-effort: factual snapshot отдаётся без overlay. Tenant-scoped today_insights_b0_enabled=false отключает новый canonical claim/server text/action; отдельный today_insights_b1_enabled=false отключает только provider generation. Оба flag входят в fingerprint для безопасного rollout/отката и не меняют существующий factual endpoint.

Риски и границы

  • Качественный текст не должен дорисовывать причинность, диагноз, лечение, прогноз или новый workout plan. Он связывает только server-selected claims; одного evidence allow-list недостаточно для достоверности смысла.
  • «Дефицит сна» и bedtime особенно чувствительны к определению: нельзя выводить накопленный долг из одной ночи, из медианы привычного сна или из mockup/неканонического source. Все sleep claims должны нести период, coverage, source/formula epoch и provenance.
  • Historical Goal — лишь предложение, потому что хронически короткий привычный сон способен занизить медиану. Population guidance не становится персональной потребностью. Accept Goal — UX-контроль, а не физиологическая валидация; baseline need, model state и recommendation нельзя объединять в одну формулу.
  • Отсутствующая запись не доказывает отсутствие сна. Для balance важно различать no data, partial, conflicting, complete outlier и eligible; неполное окно получает incomplete, а complete outlier — low_confidence, не незаметно сохранённый «актуальный» balance. Ночь и nap учитываются только через отдельные deduplicated episodes, один раз.
  • Эффективность и стадии сна — отдельные наблюдения. Они не увеличивают Need, не уменьшают balance и не получают коэффициенты «восстановительных кредитов» до собственной outcome-валидации.
  • Фаза A требует additive tenant migration и historical backfill. Нельзя включать definitive claim/action flag для tenant до успешного schema gate и завершённого idempotent backfill; иначе он недоступен, а не использует старый daily aggregate. Factual/provisional/data-guidance ответ остаётся доступен.
  • Правдоподобная длительность не доказывает полноту capture. Нужен versioned coverage commitment нашего ingest adapter для конкретной sync generation, а не недостижимое обещание внешнего vendor, что он никогда не пришлёт правку. Без contract capture_completeness остаётся unknown: нельзя «исправить» это эвристикой по quality=ok, timestamp или отсутствию второго source.
  • Промпт, JSON Schema и lexical validation не дают semantic guarantee. Поэтому B1 получает только server-built propositions и required qualifiers, а validator отклоняет текст, который усиливает claim или добавляет смысл вне packet. Lexical corpus полезен как negative evaluation, но не является safety gate; неподтверждённый текст никогда не заменяет fallback.
  • «Всегда есть ответ» не означает «всегда есть health совет». При data gap пользователь получает короткий нейтральный контекст и только уместный optional next step. Иначе незаслуженный sleep advice превращает честность в новый источник вредного шума.
  • Продуктовая честность не равна клиническому интерфейсу. Неопределённость должна ограничивать силу claim, а не доминировать над экраном; один и тот же стабильный gap дедуплицируется в нейтральный статус. Пользователь продолжает видеть остальные домены и не обязан предпринимать действие, чтобы получить ценность.
  • Нельзя калибровать сон на current full readiness или current EnergyBank без проверки состава: оба могут уже содержать sleep feature. Иначе модель подтверждает собственный predictor. Feedback также нельзя требовать или silently использовать как label до prediction_at; missing feedback — не отрицательный outcome.
  • Stopped-service migration здесь не означает, что additive DDL в PostgreSQL технически всегда требует downtime. Это существующий tenant schema-release contract, который атомарно доказывает совместимость registry, tenant markers и request pools. Online expand/contract потребовал бы отдельного двухконтрактного rollout design; обходить fleet gate в рамках insight-фичи нельзя.
  • Отсутствующие или частичные данные не надо маскировать «приятным» текстом: сервер заранее исключает недоступные отношения; provider может валидно не дать overlay, а server всё равно возвращает answer ladder с полезным factual/provisional контекстом без служебных оговорок.
  • Переход не должен нарушить legacy AI briefing, iOS-клиента или кеширование. Изменение API additive; старые narrative считаются устаревшими только для нового overlay.

Откат

Feature остаётся best-effort. При provider/validation/read-write проблеме narrative bundle API возвращает тот же factual snapshot и B0 server-text. Tenant flags today_insights_b1_enabled=false и today_insights_b1_preview_enabled=false немедленно отключают provider без потери B0; today_insights_b0_enabled=false дополнительно отключает новый catalog и wind_down без потери текущих карточек. Миграция Фазы A additive: откат бинарника не удаляет canonical rows и не меняет старые таблицы; включить feature повторно можно только после current contract audit. DB-rollback не предполагает destructive DDL.

Открытые решения

  • Рекомендация: не показывать пользователю технический ярлык «Фактическое обновление» при готовой интерпретации; заменить его спокойным «Обновлено».
  • Решение: V1 primary не является суммой трёх карточек и не создаёт cross-domain claim. Он объясняет только существующий daily_decision; сложные междоменные связи — отдельный будущий catalog revision.
  • Рекомендация: Bevel-like sleep copy реализуется через ограниченный server action wind_down, не через свободный совет модели. V1 называет только «несколько ночей короче обычного ритма»; слово sleep bank появляется лишь после Фазы C.
  • Решение 20 сентября: wind_down доступен на каждом confirmed current-evening true; action_event остаётся редкой семидневной границей только для reporting/delivery. В UI виден один компактный Sleep action, а B1 получает его точный развёрнутый server-owned текст; provider не создаёт и не меняет совет. Это снимает искусственную нехватку смысла в последующие вечера короткой серии, не превращая action в notification или в свободную медицинскую рекомендацию.
  • Решение 20 сентября: до final human quality gate допускается только явный tenant-only B1 preview: он запускает ровно тот же closed evidence packet и structural validator для одного выбранного профиля, но API/UI маркируют output как preview. Preview не пишет quality approval, не включает release flag и не распространяется на остальные tenant-ы; его можно отключить одним tenant setting.
  • Решение: каждый visible insight отвечает даже без eligible claim. Technical insufficient_data маппится на provisional_pattern, factual_context или data_guidance; в пользовательской copy нет пустой карточки, «я не знаю» и бесконечного «калибруется».
  • Решение: feedback/check-in остаётся добровольной secondary calibration signal. Его отсутствие не меняет serving; ответ после показа insight не может изменить эту же рекомендацию. Отдельно перед Phase D нужно утвердить минимальный объём label series и offline-calibration protocol.
  • Решение: будущий personal sleep model оценивается по разделённой цепочке «до сна → во сне → после сна». Full readiness и current EnergyBank не являются независимыми outcome, пока содержат sleep; сначала нужен explicit sleep-independent residual contract.
  • Решение для Фазы C: первый и последующие Sleep Goal задаются пользователем вручную и versioned effective date. Historical suggestion/accept — отдельное будущее UX-расширение, не часть расчёта C и не физиологическая Need.
  • Для Фазы D отдельно утвердить outcome-протокол, порог покрытия, набор кандидатов (simple balance / weighted / UMP), правила временного holdout и критерий, при котором model state действительно полезнее последней ночи. Только после этого обсуждать baseline need или recommendation следующего сна; они не входят в текущий AI-overlay release.
  • Перед B1 implementation согласовать и зафиксировать названия/периоды всех baseline claims. Модель не может выбирать между «средним за неделю», «личным средним» и «30-дневным baseline»; каждый comparison claim несёт один явный период и source.

Approval gate

Не начинать реализацию, не вызывать провайдера и не менять production до явного утверждения пересмотренного плана пользователем. После утверждения реализовать только Фазы A/B0: tenant-migrated canonical night record, coverage-generation adapter contract, morning provisional observation, evening finalizer, deterministic stateless action event, closed claim catalog, answer_kind ladder и server-text для одного общего плюс трёх раздельных инсайтов с серверными фактами/action/safety boundary. Контракт остаётся пользовательским наблюдением, не медицинским мониторингом: нет diagnosis/prognosis/treatment, а внутренние safeguards не должны заглушать ценность экрана или попадать в пользовательский текст. No-data states обязаны вернуть factual/provisional/data-guidance answer, а feedback не может быть required input. Morning observation включается только после теста adapter coverage commitment; definitive B0/action остаются выключенными для tenant, пока canonical 108-day availability report не рассмотрен, а proxy baseline выше не заменён replay на complete+plausible+final rows с новой семидневной cadence. До отдельного B1 quality gate UI рендерит только deterministic server text. После frozen-corpus review B1 допускается только как четыре независимых constrained narrative slot-а: overall для объединённой картины дня и sleep/recovery/energy только при distinct server-approved meaning; provider rollout и tenant enablement остаются отдельными подтверждениями. C требует отдельного approval для прозрачного balance относительно manual Goal; D — отдельного approval для sleep-independent recovery outcome, baseline need/model state/recommendation и optional feedback calibration protocol.

Статус-коррекция 12 сентября, corpus: read-only export расширен до 90 sanitised candidates за июнь–сентябрь; optional check-in lookup сохранил только answered/absent, без ответа, времени или ID.
