Implementation Plan: Readiness Monitoring Contract Cleanup

Approval required before implementation

Task Summary

Clean up readiness naive-layer monitoring after the sleep architecture evidence work. The goal is to make the monitoring panel distinguish false contract-lag warnings from real data-quality issues, especially for rolling/future-looking targets and Maria's sleep/chronic warnings.

Current Behavior

  • internal/storage/readiness_redesign_monitoring.go defines monitoring targets and computes coverage, drift, unknown-rate, and source-epoch alerts.
  • ContractLagDays is already supported and used for Acute Risk t+1..t+3 and Chronic Load t+1..t+14.
  • Recovery and Passive rolling_3d targets currently have ContractLagDays=0, even though the target rows are based on t+1..t+3. This makes a healthy mature window look like input pipeline lagging.
  • Monitoring currently reports top reason counts, but it does not expose the concrete offending dates for warnings such as sleep_total_out_of_range or event_window_data_missing.
  • Live post-deploy state on 2026-05-27 shows real warnings still mixed with likely false lag warnings: health rolling windows warn on input lag; health_mariia has Recovery sleep out-of-range and Chronic event-window gaps.

Desired Behavior

  • Recovery rolling_3d and Passive rolling_3d monitoring should treat only mature rows as expected by applying a 3-day contract lag.
  • Daily-point targets should keep their current near-real-time contract.
  • Monitoring warnings should remain visible for real low coverage, missing rows, stale input, drift, unknown rates, and source-epoch issues.
  • For coverage warnings, include a small diagnostic sample of offending dates/reasons so Maria-style warnings are actionable without manual SQL first.
  • No target formulas, baselines, chip thresholds, Telegram copy, or dashboard verdict behavior should change in this PR.

Likely File Changes

  • internal/storage/readiness_redesign_monitoring.go - update contract lag for rolling targets and add optional coverage issue samples.
  • internal/storage/readiness_redesign_monitoring_test.go - add tests proving rolling targets use mature windows and real stale input still warns.
  • internal/ui/handler.go - pass new issue samples through the admin fragment/API if the storage shape changes.
  • internal/ui/templates/partials/admin_readiness_monitoring.html - optionally render compact offending-date details in the existing monitoring table.
  • docs/ai-plans/2026-05-27-readiness-monitoring-contract-cleanup.html - update after implementation with actual checks and live results.

Implementation Steps

  1. Create a fresh branch from the current merged origin/main once local git fetch works cleanly.
  2. Add constants or explicit target config entries for the 3-day rolling target contract lag.
  3. Update readinessMonitoringTargets so Recovery/Passive rolling_3d use the mature 3-day window.
  4. Add or adjust tests for mature rolling windows: as-of 2026-05-27 should check windows ending 2026-05-24, not 2026-05-27.
  5. Add a small read-only diagnostic payload for coverage rows, capped to a few dates per row, containing date, eligibility reason, and eligible flag.
  6. Render that diagnostic compactly in admin monitoring, without turning the page into a noisy debug dump.
  7. Run local tests, then use live DB/API read-only checks against health and health_mariia after deploy/backfill.

Risks and Edge Cases

  • Applying a 3-day lag to daily targets would hide real fresh data problems; only rolling/future-looking targets should change.
  • Too many issue details could make the admin UI noisy. Cap samples and keep full counts as the primary signal.
  • Chronic monitoring already has a 14-day forward-window lag; do not regress that behavior.
  • Maria warnings may be real upstream data issues, not monitoring bugs. This PR should expose them clearly, not suppress them.

Rollback Plan

Revert the monitoring-only commit and redeploy. No schema migration or data rewrite is expected. If the diagnostic fields are added only to JSON responses/templates, rollback is code-only.

Open Questions

  • Should issue samples show only non-OK reasons, or also missing rows when the row count is below expected?
  • Should the fragment render dates inline in the comparison column, or add a separate compact details column?
  • Do we want a separate status for expected immature rows, or is contract-lag-adjusted windowing sufficient?

Implementation Update

  • Recovery and Passive rolling_3d monitoring now use ContractLagDays=3, so the recent coverage window ends on the latest mature target date instead of the current date.
  • Coverage rows now include capped IssueSamples for non-OK rows and missing dates. The admin fragment renders them as compact date/reason details under the existing comparison text.
  • No target writers, naive baselines, readiness chips, Telegram copy, dashboard verdicts, or schema definitions were changed.
  • Storage tests now prove that fresh-edge Recovery/Passive rolling_3d rows are ignored until the 3-day label window matures.
  • UI tests now check that JSON exposes the new issue samples and the admin fragment renders a concrete warning date/reason.
