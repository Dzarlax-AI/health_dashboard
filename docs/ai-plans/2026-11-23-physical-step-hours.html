Шаги в повторный час и явный ноль

Цель — один итог в API v2, Activity, Dashboard и при пересчёте истории для данных, в которых можно установить источник и физический час.

Что хранится сейчас

Первичный ключ старого почасового кэша содержит метрику, местный час и устройство. При переводе часов два наблюдения одного устройства могут иметь одинаковый ключ. API v2 располагает исходным смещением UTC и квитанцией синхронизации, которая позволяет отличить измеренные ноль шагов от отсутствия наблюдения. Текущий вход синтетической модели dbt содержит количество и качество, но опускает квитанцию и происхождение.

Воспроизведено на изолированном PostgreSQL через штатные методы Go. За 25 октября 2026 года 40 шагов Watch в 02:00 +0200 и 70 шагов iPhone в 02:00 +0100 дали 110 в API v2 и 40 в старом графике. На следующий день измеренный часовой ноль дал 0 в API v2 и пустой ряд в графике.

Согласованное решение

  1. Выделить из metric_compatibility_read.go общую SQL-проекцию шагов из нормализованных исходников. Выделять физический час по местному часу и смещению UTC. Сначала разрешать пересечение архива и синхронизации одного источника, затем применять согласованный приоритет устройств.
  2. Подключить эту проекцию к ограниченным по датам пересчётам, общим графикам и дневным итогам. В experiments/dbt_metrics передавать в модель необходимые сведения о происхождении. Сохранить формат существующих ключей, формат графика и разбивку по устройствам.
  3. Для старого часа, где сохранился итог устройства, а восстановить полные исходные данные нельзя, использовать прежний итог часа целиком до подтверждённого восстановления или отзыва. У такого часа точность ретроспективной оценки ограничена. Для полностью восстановимых часов использовать новый расчёт. Измеренный ноль учитывать при подтверждённой часовой синхронизации, отсутствие измерения сохранять как пропуск.

Проверка и риск

В повторный час с 40 шагами часов в первом интервале и 70 шагами телефона во втором ожидаются 110 шагов. Отдельно проверить день с подтверждённым нулём, старый ноль без квитанции, перекрытие архива и синхронизации, частичную доставку, явный отзыв, старый кэш без исходников, повторный пересчёт и изоляцию профилей. Сравнить длительность и план запросов при чтении одной даты и при полном пересчёте. Проверять обычные и исторические пути Go, dbt и HTTP.

Границы и откат

Работа локальная на синтетических данных. Изменение исторического алгоритма требует обновления идентификатора расчёта. До выпуска можно вернуть прежние вычисления и перепроверить те же данные в изолированной базе. Для установки и пересчёта реальных профилей потребуется отдельное решение.

Согласование

23 ноября подтверждено: для частично восстановимого старого часа сохраняется прежний итог до подтверждённого восстановления или отзыва. В таком случае две новые записи в повторный час с известными смещениями дают точное сравнение, а старому кэшу без подтверждения полноты нельзя приписать точное разбиение.

Локальная приёмка

  • Обычная синхронизация, дубликат и полный пересчёт сохранили 80 шагов у старого часа с неполными исходными данными. При восстановлении исходных записей расчёт снова учитывает приоритет устройств.
  • На двух синтетических профилях проверены часовые и дневные ответы HTTP v1 и v2 и значение в дневной витрине dbt. Повторный час дал 110 шагов. Поздняя поправка только в первом профиле изменила его итог на 114. На следующий день оба профиля вернули измеренный ноль.
  • При отсутствии смещения у пригодной старой записи весь местный час получает один итог. Если исходное число сохранено и однозначное восстановление невозможно, оно сохраняется. Для минут после пробуждения используются записи, которые можно отнести к этому интервалу.
  • Полный интеграционный прогон Go прошёл на одноразовом PostgreSQL. Для повторения проверок моделей используются пилот расчётов и замеры и сквозная проверка двух профилей.
  • Прогон Go/dbt прошёл 27 сценариев. Совпали все 17 650 почасовых и 380 дневных строк. Проверены повтор после прерывания приёма и сохранение старого дневного итога при полном пересчёте. На этом синтетическом стенде медиана трёх замеров записи Go за одну дату выросла с 12 до 34 мс, полного пересчёта — с 1,57 до 1,89 с. Пилот сохраняет планы PostgreSQL для обеих выборок.

Повторные записи одной физической точки

23 ноября согласованы исправление двойного учёта шагов в PR #291 и повторная проверка полного архива. Для одного источника и одного вида измерения одна и та же величина, полученная в один момент UTC под двумя локальными отметками времени, должна вносить один вклад. При осеннем переводе часов одинаковое время на циферблате может соответствовать двум разным моментам UTC. Оба вклада должны сохраниться.

Проверка охватывает позднее поступление копии, границу локальных суток, обновление ограниченного диапазона, полный пересчёт, чтение панели во время обновления и сохранность отправленных отчётов. Слияние и установка требуют отдельного решения.
