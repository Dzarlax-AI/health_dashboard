Implemented release contract

Candidate and source gates

  • Existing Go, database, web, contract, and security checks remain mandatory; path classification affects publication only.
  • Both standalone image contracts are checked before the full routed pair test.
  • Preflight validates role, API contract, and each component's expected revision before creating pair resources.
  • The routed test runs PostgreSQL, backend, frontend, and a pinned proxy and probes browser, API, auth, ingestion, MCP, legacy, and health routes.

Independent release

  • Backend and frontend use separate GHCR image repositories and full-SHA-tagged candidates.
  • Tags can move; exact image digests are the immutable component identities used by compatibility metadata and routed verification.
  • Each component publishes when changed or resolves its exact prior digest from the authoritative pair pointer when unchanged.
  • Backend and frontend revisions may differ; both component revisions and the current pair revision are preserved.
  • Main release runs are serialized so concurrent jobs cannot race the pair pointer.

Single authoritative pair pointer

The exact routed-tested digest pair is the release identity. The released-pair job creates compatibility-manifest.json, embeds those exact bytes in a scratch metadata image, verifies the metadata labels and embedded file, then atomically moves ${repo}-pair:compatible to that image.

Component latest tags are promoted only after the pair pointer succeeds and are non-authoritative conveniences. Compatibility must never be selected from either component's latest tag. The JSON artifact and metadata image contain the pair revision, API contract version, image names, exact digests, component revisions, roles, and creation time.

Generated credentials and all resources are disposable. Signal, failure-cleanup, resource ownership, and foreign-name collision cases are explicitly tested.

Known limitations and remaining risks

  • Hosted expressions: GitHub-hosted evaluation of job conditions, outputs, package permissions, and registry behavior still requires the PR CI run.
  • Hosted semantics: actionlint, YAML, pins, graph, expression placement, ordering, concurrency, and pointer assertions passed locally, but GitHub-hosted package and event behavior still requires the PR CI run.
  • First pair pointer: a selective main release needs an existing valid ${repo}-pair:compatible to resolve an unchanged component; conservative unknown/shared classification rebuilds both.
  • Mutable conveniences: operators could still misuse component latest; documentation and #217 deployment logic must consume the pair metadata instead.
  • Fixture versus production: the Nginx test router proves the route contract but does not replace the Traefik canary, rollback, and observability rehearsal in #217.
  • Architecture boundary: the manual backend ${sha}-arm64 image is architecture-qualified and intentionally excluded from the verified linux/amd64 pair.

Deviations and rollback

  • The original plan described same-revision candidates; the implementation deliberately supports different component revisions and records both.
  • The original plan treated compatibility metadata mainly as a CI artifact; the implementation adds one authoritative OCI pair-pointer image while retaining the JSON artifact.
  • The implementation added the router and classifier as focused helpers, while extending the pair harness instead of introducing another orchestration layer.
  • The harness uses canonical tenant_isolation bootstrap, startup provisioning, migrate, audit, finalize, and verify paths; it does not load a standalone init.sql fixture.
  • Before publication: revert the git/CI changes; no registry rollback is needed because no GHCR pointer or CI artifact has changed.
  • After publication: repoint the authoritative ${repo}-pair:compatible tag to a previously verified metadata image digest. If operator convenience requires it, repoint each component latest tag to the exact component digest recorded by that same prior metadata image.
  • Registry rollback never deletes candidate images, metadata images, digests, tags, or compatibility artifacts. It changes pointers only and does not require database rollback or production route changes.
